### 2b. 叙事（一次完整链路）

1. 用户输入 `/plan 给配置模块加校验`。`parse_slash`（`app/slash.py:64-75`）认领；`handle_input`（`app/commands.py:98,235`）分流到 `_handle_plan`（`commands.py:434`）。
2. `_handle_plan` 把姿态切到 plan+readonly：空闲时 `agent_loop.request_posture` 立即写 `session.mode="plan"`、`session.readonly=True`（`agent_loop.py:456-459`），命令层 `_save_session`（`commands.py:519,275`）；mid-turn 则进 `pending_posture`（`agent_loop.py:448-455`），回合 close 前落地（`:1364`），`_save_session` 缺失由 close 自带 save 覆盖（注释 `:471-474`）。
3. 有 topic → `plan_only`（`plan_runner.py:137`）：工作区外路径预检（`:157-159`）→ `begin_plan(topic)`（`:162-164`，重置 goal/items/step_deliveries/intervention_state，`session.py:375-389`）→ `continuations_disabled(loop, max_iterations=30)` 内执行 `loop.process_input(session, PLAN_PROMPT.format(topic))`（`:165-169`）。
4. 该回合中每个请求：system prompt = base + project + methods（按工具面裁剪）+ `<plan-mode>` 段（`prompt.py:127-138`）；工具 schema 只含 `mutates_world=False` 的工具（`agent_loop.py:1703`）；模型做只读探索（read/grep/glob/…）；任何 bash/write/edit 类调用被 dispatch 结构化拒绝（`dispatch.py:323,578-596`）。
5. 模型调用 `present_plan(plan=<markdown>, items=[{content,verify}...])`。工具先做结构校验（空 items → `no_plan_items`，`present_plan_tool.py:131-139`），然后经 `UserPromptCallback.ask("批准这个计划并开始执行？", ("开始执行","继续规划"), detail=plan, intent="plan_review")` 阻塞（`:140-146`）。
6. 前端 `ask.ts`/`session.tsx` 用 `intent="plan_review"` 渲染 `PlanReviewPanel`；approve 答案 = `{"choice":"approve"}` JSON（`util/ask.ts:47-49`），面板 `onAnswer` 同时置 `pendingPlanRun=true`（`session.tsx:626-629`）。
7. `present_plan.execute` 走 approve 分支：`items.clear()` + 逐条 `task.add(content, verify=verify)`，`armed=True`、`armed_profile="plan"`（`present_plan_tool.py:185-189`），返回 `_APPROVED`（"执行由系统接管…不要开始执行"）。列表变更经由 `agent_loop.py:1506-1515` 发 `TaskUpdated` → wire `plan.updated`（`bridge.py:143-164`）→ 转录计划卡 + 侧栏 goal 行（`state/session.ts:559-597`）。
8. 模型收到 `_APPROVED` 后简短收尾；本回合停步时进入 plan 分支的 stop guard（`turn_policy.py:307-321`）：`plan_submitted=True`（因为 `tool_success` 含 `present_plan`，`turn_books.py:401`）→ 直接 FINISH（`"model finished"`）。若模型没提交就停：注入一次 `PLAN_NUDGE`（`agent_loop.py:871-874`），再停则以 note `PLAN_UNSUBMITTED_NOTE` 结束（`:862-866`）。
9. 回合 close：`session.open_turn=None`、落地 pending posture、`TurnCloser.close` 保存（`agent_loop.py:1343-1378`）。arm 已在第 7 步写入同一内存对象，因此本 save 把它带到磁盘（`present_plan_tool.py:171-173` 注释）。
10. 12. 驱动循环：复查 armed → `next_item`（`plan_runner.py:465-473`，第一个无阻塞未尝试开项）→ 回合上限检查 → `before_round`（fiat 回填）→ `run_round`=`_run_step`：
    - 为步建 fresh `SessionData`（`ephemeral=True`、共享 task、seed 只列未完成项+本步验收+历史失败，`plan_runner.py:514-590`）；
    - 若有 verify，建 `AcceptanceItem(id="plan-n", statement=content, verify=...)`（`:653-658`）；
    - 换 policy：`max_iterations=8`、`stop_policy="natural"`、C3=0（`:667-670`）；
    - `process_input(step_session, "只做这一步，不要做别的：" + content…)`（`:680-683`，`STEP_HEAD` 在 `:47`）；
    - 计费一回合（`:687`）；验收不过 → 一次 repair（含失败输出、不含命令原文，`_repair_prompt:882-887`）；预算切断且未完成 → 一次 continue（`:695-705`，与 repair 共享唯一机会）；
    - `_settle`（`:791-829`）：verify 过→completed；verify 败→blocked（机械判定优先）；无 verify 且模型未标完成→stalled；写 `StepDelivery` 进 `report.deliveries` 和 `parent.step_deliveries`；
    - 父会话补两个气泡（step prompt + summary，`:735-771`）并发 `PlanStepReceipt` → wire `plan.receipt`；
    - 异常路径也留 blocked 收据与气泡（`:714-729`）。
13. 每轮后 `after_round`：`task.rounds_run++` 且 `_persist`（`:401-406`，崩溃点②）。`should_stop`：blocked → 整条 run 停止（`:408-413`，driver `task_driver.py:127-128`）。
14. 结束：`task.armed=False` + `_persist`（driver `:132-134` 与 runner finally 双侧）；`report.render()` 输出"完成 x 步 / 受阻 / 停滞 / 止于"（`:229-257`）。
15. 崩溃恢复：磁盘上 `task.armed=true` 的会话被 `find_armed_session` 选出（`world.py:66-91`）；`initialize` 判 `resume_count < 5` 后 `_launch_boot_resume`（`handlers.py:289-343`）；`_launch_armed_run` 先补 open_turn 的 `resume_turn`，再按 profile 跑 `PlanRunner`/`GoalRunner`（`:549-591`）。

## 7. 计划-执行衔接结论

**有 plan→approve→auto-execute**，共三种形式/边界：

1. **主路径（前端事件驱动）**：`present_plan` 评审 approve → 工具内写 items + armed（`present_plan_tool.py:185-189`）→ 前端置 `pendingPlanRun`（`session.tsx:627`）→ 该回合 `turn.finished` 时前端静默 `dispatch("/plan run")`（`session.tsx:489-495`）→ `_handle_plan("run")` → `PlanRunner`。【verified】
2. **崩溃恢复路径**：approve 后、run 派发前进程崩溃 → 磁盘 `task.armed=true` → 重启 `initialize` 自动 `_launch_boot_resume` → `PlanRunner`（`handlers.py:535-607`），上限 5 次（`handlers.py:201,324-332`）。【verified】
3. **手动入口**：任何时候 `/plan run` 都直接跑既有列表（`commands.py:470-506`）；run 结束 `finally` 强制回 normal（`:502-505`）。【verified】

边界与语义：
- approve 即 consent：批准的是"用户读到的这份列表"（替换语义，`present_plan_tool.py:176-180`）；空 items 不能被批准（`no_plan_items`，`:131-139`）。
- run 期间每步独立会话、步预算 8 迭代（`config/models.py:111`）、C3 禁（`plan_runner.py:667-670`）、repair/continue 各最多一次（共享，`:688-705`）。
- 失败语义：verify 败=blocked 且**整条 run 停止**（`plan_runner.py:408-413`）；无 verify 未标完成=stalled，记录后继续下一 ready 项（`:821-823`）；无 ready 且存在未尝试开项=deadlock（`:366-373`）；run 回合上限 `plan_max_step_turns=20`（`config/models.py:123`）。
- 执行后列表状态留在会话（步骤账目 + 收据 + 气泡），再次进入 Plan 可继续（`commands.py:464-466` 提示未执行项）。
- 非 goal 的 auto-run 不会自主重试 failed run：blocked 后需要人（或模型）再次发起 `/plan run` 或重规划。【verified：无自动重试代码路径；仅在 boot 时 armed 才自动续】

- 机制 [verified]：提交守卫只在"模型停步"时施压（`turn_policy.py:307-321`），`present_plan` 的 `items` 是 required（`present_plan_tool.py:108`）且空数组被 `no_plan_items` 拒（`:131-139`）；prompt 语义是"every request is answered with a plan"（`prompt.py:129-130`）、PLAN_PROMPT 同构（`plan_runner.py:68-88`）。
- 结论修正 [inferred]："只能编一个假计划"偏强：守卫只给一次 NUDGE，模型第二次停步仍可结束（outcome.note=PLAN_UNSUBMITTED_NOTE，`agent_loop.py:862-866`）。准确说法是：**没有一等公民的"只研究、不规划"出口**；退出只有 (i) 忽略 nudge 二次停步（带"未提交计划"的负面注记），(ii) 编一份能过 items 校验的计划，或 (iii) `ask_user`/对话说明后停。且 plan 工具面不含 websearch/webfetch（见 (b) 同类过滤），"纯研究"连联网检索也没有。
- 相关派生事实 [verified]：守卫对 `readonly=True` 也会生效（`turn_policy.py:312`），即 `/readonly on`（mode=normal）会话也被要求交计划。

### (b) subAgent 在 plan 下被过滤
- [verified]：`SubAgentTool`（`subagent_tool.py:119`）只声明 `parallel_safe=True`（`:124`），未覆写 `mutates_world` → 默认 True（`base.py:106`）→ 被 `_readonly_schemas` 排除（`agent_loop.py:349-350`）+ dispatch 拒绝（`dispatch.py:323`）。旁证：`base.py:105` 注释明确把 `subAgent` 描述为 "runs arbitrary work yet is parallel-safe"；`SubAgentListTool` 反而 `mutates_world=False`（`:337`），所以模型能看到子代理表却开不了新子任务。
- 附带同类 [verified]：webfetch/websearch/mcp_call/memory_write/job_kill 也因未覆写被一并过滤（`webfetch_tool.py:147/198`、`websearch_tool.py:39/80`、`mcp_call.py:37/41`、`memory_write_tool.py:30/33`、`job_tools.py:159`）。

### (c) todo_write 在 plan 下仍可见，仅靠 prompt 禁止
- 可见性 [verified]：`mutates_world=False`（`todo_write_tool.py:25`）。
- "仅靠 prompt" 部分不准确 [verified]：
  - prompt 层确实禁止（`plan_runner.py:75` "Do not track the planning with todo_write"；`prompt.py:133-134`）；
  - 但还有一层运行时拒绝：readonly 下 `update→completed` 被拒（`todo_write_tool.py:104-117`）；
  - `clear` 动作已删除（enum 只有 add/update/list，`todo_write_tool.py:58`；`TaskState.clear` 已随 e71861c 移除，`domain/task.py` 无该方法）。
  - 仍可用的：add / update(pending/in_progress/dropped, verify, depends_on) / list —— 也就是说模型仍能在规划期用 todo_write 起草列表（执行期批准时会被整体替换掉，`present_plan_tool.py:185`）。

### (d) verify 批准后无法修正
- [verified]：repair prompt 不包含 verify 命令原文，只含失败输出（`plan_runner.py:882-887` 拼 `self._verify_output(step_session)`；`item.verify` 未出现），也没有"修改 verify"的指引；文案只说"只修复失败点"。
- [verified]：verify 失败 → `task.update(id, status="blocked")` + `report.blocked`（`plan_runner.py:812-820`），`should_stop` 返回 True（`:408-413`）→ `task_driver.py:127-128` break → **整条 run 停止**，后续步骤不再执行。
- 还原路径 [verified]：blocked 项保持 open（非 terminal，`task.py:23,225-226`），下一次 `/plan run` 会在 `_next_ready` 里重新选中并重试（`plan_runner.py:465-473`）；seed 会带上"此前已尝试 N 次 + 上次结果"，要求"从上次停下的地方继续"（`:573-589`）。修改 verify 本身只能靠重规划（present_plan 替换列表）或在执行步里 `todo_write(update, verify=...)`（工具在步会话里可用），但**没有任何 prompt 引导**这一点。[后句 verification: 工具面允许；引导缺失 = inferred from absence]

### (e) guard 只在 stop 时触发
- [verified]：`PlanSubmissionGuard.on_stop` 唯二调用点在 `decide_after_step`（`turn_policy.py:307-321`），即"模型本轮不再请求工具"之后；`decide_next_iteration`（回合中途）不经过 stop guards（`:251-303` 只跑 PRE 阶梯：strategy/fatigue）。
- 中途唯一的压力块是预算压力（`turn_policy.py:371-404`；注入 `request_assembly.py:224-230`），与"提交计划"无关。
- 结论：**没有"先交计划再探索"型的回合内压力**；PLAN_NUDGE 的"不能以纯文本收尾"只发生在第一次停步之后。[verified]
