## 0. 这一轮到底要做什么

M2 在依赖图上是 `{T1,T10,T2} ─► T3` 与 `T2 ─► T6`（`08` §4.0）。
T1（agent 表）与 T10（四态 + durable pending）已由 M1b 落地，T2（规则语言）已由 M1a 落地。
所以 M2 的**实际内容是两件事**：

| 任务 | 内容 | 治的缺陷 |
|---|---|---|
| **T3** | 提醒内化：plan 的提醒变成 **durable 的合成消息**，在**请求边界**投递、**每请求对账** | B1（姿态是字段不是事件）/ B2/B4（规划指令一次性、无对账、退出不撤销）/ B3（规划指令非 synthetic 污染三个读者）/ G6（退出 plan 不撤销历史里的指令）/ G7（规划指令对用户可见） |
| **T6** | 软/硬只读开关：`plan_strict_readonly`，把只读从 **dispatch 的结构特判**改成**规则层的一条声明** | C1（只读与权限表两套谓词）/ C3（两轴拆开时提示成假话）/ G3 / D08 |

**T4（研究出口）已由 N1 落地**（`18`），**T12（计划提示词 v2）依赖 T3**，本轮不做。

### 0.1 为什么 T3 与 T6 必须同一批

它们看起来是两件事，但它们共用**同一个根**：

> 「plan 模式是什么」今天由**三处**分别回答：prompt 的静态 `<plan-mode>` 段说一套，
> dispatch 的 `ctx.readonly` 特判做一套，命令层的 `session.mode` 又做一套。

T3 把「提醒」变成一件事（durable + 每请求对账），T6 把「只读」变成一件事（一条规则）。
两者做完，plan 模式的语义就只剩**一个**来源：`session.agent` + 它的规则层。
分开做会留下中间态 —— 提醒已经是 durable 的、只读还是特判 —— 那正是今天的样子。

## 1. 核验：今天的相关设计（逐处实测）

### 1.1 规划指令今天的形状

`core/plan_runner.py:424`：

    await loop.process_input(
        session, f"{PLAN_MARK}{PLAN_PROMPT.format(topic=topic)}", ...

**一次性 user 消息**，`PLAN_MARK = "[plan] "`（`:55`）。
它带来四个已知问题（都是实测过的，不是推测）：

| # | 问题 | 今天的证据 |

### 1.2 只读今天的形状

**结构特判**，在权限门**之前**。它的后果：

### 1.5 竞品事实复核（在同 commit 源码上）

#### opencode：提醒怎么做的（`packages/core/src/plugin/plan.ts`）

    // 1. 切换时：事件订阅
    ctx.event.subscribe().pipe(
      Stream.filter((event) => event.type === "session.agent.selected"),
      Stream.runForEach((event) => {
        const text = switchReminder(event, enterReminder)   // enter / leave
        return ctx.session.synthetic({ sessionID, text, resume: false })
      }),
    )

    // 2. 每请求对账：context hook
    ctx.session.hook("context", (event) => {
      const reminder = lastReminder(event.messages, enterReminder)
      const missing = event.agent === plan && reminder !== enterReminder
      const stale  = event.agent !== plan && reminder === enterReminder
      const text = missing ? enterReminder : stale ? leave : undefined
      if (!text) return
      // 3. 插入位置：最后一条 user 之前
      const at = event.messages.at(-1)?.role === "user"
        ? event.messages.length - 1
        : event.messages.length
      event.messages.splice(at, 0, Message.user(text))
      return ctx.session.synthetic({ sessionID, text, resume: false })
    })

**四个可抄的机制**：

1. **两条文本**：`enter`（你在 plan 模式）与 `leave`（你不在了）。leave 是**显式撤销**，
   不是「不再加新的」—— 这治 G6。
2. **`synthetic({resume: false})`**：进 inbox 而**不是**立刻成消息，
   由**请求边界**投递 ⇒ 切换不会打断正在跑的回合。
3. **每请求对账**：`lastReminder()` 扫消息找最后一条提醒；缺了就补、
   过期了就换成 leave ⇒ 压缩把提醒吃掉后会自动补挂（治 B2/B4）。
4. **插入位置**：最后一条 user **之前** ⇒ 提醒在「人刚说的话」旁边，
   而不是压在最底下。

#### dsh：姿态是事件，不是字段（`packages/plan/plan-mode/src/index.ts`）

    // log-only 事件，整值替换，最后一条赢
    session.append('plan/mode', { active })

    // pending 是进程内 WeakMap —— 崩溃丢（我们要 durable，M1b 的 sidecar 已给）
    private readonly pendingIntents = new WeakMap<Session, {active, narrate}>()

    // 边界提交：下一个 accepted pre-step
    ctx.on('agent/pre-step', async ({agent, signal}, next) => {
      const decision = await next()
      const pending = this.pendingIntents.get(agent.session)
      if (decision.kind === 'reject' || signal.aborted || pending === undefined) return decision
      this.onBoundary(agent.session)      // 追加日志事件
      return !pending.narrate ? decision : { ...decision, messages: [...decision.messages, narration] }
    })

**可抄的**：「pending → 边界提交 → 叙述注入」的三段；
**不可抄的**：进程内 WeakMap（崩溃丢）—— 我们的 M1b sidecar 已经是 durable 的，
而 dsh 自己也把这个列为反例（N05）。

#### 结论：M2 抄什么、不抄什么

| 抄 | 不抄 | 为什么 |
|---|---|---|
| enter/leave **两条**文本 | — | 治 G6（显式撤销） |
| 每请求**对账**（缺了补、过期了换） | — | 治 B2/B4（压缩后自愈） |
| 插入在**最后一条 user 之前** | — | 提醒紧邻人的话，而不是压在最底下 |
| 提醒是 **synthetic** | — | 治 B3（不再污染三个读者） |
| pending → **边界提交** | dsh 的**进程内** WeakMap | 我们有 sidecar（durable） |
| — | dsh 的 `plan/mode` **log-only 事件** | 我们已有 `session.agent` 这个权威字段；再造一个事件源就是**第二个真相源** |
| — | opencode 的**整条 inbox 机制** | 我们已有 `pending_posture` sidecar；T3 要的是「提醒」，不是「输入投递」 |

## 2. 目标设计

### 2.1 T3：提醒内化

#### 2.1.1 提醒的形状

**新** `ai_coding/core/plan_reminders.py`（08 T3 点名的文件）：

    PLAN_ENTER_REMINDER = (
        "<system-reminder>You are in Plan mode. …</system-reminder>"
    )
    PLAN_LEAVE_REMINDER = (
        "<system-reminder>You are NO LONGER in Plan mode. …</system-reminder>"
    )

两条文本**各一个定义**。opencode 用 `enter(directory)` / `leave`，
它的 enter 带 plan 目录路径 —— 我们**没有**那个目录（T5 才引入），
所以 enter 不提目录，只讲「只读 + 两个出口」。

#### 2.1.2 什么时候发

**由 `commit_posture` 触发**（agent 变了才发）：

    if target_agent != previous:
        # 1. 记历史（M1b 已有）
        # 2. 发 AgentSwitched 事件（M1b 已有）
        # 3. 【新】排一条提醒
        self._queue_reminder(session, text_for(previous, target_agent))

`text_for` 的规则（照 opencode 的 `switchReminder`）：

| 从 | 到 | 提醒 |
|---|---|---|
| 非 plan | plan | **enter** |
| plan | 非 plan | **leave** |
| 非 plan | 非 plan | 无（换了个自定义 agent，不是姿态变化） |
| plan | plan | 无（没变） |

#### 2.1.3 怎么投递（durable + 边界）

| 阶段 | 做什么 |
|---|---|
| **排队** | `commit_posture` 把提醒写进 `session.pending_reminders`（durable，形状与 `pending_posture` 同型：sidecar） |
| **边界投递** | `_apply_pending_posture` 之后、turn close 的 save 之前 ⇒ 提醒随回合的 save 落盘，**零新保存点** |
| **每请求对账** | `RequestAssembler.assemble()` 每轮检查：当前应是 plan 但历史里没有 enter ⇒ 补一条；当前不是 plan 但最后一条是 enter ⇒ 补一条 leave |

**为什么提醒也要 sidecar**：与 M1b 的 pending_posture 同理 ——
排队发生在**回合运行中**，此时写会话文件会跑 `ensure_tool_pairing`，把在途的 carrier 丢掉。
而且「切换已落地但提醒还没投」是一个**真实存在的中间态**（进程正好死在中间），
崩溃恢复后必须能补上 —— 这正是 opencode 的 `context` hook 每请求对账要解决的事。

#### 2.1.4 提醒长什么样（一条消息）

    {
      "role": "user",
      "content": "<system-reminder>You are in Plan mode. …</system-reminder>",
      "synthetic": true
    }

**是 synthetic** ⇒ B3 的三个读者自动正确：

| 读者 | 今天 | T3 之后 |
|---|---|---|
| `human_utterance` | 特判 `PLAN_MARK` | **特判可删**（synthetic 已经排除） |
| 前端 replay | 特判 `PLAN_MARK` | **特判可删** |
| 压缩锚点 | 躲 `PLAN_MARK` | 走 synthetic 的既有规则 |
| `/undo` | 可能摘错 | synthetic 不会被当成「真人回合」 |

**但**：`plan_only()` 的**规划指令**（`[plan] ` + PLAN_PROMPT）**仍然要保留**——
它是**这一轮**的任务（"为 X 写计划"），不是**姿态**（"你在 plan 模式"）。
T3 把**姿态提醒**内化，不动**任务指令**。
⇒ 规划指令也该标 synthetic 吗？**该** —— 它是 harness 写的。
但 `PLAN_MARK` 前缀要保留（前端用它跳过这一行，且 `19` 的 B3 修法就是"标 synthetic"）。

#### 2.1.5 静态 `<plan-mode>` 段怎么办

08 的 C14 说：「静态段与软/硬档一致，不矛盾」。

**决定**：静态段**保留但收窄**。它继续说「只读 + 两个出口」，
因为它是**每请求都在**的稳定事实（cache 友好、模型不会忘）；
而 enter/leave 提醒是**变化时的一次性事件**（撤销、恢复）。
两者的分工是：

| | 静态段 | enter/leave 提醒 |
|---|---|---|
| 说什么 | 「plan 模式下怎么工作」 | 「你刚进入/离开了 plan 模式」 |
| 何时变 | 姿态变了就变 | 切换时一条 |
| 为什么 | 模型**每轮**都需要 | 模型**只在切换那一轮**需要 |

静态段里**不能**说的话：「bash/write/edit unavailable」——
那是 T6 的软档内容，会随 `plan_strict_readonly` 变。
⇒ 静态段改为**不含具体工具名单**，由工具面自己说话（M1b 的 `_surface_tools` 已经按规则裁剪）。

### 2.2 T6：软/硬只读开关

#### 2.2.1 目标形态

`plan` agent 的规则层（`domain/agents.py` 的 `AgentSpec.permissions`）从「空」变成「有」：

    软档（默认，plan_strict_readonly = false）：
      (deny edit *)                # edit = write + edit 两个工具
      (allow edit <plan dir>/*)    # plan 目录可写 —— 但目录还没有（T5）

    硬档（plan_strict_readonly = true）：
      软档 + (deny shell *) (deny subagent *) (deny webfetch *) (deny websearch *)

**08 T6 的原话**：「软/硬只读开关：`plan_strict_readonly`；软档 = 基础 allow + edit deny/plan 目录 allow
（shell/subagent/web/MCP 仍 allow）；硬档追加 deny；**不通过设置 `readonly=True` 实现**（保留 `/readonly` 独立 overlay）」

#### 2.2.2 与今天的等价性（**这是 T6 的硬约束**）

今天的软档 = `ctx.readonly` 特判 ⇒ **所有** `mutates_world` 工具被拒。
今天 `mutates_world=True` 的工具：write / edit / bash / subAgent / present_plan / finish_research /
start_goal / update_goal / job_* / webfetch / websearch / memory_write …（需实测清单）。

**08 的软档比今天的特判**宽**（shell/subagent/web 仍 allow）。
所以 T6 **不是**等价迁移，而是**改变行为** —— 这需要拍板（见 Q2）。

若采用「软档 = 今天的特判」：那 `plan_strict_readonly` 就是个空开关（没有第二档）。
若采用「08 的软档」：plan 模式**变得可写 shell**，这是行为变更，且 C4（「批准即自动执行」）
与 D09-D11 会重新打开。

#### 2.2.3 `mutates_world` 怎么办

**不删**。它有两个消费者：

1. `dispatch.py:340` 的特判 —— T6 要**换掉**这个消费者；
2. `tools/base.py` 里每个工具的声明 —— 它是「这个工具会不会改世界」的**事实**。

但**事实与判定要分开**：

| | 是什么 | 谁定 |
|---|---|---|
| `mutates_world` | **事实**：这个工具会不会改世界 | 工具自己声明（不变） |
| 规则层的 `deny edit *` | **判定**：在这个 agent 下能不能改 | 规则层（T6 新增） |

⇒ T6 之后：`mutates_world` 仍用于**其它**地方（前端工具表、`/readonly` 的语义），
但 plan 的只读**不再由它决定**。

#### 2.2.4 `/readonly` 怎么办

**保留为独立 overlay**（08 T6 明确：「保留 `/readonly` 独立 overlay」）。
它仍走 `ctx.readonly` 特判 ⇒ `/readonly on` 的行为**零变化**。

⇒ 于是有**两条只读路径**：

| | 触发 | 判定 | 文案 |
|---|---|---|---|
| `/readonly on` | 人显式开 | `ctx.readonly` 特判 | `readonly_denied`（不变，G9 的修法） |
| plan agent | 姿态 | 规则层 deny | 规则层的 reason |

这**两条会不会打架**？会 —— 同一个工具可能被两条理由都拒。
**裁决**：规则层**先判**（它更具体、有 reason），特判**兜底**。
这与 M1b 的 agent 否决层同一形状（先具体后宽泛）。

## 3. 数据流

### 3.1 一次 `/plan`（进入）

    /plan <topic>
      → commands._handle_plan
        → loop.request_posture(session, agent="plan", readonly=True, reason="/plan")
          → turn_running? 否 → commit_posture
              ├─ session.agent = "plan"; session.readonly = True
              ├─ agent_history += {build → plan, ts, reason}
              ├─ _emit(AgentSwitched)          → 前端 notice
              ├─ 【新】_queue_reminder(ENTER)    → session.pending_reminders + sidecar
              └─ 清 pending_posture
        → 规划回合：
          RequestAssembler.assemble()
            ├─ 压缩历史
            ├─ 对账：当前是 plan，历史里没有 enter？→ 补一条 ENTER（synthetic）
            └─ 尾部块 + 静态段（收窄后）
          → 模型看到：「你在 plan 模式」（提醒）+「plan 模式下怎么工作」（静态段）
    回合收尾
      → _apply_pending_posture（无 pending）
      → 【新】_apply_pending_reminders → ENTER 消息入历史
      → close 的 save ⇒ 提醒与姿态一起落盘

### 3.2 一次 `/plan off`（离开）

    /plan off
      → commit_posture(agent="build", readonly=False)
          ├─ agent_history += {plan → build}
          ├─ _emit(AgentSwitched)
          ├─ 【新】_queue_reminder(LEAVE)
          └─ 清 pending
      → 下一回合的对账：当前不是 plan，但历史最后一条是 ENTER？→ 补一条 LEAVE
    ⇒ **显式撤销**：模型读到「你不在 plan 模式了」，而不是「历史里没有新的 enter」

### 3.3 压缩把提醒吃掉之后

    历史被压缩 → ENTER 那条可能没了
      → 下一轮对账：当前是 plan，历史里没有 enter
        → 补一条 ENTER（synthetic）⇒ 模型重新知道自己只读
    ⇒ 治 B2/B4（「压缩后模型忘记自己是 plan 模式」）

### 3.4 崩溃恢复

    commit_posture 落地了姿态，但提醒还在 sidecar 里（没投）
      → 重启 → load → session.pending_reminders 被回填
        → 下一回合的边界 → 提醒投出
    ⇒ 与 M1b 的 pending_posture 同一形状

### 7.1 Q1=A 的连锁修正：action 走**小写工具名**，别名表只做语义分组

实测（`permission_gate.py:540` 的 `name = tool_name.lower()`）：gate 把 action **小写化**后匹配。
所以规则里必须写**小写**的工具名 —— 这不是「缺陷」，base 层本来就是小写的
（`_allow_tools` 里是 `"subagent"` 不是 `"subAgent"`）。

⇒ **`04` 号文的别名表要按小写重写**，且它的 `subagent`/`read` 两行是**恒等**（小写即命中）：

| action | 命中工具（小写） | 备注 |
|---|---|---|
| `edit` | `write`, `edit` | **真分组** —— 一个 deny 同时挡住两个工具 |
| `shell` | `bash` | **真分组** |
| `question` | `ask_user` | **真分组** |
| `subagent` | `subagent` | 恒等（`subAgent` 被小写化） |
| `read` | `read` | 恒等 |
| 其余 | 即工具名 | |

**实测出来的坑**（实施前必须知道）：

    gate.check("subAgent", …, agent_rules=(Rule("subAgent", …),))
    → ALLOW      # 规则写 "subAgent" 永远不匹配（gate 把它小写成了 "subagent"）
    gate.check("subAgent", …, agent_rules=(Rule("subagent", …),))
    → DENY       # 写小写才对

⇒ **别名表必须小写**，否则 M1a 就有「`subAgent` 永远拦不住」的洞。
本批**顺手**把这条钉成测试（它是 M1a 的既有缺口，不是 M2 引入的）。

### 7.2 Q2=A 的连锁修正：`readonly` 的两类消费者要分开

实测：`session.readonly` 有 **6 个**读者，分两类：

| 类 | 读者 | Q2=A 之后 |
|---|---|---|
| **语义类**（4） | `agent_loop._verify_acceptance`（只读不跑证明命令）/ `turn_policy.decide_after_step`（只读不催工具）/ `todo_write_tool`（只读不能标 completed）/ `goal_tools.start_goal`（只读不能起目标） | **保留 overlay** —— 它们问的是「这个会话是只读的吗」，不是「这个工具能不能调」 |
| **工具拒绝类**（2） | `dispatch.py:340` 的结构特判 / `agent_loop._surface_tools` 的 `mutates_world` 过滤 | **改由规则层承担** —— plan agent 的规则产生同样的 deny |

⇒ **`/plan` 之后 `readonly` 仍设为 True**（语义类消费者要它），
但**工具拒绝**改由 plan agent 的规则决定。
⇒ 于是 `/plan` 与 `/readonly on` 在**工具面**上等价，在**语义**上也等价 ——
这是今天就成立的性质（今天的 plan 就是 readonly=True）。

⇒ **裁决顺序**（`dispatch.py`）：规则层先判（有 reason），`ctx.readonly` 特判兜底。
与 M1b 的 agent 否决层同一形状（先具体后宽泛）。

### 7.3 Q2=A 的软档规则集（等价迁移的精确清单）

今天的特判挡掉的是**六个**工具（实测 `mutates_world=True` 的全部）：

    bash, edit, subAgent, webfetch, websearch, write

⇒ plan agent 的软档规则（小写 action）：

    (deny edit *)      # → write + edit（别名）
    (deny shell *)     # → bash（别名）
    (deny subagent *)  # → subAgent（小写化后命中）
    (deny webfetch *)
    (deny websearch *)

**硬档**（`plan_strict_readonly = true`）在此之上追加：

    (deny question *)      # → ask_user
    (deny todo_write *)    # 规划期不能改清单？（M3 的 T8 才是隐藏 todo，这里先只 deny）
    (deny memory_write *)  # → 记忆写入
    (deny start_goal *) / (deny update_goal *)
    (deny present_plan *) / (deny finish_research *)  # ← 见 §7.4

### 7.4 一处必须说清的矛盾：硬档不能 deny present_plan / finish_research

`present_plan` 与 `finish_research` 是 **plan 模式的两个出口**（`18` 的 N1）。
硬档若 deny 它们，plan 模式就**没有出口** ⇒ 守卫会一直催 ⇒ 回合永远收不了。

⇒ **硬档不 deny 这两个**。硬档收紧的是「能不能改世界」，
不是「能不能交卷」。

### 7.5 Q3=A 的连锁：提醒进历史 ⇒ 前端要会跳过它

提醒是 `role=user` + `synthetic=true`。
前端 replay 的 synthetic 分支（`replay.ts`）已经会跳过它 ——
但**只对非 steering 的 synthetic**；提醒不带 steering 前缀 ⇒ 会被跳过。✅

⇒ 前端**零改动**（除了可能的顺序调整）。这是 Q3=A 的额外好处。
