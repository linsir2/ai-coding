## 3. 目标设计

### 3.1 M4a：安全收口

#### L1 软链 TOCTOU

**根因**：同一次写入被解析两次，两次之间路径可被替换。

**目标**：把"解析"收敛到**打开文件的那一刻**。

新增一个工具函数（放 `security/sandbox.py`，与现有 `Sandbox` 同文）。
**唯一签名**是下面的 `open_inside(root, path, *, mode)`；不再暴露 raw flags，
也不把 `/proc` 当依赖：

```python
def open_inside(
    root: Path,
    path: str | Path,
    *,
    mode: str,
    create: bool = False,
) -> OpenedFile:
    """Open ``path``, refusing any symlink on the way to it.

    Every component is opened with ``O_NOFOLLOW | O_DIRECTORY`` relative to
    the previous fd (``dir_fd``); the last one with ``O_NOFOLLOW`` as well.
    ``mode`` is ``"read"``, ``"readwrite"``, ``"write"`` or ``"append"``;
    ``create`` adds ``O_CREAT`` (and therefore needs ``"write"``).  The caller
    cannot pass raw flags: the mode decides ``O_TRUNC``.

    Returns an ``OpenedFile`` with the fd, relative path, and a display path.
    The caller owns the fd and must close it.
    """
```

**为什么不用「开完再读 `/proc/self/fd`」**：那只是**事后**发现越界，
文件已经被创建/截断。逐段 `openat` 是**事前**拒绝，且不依赖 `/proc`。
`os.open(..., dir_fd=..., nofollow)` 在 Linux 上可用（已实测：
中间组件是软链时报 `ENOTDIR`）。

**非 POSIX / 无 `dir_fd` 平台**：`open_inside` 抛 `SandboxViolation`，
plan 目录写入直接不可用（fail-closed）。这是 `os.supports_dir_fd` 的判断，
不是第二套实现。

**评审补充：光有 `open_inside` 不够。** 同一条路径上还有三处仍按名字操作：

1. `WriteTool` 的 `target.parent.mkdir(parents=True)` 会**跟随**父目录软链
   ⇒ 改用 `mkdirat` 逐段（与 `open_inside` 同一套遍历，抽成
   `_walk_to(root, path)` 返回最后一层的 dir_fd）。
2. `artifacts` 里的 `target.relative_to(...)` 与 `target.stat()` 是**再次按名
   判断** ⇒ 用已验证的 fd 链算出相对路径，`stat` 走 `os.fstat`。
3. `EditTool` 是读-改-写：必须 `openat(O_RDWR|O_NOFOLLOW)` 一次，
   在同一个 fd 上 `read` → 改 → `ftruncate` + `write`，不能二次 `write_text`。

**plan root 的注入**：`WriteTool` / `EditTool` 的构造函数新增可选的
`plan_root: Path | None = None`（由 `tools/builder.py` 用
`Sandbox.workspace / PLAN_DIR` 传入，复用 `domain.agents.PLAN_DIR` 唯一
契约，不新增配置项）。只有 `ctx.mode == "plan"` 且 `plan_root` 存在时才走
fd 写入；build/readonly 保持现有 path 写入。plan 姿态下路径先按现有
`Sandbox.resolve` 做授权判定，再交给 `open_inside` 做 fd 级安全打开；
相对路径相对 workspace，绝对路径必须位于 workspace。两者都不能绕过 plan
目录。

`WriteTool` 在 plan 姿态下用 `open_inside(plan_root, path, mode="write",
create=True)`；`EditTool` 用 `mode="readwrite"`。前者在同一 fd 上
`ftruncate` + 写入，后者在同一个 fd 上读-改-写。`OpenedFile.relative_path`
直接用于 artifact，`os.fstat(fd)` 直接用于文件大小，不再用 `target.stat()`。

**为什么只在 plan 姿态**：build 的边界是 workspace，本来就允许软链；
plan 的边界是子目录，才是这条攻击的落点。改 build 是扩大范围。

#### L2 grep 读 `.env`

**目标**：不带审批的 grep **不读**凭据文件；显式指定单文件并**获批**后可以读。

**评审纠正了两处会导致假绿的错误，方案据此改写：**

1. **凭据词汇不能只覆盖 dotenv。** 实测今天：

   ```
   read .env        → warn      read .npmrc   → allow
   read id_rsa      → allow     read server.pem → allow
   grep .env        → warn      grep id_rsa   → allow
   ```

   `_CREDENTIAL_NAMES` / `_CREDENTIAL_SUFFIXES` 已覆盖 `.npmrc`、`id_rsa`、
   `*.pem` 等，但只用于 **bash 红线**，没有进 file-tool 规则。
   ⇒ L2 的范围是**整份凭据词汇**，不是 `.env` 家族。

2. **不能用 `target.is_file()` 推断"已获批准"。** 它是形状判断，不是授权凭据。
   一个 `grep(path="id_rsa")` 也会 `is_file()`，于是无需点击就通过。
   ⇒ 过滤的例外只能来自**分发器已经给出的批准事实**。

**实现**（三处，一处定义）：

- 新 `ai_coding/security/credentials.py`：把 `_CREDENTIAL_NAMES` /
  `_CREDENTIAL_SUFFIXES` / `_CREDENTIAL_PATTERNS` 从 `permission_gate.py`
  与 `bash_redlines.py` 收敛成一份，提供
  `is_credential_path(path: str | Path) -> bool` 与
  `credential_rules(actions) -> Ruleset`。前者同时匹配 basename 与路径形状
  （`.ssh/`、`.aws/`、`.docker/config.json` 等），所以调用方必须分别传
  词法路径和 `resolve()` 后的路径；只传 basename 不够。
  `permission_gate`、`bash_redlines`、`read_tool` 与 `grep_tool` 都 import
  它——**不是新名单**。
- `PermissionGate._base_rules`：对 `read` **与** `grep` 都追加
  `credential_rules(("read", "grep"))`，效果是 `ASK`；
  只有 `.env.example` 一类明确的文档文件保留 `ALLOW`。
- `grep_tool`：rg 走 `--glob=!**/{name}` 与后缀排除；Python fallback 在
  `_walk` 之后按**解析后的路径**过滤（见下）。

**软链**：`_walk`（`grep_tool.py:301`）返回的是符号链接**本身**，
按可见文件名过滤会漏掉 `config.txt -> .env`。实测今天可读：

```
grep(pattern="TOKEN", path=".") → .env:1: TOKEN=SECRET
                                  config.txt:1: TOKEN=SECRET
```

⇒ 过滤判定必须同时看**词法名**与 `Path.resolve()` 后的真实名，
rg 与 Python 两条路径都要覆盖。

**批准来源**：`ToolContext` **不是**分发器构造的。它由
`core/request_builder.py::tool_context` 在批次分发前构造一次，
`ToolDispatcher._handle` 只补 `call_id`（`dispatch.py:335`），批准发生在
之后的 `_decide`（`dispatch.py:454`）。因此必须把“本轮批准”追加到逐调用
的上下文继承链：

1. `ToolContext` 新增 `credential_approved: bool = False`，默认 fail-closed；
2. `_decide` 在 WARN 分支得到 `verdict_from_user is APPROVED` 后，
   **仅当批准来源是人类交互**（`approval.is_human is True`）**并且**这次
   调用是 `grep`/`read`、词法或 resolve 后的目标命中凭据路径时，把用于
   执行的 ctx 替换为
   `replace(ctx, credential_approved=True)`；其他批准不置位；
3. `_execute` 继续在传入 ctx 上补 `kill_event`，不改批准位；
4. `ReadTool.execute` 面对显式凭据路径且批准位为假时返回
   `credential_approval_required`，不读文件；
5. `GrepTool.execute` 对显式凭据单文件且批准位为假时返回同一错误；
   对目录搜索则在 rg/python 两条路径过滤凭据；只有批准位为真才跳过过滤。
6. **唯一的 grantability 入口**是
   `PermissionGate.grant_key(tool_name, params) -> str | None`：它调用模块级
   `grant_key(..., workspace=self._workspace)`，对 path 同时检查词法路径和
   `Path(workspace) / path` 的 resolve 结果。显式凭据路径（包括
   `config.txt -> .env`）返回 `None`，因此 TUI 不提供 Always、
   `PermissionGate.grant()` 即使收到 ALWAYS 也不落盘；下一次调用必须重新问。
   普通文件、普通工作区外路径与 `.env.example` 的 Always 不变。
   `handlers.py` 的 approval payload 从 dispatcher 的 gate 调实例方法取
   `grantable`，不能直接调用无上下文的模块函数。

批准位不跨调用、不跨会话、不持久化；它是“这次明确批准了这一个大纲内
的凭据读取”的事实，不是新的权限真相源。默认 False 时 rg 和 Python
fallback 都必须过滤。

**批准来源必须有类型契约**：`ApprovalCallback` 增加
`is_human: ClassVar[bool] = False`；`CLIApprovalCallback.is_human = True`，
`AutoApproveCallback.is_human = False`。子代理固定使用
`AutoApproveCallback`，因此自动 YES 永远不能产生 `credential_approved`。
这不是新的权限判定，只回答“谁说了 yes”，避免把无人值守的自动放行伪装成
人的授权。

#### L3 字符串内路径

**目标**：verify 命令里以字符串形式出现的越界路径，也要被看见。

`command_views` 当前只收集 `string` 的 `string_content` 子节点；
`raw_string`（单引号）的直接文本不会进入 `arguments`。这是解析器的现有
缺陷，L3 的用例不能绕过它：

- `shell_parse.command_views` 对 `raw_string` 读取引号内的直接文本；
- `acceptance._relative_targets_outside` 再对这一表示做一次**字符串片段**扫描：

```
for view in command_views(command):
    for arg in view.arguments:
        for token in _path_like_tokens(arg):   # 从自由文本里取 ../x、/abs/x
            resolve & contain-check
```

`_path_like_tokens` 的规则：含 `/` 或 `..`，且至少两段；跳过 URL scheme。
实现只读 `CommandView.arguments` 的**引号内容残片**，不把整个 shell
参数重新当成命令；先去掉单/双引号，再按空白和常见分隔符取片段。
它不是 Python 解释器，只识别**明显写在字符串里的字面路径**；动态拼接、
格式化、base64 或运行时构造的路径不在这一层能保证的范围内。M4 的承诺是
“关闭 M3 记录的字面路径绕过”，不是“任何程序都不可能越界”。

**评审纠正：不能复用 prose 扫描。** `_OUTSIDE_PATH_RE`（`plan_runner.py:147`）
**只认绝对路径**，`path_candidates`（`shell_parse.py:321`）也只要 `/` 与 `~`。
实测 `python -c "open('../x')"` 走 prose 扫描得到的仍是 `[]`。
所以相对片段必须**单独定义规则**，同一个 `Sandbox.resolve` 做最终判定：

```
token 含 "/" 或 ".."；以 letter 开头或 "../" 开头；不是 URL scheme；
且解析后不在任何 root 内 ⇒ 记为一个 offender
```

误报控制（评审要求的三条）：`grep 'a/b' f`、`pytest tests/unit`、
`https://x.dev/a/b` 都必须**不**被判为越界。另加单引号、转义、
`.format()` / `%` 构造和非 Python 解释器的用例。对于不能可靠识别的动态
构造，测试断言 detector 返回空并明确标为已知限制，不能写成“已关闭”。

### 3.5 M4c：T7 交互

**当前 agent 必须成为前端状态**。今天的唯一来源是 `stats().mode`（派生），
那是"是不是 plan"，不是"是谁"。

最小实现：

1. **`session.stats` 加 `agent` 字段**（后端已有 `session.agent`，零新逻辑）；
2. **新 RPC `session.agents`** 返回
   `tuple(spec for spec in world.loop.agents.visible() if spec.kind == "primary")`
   的 `{id,name,kind,source,description}`；`AppWorld` **没有** `agents` 字段，
   唯一现成引用是 `world.loop.agents`。`primary()` 会包含 hidden agent，
   不能直接拿来当选择器来源；picker、shift+tab 与 IPC 列表共用上述
   “可见 primary”集合。subagent 不是切换目标，继续由现有 `/agents` 文本
   入口展示，不把“查看委派目标”和“切换当前 agent”混在一起；
3. **新 RPC `session.agent.select`** —— **评审指出方案漏了它**。前端只有列表
   和当前值，没有"切换"这个动作；`handlers.py` 的 RPC 表里也没有。
   它必须是 `request_posture(session, agent=<id>, readonly=is_plan_agent(id))`
   的**薄适配器**，带 bridge observer，提交后持久化。返回
   `committed/queued/cancelled/noop` 四态（`PostureResult` 已有）；
   subagent id 与未知 id 各自返回一个明确错误。**不新写状态机。**
   具体流程：查 `world.loop.agents.get(id)`；缺失返回 `unknown_agent`，
   `kind != "primary"` 返回 `not_primary`；否则调用
   `world.loop.request_posture(...)`，若结果不是 queued，
   `_persist_session(world, state.session)`；queued 不持久化临时状态，
   原有 `pending_posture` sidecar 负责崩溃恢复。
4. **`state/agents.ts`**：**只保存 primary 列表**。当前 agent 的唯一前端
   真相源是 `SessionState.agent`；`session.stats.agent` 是挂载/重连时的
   水合来源，`agent.switched` 是运行期更新来源。模块不得再存一份 current；
5. **`component/agent-picker.tsx`**：`/agents` 的 TUI 版本，复用 `dialog-select`
   （不新造列表组件）；
6. **shift+tab 改语义**：循环 **primary** agent（不再只是 plan ↔ off）；
7. **状态栏**：`<agent.name>` 为主，`PLAN·只读` 降为后缀；
8. **`agent.switched`** 同时更新当前 agent（今天只插 notice）。
   `SessionState` 增加 `agent?: string`；事件到达时同时写该字段并插 notice，
   不把当前 agent 从 assistant message 的 tag 推导出来（tag 是历史归属，
   不是当前姿态）。`state/agents.ts` 不保存 current。
9. **色标**：不扩建 agent schema。现有 `theme.agentColor` 是默认 agent
   色，`theme.feedbackWarning` 是 plan 色；新增纯函数
   `frontend/src/util/agent.ts::agentAccent(agentId)` 固定返回这两枚语义
   色（plan → warning，其余 → agentColor），消息标签、composer 与状态栏
   共用它。自定义 agent 的用户自定义颜色不在 M4 范围，避免把 M1b 的
   agent 文件格式无依据地扩字段。

**Home 的 draft 也要一起定**（评审指出）：`routes/home.tsx:62` 现在只有一个
boolean `mode` 信号，无法表达自定义 primary。改成
`agent: string | null`（null = 用默认 agent），Home 与 session 用同一条
选择路径。Home 的 `agent` 传为初始 selection，Session 在 `initialize/load`
后读 `stats.agent`；提交前的 Home 选择通过 `session.agent.select` 落盘，
不再只发 `/plan` prelude。若 `session.agent.select` 返回 queued，
Home 的提示按 queued 处理；不得把未提交的选择伪装成当前 agent。

Home 的首会话顺序固定为：

1. App 已有一条由 `initialize` 创建的 session（即使仍显示 Home）；
2. Home 挂载时并行请求 `session.stats` 与 `session.agents`，拿到当前
   agent 与 primary 列表；
3. shift+tab 只改 Home 的 `agent` draft，不发请求；
4. 首次提交把 `agent` 放进 `PendingPrompt`，App 切到 Session 路由；
5. Session 挂载后，在发送 prompt **之前**调用一次
   `session.agent.select {id: draftAgent}`；返回 `committed`/`noop` 才继续
   原有的 plan prelude 与 prompt，返回 `queued` 显示排队提示并停止本次
   自动 prompt（当前没有正在运行的回合时，正常实现不会出现 queued）；
6. 任何错误都不发送 prompt，并在 composer 上显示原因，避免“界面显示 A、
   实际请求由 B 执行”。

涉及 `routes/home.tsx`、`app.tsx`、`util/submission.ts`、
`routes/session.tsx`、`state/agents.ts`。不再把 Home 的 `mode` 当姿态
真相源；`mode` 只由选择后的 agent id 在渲染时派生。

**"评审卡自动打开"不是 M4 的缺口**：opencode/dsh 的自动打开语义在本仓已由
`user_prompt.ask` 的模态通道实现（评审卡出现即占据 composer 槽位）。
M4 不再重复实现，也不为它加"每会话一次"的额外状态。

**风险**：shift+tab 的旧语义有测试（`keymap-shift-tab.test.tsx`、`home-mode.test.tsx`）。
这是**有意变更**，需要迁移并写清理由。

## 8. 为什么拆成四片

M4 原计划是一批，但四块的性质完全不同：

- **M4a 改安全边界**，必须最严的门禁（全量 + 变异）；
