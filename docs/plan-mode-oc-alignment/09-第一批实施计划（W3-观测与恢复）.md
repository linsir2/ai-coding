## 0. 目标与最终模样

一句话：让「批准 → 执行 → 重启恢复」这条链路**对用户可见、对账本可信、对预算诚实**。

W3 落成后你会看到：

1. 计划执行期间，任务卡/侧栏**实时**随每步结算、fiat 回填、arm/disarm 刷新（不再只在批准那一刻更新一次）。
2. 重启 / 重开会话后，计划卡、每步收据、armed 状态**从会话文件重建**（不再"执行到一半的会话看不见计划"）。
3. 崩溃自动续跑**不再把会话留在 PLAN·只读**：boot 前复位为 normal，状态栏与提醒不复错位。
4. 规划回合的 `[budget]` 提示与它**真实的**迭代预算一致（/plan <topic> 30、执行步 8、普通回合按配置），不再被旧 policy 口径污染。
5. 坏 `armed_profile` 的历史数据**不再吞掉**较新合法会话的恢复机会；`/resume` 按真实最近使用排序。

## 3. R01 · assembler 读活 policy

### 3.1 现有设计（根因）
- `RequestAssembler.__init__` 存 `self._policy = policy`（`request_assembly.py:126`）；`:200`（`inject_task`）与 `:228-230`（`budget_pressure`）直接读快照。
- `AgentLoop` 构造 assembler 时传 `policy=self.policy`（`agent_loop.py:395-407`）；此后 `loop.policy` 会被整体替换（规划回合 30 轮、执行步 8 轮、还原），**assembler 手里的还是旧对象**——预算压力块与任务注入读旧口径（F-51）。

### 3.2 目标设计
```python
# request_assembly.py
def __init__(..., policy: Any, policy_provider: Callable[[], Any] | None = None, ...):
    self._policy = policy
    self._policy_provider = policy_provider
def _active_policy(self) -> Any:
    return self._policy_provider() if self._policy_provider is not None else self._policy
# :200 inject_task / :228 budget_pressure → self._active_policy()
```
```python
# agent_loop.py:395-407
RequestAssembler(..., policy=self.policy, policy_provider=lambda: self.policy, ...)
```

### 3.3 数据流影响
请求装配在**每个 iteration** 取当前 policy → `[budget]` 提示与实际上限一致；policy 还原后立即回到正常口径，无残留。

### 3.4 RIPR
- **Red**：`tests/test_request_assembly.py::test_budget_pressure_reads_the_provider_not_the_snapshot`（provider 换 `TurnPolicy(30 轮)` → 压力块按 30 轮口径）。
- **Implement**：上述两文件三处。
- **Prove**：`pytest tests/test_request_assembly.py tests/test_plan_budget.py tests/test_plan_runner.py -q`。
- **Regression**：全量 `pytest` + `ruff check ai_coding tests` + `mypy ai_coding`。

### 3.5 效果
规划/执行/普通三种回合的预算提示与各自真实上限一致；`policy` 还原后无旧口径残留。

## 4. R07 · boot 恢复语义

### 4.1 现有设计（三处缺口）
1. `SessionService.save`（`session_service.py:157-162`）不更新 `last_access_time`；只有 `create` 写（`:150-154`）→ `find_armed_session`（`world.py:66-91`）与 `/resume`（`session_service.py:224-226`）按**创建时间**排序。
2. `find_armed_session` 不筛 `armed_profile`；`initialize` boot 分支（`handlers.py:298-345`）对 `profile ∉ {plan,goal}` 静默放弃 → 坏 profile 的"最新"候选会**吞掉**较新合法会话的恢复机会。

2. `find_armed_session`：候选条件加 `raw["task"].get("armed_profile") in ("plan","goal")`。
3. boot 分支在 `_launch_boot_resume(session)` **之前**：
   `session.mode = "normal"; session.readonly = False; session.pending_posture = None` → `_persist_session(world, session)` → 再 launch。

### 4.3 数据流影响

## 5. R06 · 执行期 `TaskUpdated`

### 5.1 现有设计
- `TaskUpdated` 目前只在**工具改任务**后发射（`agent_loop.py:1515`）与命令层（`commands.py:216/:347`）；
- `PlanRunner` 自身的 `task.update(...)` 不发事件：`_settle`（`plan_runner.py:791-829`）、异常分支（`:712-717`）、`_backfill_fiat`（`:475-508`）→ 执行期卡停在批准那一刻的样子（F-47）。

### 5.2 目标设计
```python
# plan_runner.py（模块内助手）
@staticmethod
def _emit_task(observer: Any, task: Any) -> None:
    if observer is not None and hasattr(observer, "on_event"):
        observer.on_event(TaskUpdated(task=task))
```
发射点（状态**真的**变化处，一次变化一个事件；实现期修正两处，见下）：
- a. `run()`：arm 持久化之后；exit 处**无论哪层 disarm**（driver 正常路径或 finally 兜底）都补发一次最终态；
- b. `_settle`：completed / blocked 两个分支 `task.update` 之后（仅 verify 项会走到这里）；
- c. `_run_step` 异常分支 `task.update(blocked)` 之后。

**实现期修正（砍冗余，遵循最小化）**：
1. **不发“step start”**：runner 不改该状态；in_progress 由模型 `todo_write` 触发，已走 tool 路径发射。
2. **不发 `_backfill_fiat`**：核对源码后确认它是**纯观察**（`plan_runner.py:475-508`“nothing is re-run, verified, or mutated”）——它只补收据，不改任务状态；其状态变化早已由模型的 `todo_write` 发射，这里再发只是重复未变化的状态。原计划的“每个回填一次”与 `test_backfill_emits_per_receipt` 一并砍掉。

### 5.3 数据流影响
`plan.updated` 在执行期随状态变化流出；前端消费者（`session.ts`）零改动即刷新；事件顺序 = 状态变化顺序，可重放。

### 5.4 RIPR
- **Red**：`tests/test_plan_runner.py::test_runner_emits_task_updated_on_arm_and_disarm`、`::test_settle_emits_updated_when_a_step_completes`、`::test_backfill_emits_per_receipt`（用现有 observer 桩模式）。
- **Implement**：`plan_runner.py` 一处助手 + 五处调用点。
- **Prove**：`pytest tests/test_plan_runner.py tests/test_plan_m1.py -q`。
- **Regression**：全量；真机：3 步计划执行时看卡逐步刷新。

### 5.5 效果
执行期卡/侧栏实时；收据气泡与卡上状态一致。

## 6. R05 · 计划与收据回读

### 6.1 现有设计
- `session.load` 返回消息与 `mode/readonly` 等（`handlers.py:394-414`），**不返回 task / 收据**；
- 前端计划卡只在 live `plan.updated` 渲染；`stepDeliveries` 前端零消费（F-48）。

### 6.2 目标设计（后端）
`session.load` 响应增加一个**只读**键（空 task 读作 `None`，与存储规则一致）：
```python
task = getattr(session, "task", None)
task_payload = task.to_dict() if task is not None and task.items else None
"task": task_payload,   # 复用现有序列化；前端走同一 applyPlanUpdate 归约器
```
不新增 endpoint、不改存储格式。

**实现期修正（砍冗余）**：`stepDeliveries` **暂不上 wire**。核读前端后确认：每步的两条气泡（step head + summary）已由 `_record_on_parent` 持久化进消息、replay 天然呈现；结构化收据在 live 端也没有超出气泡的消费者。此时把 `stepDeliveries` 放上 wire 只会**重演 F-48 的“有契约无消费”缺陷**。待收据面板/卡片批注有真实消费者时（W1 的评审面或后续批次）再上，届时复用 `StepDelivery.to_dict()`。

### 6.3 目标设计（前端）
- `session.load` 消费者：把响应的 `task` 走与 `plan.updated` **同一个** store 写入路径（同一 reducer），收据块同样水合；
- `replay.ts`：重放时重建计划卡（含 armed 标记）与收据；完整计划 markdown 从历史消息里 `present_plan` 调用的 `arguments.plan` 取（tool args 权威，A07），不新增 IPC。

### 6.4 数据流影响
打开/重启会话：卡与收据立即可见，且与 live 形态同构——不需要第二套 UI 状态。

### 6.5 RIPR
- **Red**：`tests/test_server_ipc.py::test_session_load_returns_task_and_receipts`；前端 bun 用例 `load hydrates the plan card and receipts`（按 `frontend` 现有测试模式就近新增）。
- **Implement**：`handlers.py:394-414` + `session.ts` + `replay.ts`。
- **Prove**：`pytest tests/test_server_ipc.py tests/test_session_service.py -q`；`cd frontend && bun test`。
- **Regression**：全量 + 真机：批准 → 执行 1 步 → 关闭 → 重开 → 卡/收据可见。

### 6.6 效果
"执行到一半的会话，重开后仍看得见计划与每一步的收据"。

## 7. 数据流（改前 vs 改后）

```
[改前]
批准 → plan.updated（一次）→ PlanRunner: task.update（无事件）→ 收据落盘（前端不消费）
     → 重启: task/收据不在 load → 卡空白；boot: 姿态残留 PLAN

[改后]
批准 → plan.updated → PlanRunner: arm / settle / fiat / disarm 各发 TaskUpdated → 卡实时
     → 收据落盘 → 重开: session.load(task + stepDeliveries) → 前端水合重建卡/收据
     → boot: find_armed（profile 过滤）→ 姿态复位 normal → resume（budget 口径由活 policy 提供）
```
