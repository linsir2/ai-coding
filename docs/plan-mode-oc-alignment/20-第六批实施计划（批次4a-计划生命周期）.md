## 1. 为什么是这三项

`19` 号稿按「用户撞上的伤害」排了序，P1 是三项**同一主题**的缺陷：

| # | 缺陷 | 用户撞上时的体验 |

## 3. 现有设计 → 本批设计（逐条：复用什么 / 为什么）

### 3.1 撤 arm：10 处重复 ⇒ 一个方法

现状（`armed = False` + `armed_profile = ""` 两行）散在 **10 处**：

```
ai_coding/core/agent_loop.py:991-992, 1479-1480
ai_coding/core/plan_runner.py:333-334, 597
ai_coding/core/task_driver.py:133
ai_coding/core/goal_runner.py:168
ai_coding/app/commands.py:340
ai_coding/server/handlers.py:332, 734
```

⇒ **`TaskState.disarm()`**（`domain/task.py`）是「消除重复」而不是「造轮子」：一个方法消灭 10 份副本，且 10 处的语义本来就必须一致（撤 arm 却不清 profile ⇒ `world.py:90` 的 profile 白名单会捡起一个无主的 armed 任务）。

```python
# ai_coding/domain/task.py
def disarm(self) -> bool:
    """Give up the task: not armed, and owned by nobody.

    Ten places did this by hand, and they had to agree: an armed task
    with no profile is one the boot resume will not pick up
    (``server/world.py``), so a half-disarmed task is a task nobody
    finishes and nobody can see.  One method, so they cannot drift.
    """
    was_armed = bool(self.armed)
    self.armed = False
    self.armed_profile = ""
    return was_armed
```

**契约**：`disarm()` 清两个字段，返回「之前是不是 armed 的」。**幂等**（重复调用第二次返回 False）⇒ D1 的 `/plan off` 与 runner 的收尾撤 arm 不会互相打架。

### 3.2 D1：`/plan off` 该撤什么

**判据**：`task.armed and task.armed_profile == "plan"` ⇒ 撤；**`armed_profile == "goal"` 不动**（goal 是另一条线，`/goal off` 才是它的退路）。

**为什么不动执行中的**：`/plan off` 是命令，而命令在回合忙时会被排队（`session.tsx:366-369`）⇒ 它落地时 runner 早已收尾并撤过 arm ⇒ 无需额外分支。**boot 续跑的情况**（`world.py:66-98` 捡 armed plan）⇒ 用户在重启后 `/plan off` ⇒ 撤 arm ⇒ **下次重启不再捡它** ⇒ 这正是「放弃」该有的效果 ✓。

**可见说明**：`/plan off` 已经有「还有 N 项未执行（重新进入 Plan 模式可以继续）」这句（`commands.py:466`）—— **它说的是「可以继续」，与「已批准的计划还在」冲突** ⇒ 本批把这句话改成对应实际状态的两句：
- 撤了 arm ⇒ 「已放弃这份批准的计划（可以重新规划）」
- 没撤 ⇒ 保留「还有 N 项未执行」

**事件**：撤 arm 后发 `TaskUpdated` ⇒ 前端计划卡刷新（`session.ts:564` 的 `applyPlanUpdate`）⇒ 否则前端会一直显示一份已被放弃的计划。

### 3.3 D2：批准被撤回要留痕

现状：`agent_loop.py:1479-1480` 在回合**未干净收尾**时撤 arm（`f94a308` 的设计，R11 的要求）⇒ 但**不出声**。

⇒ **在该处给 outcome 加一条 note**：`「已批准的计划在本回合未干净收尾，批准被撤回；重新规划后再次提交。」`

**与守卫的 note 不冲突**：守卫的 note 是「计划没交」（没提交的场景），D2 的 note 是「提交了但被撤回」（提交了的场景）⇒ 互斥 ⇒ 不需要拼接逻辑。

**为什么这条 note 重要**：它是「人批过的东西被系统收回了」的**唯一**痕迹。R11 的设计（`f94a308`）是为了不让「批准了但回合崩了」的计划被静默执行 —— 那是对的，但**必须让操作者知道**。

### 3.4 E4：CLI 也要读 note

**通道已经存在**：`TurnOutcome.note`（`domain/loop.py`）→ `agent_loop.py` 写入 → `server/bridge.py:189` 上线给前端。
**CLI 侧**：`loop.last_outcome`（`agent_loop.py:2372` 的属性；`commands.py:568` 已在用同一个通道读 `MAX_ITERATIONS`）⇒ **复用它，不新增通道**。

**落点**：`app/commands.py` 的**两处会跑回合的地方**：
- 纯文本分支（`commands.py:109`）—— 普通回合的 note
- `/plan <topic>` 分支（`commands.py:558` 之后）—— 规划回合的 note（「计划没交」「预算耗尽」）

**为什么不是 `handle_input` 末尾统一打印**：命令路径（`/plan off`、`/permissions`）不跑回合，`last_outcome` 是**上一回合的**⇒ 打印它会是**陈旧信息** ⇒ 必须按「刚跑过回合」逐处打印。

**输出通道**：`console.info(...)`（CLI 的既有通道，`commands.py:466` 等已在用）⇒ 与 TUI 的 muted notice 视觉上对齐（TUI 走 `state/session.ts:726` 的 `appendNotice`）。

## 4. 数据流的影响

```
【D1】/plan off
   → commands._handle_plan(off)
        ├─ request_posture(normal, readonly=False)      （不变）
        ├─ task.armed and armed_profile=="plan"?
        │    ├─ 是 → task.disarm() → TaskUpdated → console.info("已放弃…")
        │    └─ 否 → 不动
        └─ 落盘
   ⇒ 后果：boot 续跑不再捡它（world.py:90 的 profile 白名单）
   ⇒ 后果：plan_only 与 present_plan 的「已批准」拒绝随之解除 ⇒ 死路解除

【D2】回合未干净收尾
   → agent_loop._close_turn
        └─ 撤 arm（改调 disarm()）
        └─ outcome.note = "已批准的计划…批准被撤回…"
   ⇒ 前端：已有 note 通道（bridge.py:189 → session.ts:726 的 muted notice）
   ⇒ CLI：本批的 E4 让它也看得见

【E4】CLI
   → commands.handle_input → 跑回合 → loop.last_outcome.note
        └─ console.info(note)
   ⇒ 守卫在每条结束路径上的提示（A4 做的）在 CLI 里终于可见
```

**不变的部分**：机械验收与收据的执行语义、`armed` 的判定逻辑（`world.py:90`）、评审三态、只读闸、step 会话。

## 8. 自核

| 检查项 | 结论 |
|---|---|
| **有没有造轮子？** | 没有。`disarm()` 是**消除 10 处重复**，不是新增机制；note 通道、`last_outcome`、`console.info`、`TaskUpdated` 全部复用。 |
| **有没有说不清作用的契约？** | `disarm()` 的作用是「撤 arm 且不留无主任务」（`world.py:90` 的 profile 白名单依赖它）—— 说得清。 |
| **行为破坏性变更？** | 提交 1 零变更（行为等价的重构）；提交 2 让 `/plan off` 真的能放弃计划（**这是修死路**）；提交 3/4 只加可见输出。**没有一条削弱「人批准才执行」** —— 恰恰相反：撤回现在是**有痕迹**的。 |
| **安全边界是否后退？** | 没有。`/plan off` 撤的是**用户的**计划，且只撤 plan profile（goal 不动）。boot 续跑的白名单逻辑未改。 |
| **会不会与已有的「未干净收尾就撤 arm」打架？** | 不会：`disarm()` 幂等；D1 与 D2 都在同一处撤 arm，但 D1 是用户主动、D2 是回合崩溃，note 只在 D2 加。 |
| **与 08 §8.3 的保留契约冲突吗？** | 不冲突。保留的是「批准 → arm → 执行 → 验收 → 收据」链路；本批改的是**撤销**路径的可见性。 |
| **影响相似度吗？** | 不直接计分（没有一维是「计划可撤销」）。但它治的是**用户在计划模式里卡死**的路径。 |

## 10. 最终模样推演

**场景 A · 用户改主意了**

```
$ /plan 调研这个分支
  …（规划回合，模型交了一份计划，评审卡弹出）
$ 1                      ← 批准
  [plan] 计划已批准：执行由系统接管…
$ /plan off
  [plan] 已退出计划模式（只读已关闭）。已放弃这份批准的计划，可以重新规划。
  （前端：计划卡消失；task.armed=False ⇒ 重启也不会再自动跑它）
$ /plan 再调研一次，这次只要提交历史
  …（新的规划回合正常开始）        ← 死路解除
```

**场景 B · 计划没交，CLI 上看得见**

```
$ 帮我改个 bug
  …（模型探索后被守卫追讨）
$ /plan 帮我改个 bug
  [plan] 已进入计划模式（只读）。继续对话写计划；…
  [plan] 本回合未提交计划（未调用 present_plan）；可继续对话让它提交。   ← E4 之前这句是哑的
```

**场景 C · 批准了但回合崩了**

```
  [plan] 计划已批准：执行由系统接管…
  （回合被打断）
  [plan] 已批准的计划在本回合未干净收尾，批准被撤回；重新规划后再次提交。  ← D2 之前没有任何下文
```
