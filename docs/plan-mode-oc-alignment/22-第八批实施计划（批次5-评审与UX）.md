## 1. 为什么是这四项

一句话：**评审流程在用户最需要输入的那一刻把输入框拿走了（D4），harness 的话被当成用户的话显示（D6），Home 提交后忙闲指示错序（D7），而唯一的 posture 入口对用户完全隐形（E1）。**

### 1.1 D4：卡片在场 = composer 整块卸载、会话键位全关

- `frontend/src/routes/session.tsx:657`：

  ```tsx
  <Show when={props.permission === null && props.ask === null} fallback={<></>}>
  ```

  卡片一出现，Prompt（含 textarea renderable 与草稿）**直接从树上消失**；card 结束后重新挂载 ⇒ 草稿丢、布局跳。
- `session.tsx:271` 的会话 bindings `enabled` 同样把卡片状态当关闸 ⇒ shift+tab / ctrl+t / leader+i 全失效。
- 为什么不能「让输入框继续可打字」——键位层先手，这是实测结论：
  - `@opentui/keymap` 的绑定默认 `preventDefault = true`（`node_modules/@opentui/keymap/src/index.js:2174`）；
  - keymap 用 `prependListener` 挂在 keypress 上（`index.js:2080`），并 `stopPropagation`；
  - 层序 = priority 降序，同 priority **后注册者先**（`compareLayers`：`right.priority - left.priority || right.order - left.order`，`index.js:3628`）；`useBindings` 每次依赖变化都重建层（`solid/index.js:66-97`）⇒ 靠注册顺序分胜负不可靠，必须用 `priority`。
  - 于是卡片期间打字：`1`/`2` 选计划选项、`j`/`k` 移动、`return` 确认、`esc` 驳回、`y`/`n`/`s`/`a` 答权限。**这是误批准，不是体验问题。**

### 1.2 D6：步骤 marker 被画成用户发言（live 与 reload 各错一半）

- 后端 `ai_coding/core/plan_runner.py:1069`：`ChatMessage(role="user", content=prompt, ...)`，**没有 `synthetic=True`** ⇒ 它是「用户说的话」。
- live：`frontend/src/state/session.ts:550-563` 的 `plan.receipt` 把 `prompt` 硬编码成 `role:"user"` 气泡。
- reload：`frontend/src/state/replay.ts:92-134` 靠**内容前缀**判断（`PLAN_MARK`/`NOTICE_MARK`/`STEERING_MARK`），不是 synthetic；`src/` 里 grep 不到任何 synthetic 读取。
- 后果：①用户看到 `只做这一步，不要做别的：…` 冒充自己说过的计划；②`request_assembly`/undo/压缩把 harness 记账当人话；③同类缺陷：`decision.inject`、`_CLOSING_PROMPT`、`_STREAM_CONTINUE` 这些 synthetic nudge 在 reload 时也画成用户气泡（live 不显示）。

### 1.3 D7：prelude 的终局事件抢掉后续提交的 busy

- `ai_coding/server/handlers.py:873`：`session_command` `spawn(run_command())` 后**立即 ack**；终局 `turn.finished` 由 `_notify_terminal_turn`（`:478-518`）在 `bridge.command_run = False` 之后才发（`bridge.py:335` 只在 command_run 期间把内层 `TurnFinished` 改名 `turn.step`）。
- `frontend/src/routes/session.tsx:568-585`：`planPrelude` 在 **ack** 上 `.finally(() => submit(...))` ⇒ 提交先置 `busy:true`，随后命令的 `turn.finished` 又置 `busy:false`（`state/session.ts:736`）⇒ 用户 prompt 回合在跑、输入框显示空闲。
- 这个窗口里二次提交会走 `submit()` 的 `state.busy` 分支 ⇒ `session.steer`（静默并入，不是新回合）。
- **关键时序证据（决定修法）**：命令任务在 ack 之前就已经在跑，而 `session.prompt` 还要一次完整往返 ⇒ 命令的终局事件**通常先于** prompt 的 ack 到达。所以「在 prompt ack 上记 turnId、终局按最新 id 判断」是不够的——终局到达时前端还不知道新回合的 id。唯一顺序无关的规则是：**终局只清「本端已登记的那个回合」的 busy；id 不匹配或本端从未登记 ⇒ 不是当前回合的终局，整条忽略。**

### 1.4 E1：shift+tab 存在但不可发现

- `frontend/src/routes/home.tsx:99` 已绑 `shift+tab → home.mode.cycle`；`composer-meta.tsx` 在 plan 下显示 `PLAN` 小字。
- 但全仓没有任何提示文本（`shift+tab` 只出现在注释与绑定里），15 号稿记录「按完只看到状态栏变成 `PLAN · dashscope · qwen3.7-flash`」。
- `ToastProvider` 只包 Session 路由（`frontend/src/app.tsx:534`），Home 是 `<Show when={route()==="session"}>` 的 fallback（`:517-530`）⇒ Home 内 `useToast()` 会抛。
- oc 的先例：`packages/tui/src/feature-plugins/prompt/footer.tsx:97` 常驻 `shortcut("agent.cycle") + muted "agents"` 提示——键位本身是提示的一部分。

## 3. 现有设计 → 本批设计（逐条：复用什么 / 为什么）

### 3.1 D4：卡片期间「收起而非卸载」

**复用**：`Renderable.focusable`（opentui 现成 setter）、`useBindings` 的 `enabled`、以及绑定层的 `priority` 字段。

1. `Prompt` 新增 `disabled?: boolean`：`disabled` 时 `input.focusable = false` 并失焦；**文本内容不碰**（草稿就地保留），视觉上仍是一行灰显占位。
2. 路由把 `<Show … fallback={<></>}>` 换成常驻 `<Prompt disabled={cardOpen()}>`。
3. 主会话层闸门**不动**；新增一条 `priority: -1` 的层，`enabled: cardOpen()`，命令表只有 `session.mode.cycle`，绑定只有 `shift+tab`（`run` 抽成共享的 `cycleMode()`）。卡片层 priority 0 ⇒ 卡片键位永远先手；shift+tab 卡片不管 ⇒ 继续可用。
4. 排队输入面板保持现状（它不在 Prompt 内）。

**为什么不是「放行整层」**：卡片期间放行整层会让 `escape` 等重叠语义重新排序（`session.interrupt` 与卡片的 dismiss 同键），收益（ctrl+t / leader+i）远小于误触风险。

**为什么不是「可输入 + 提交进队列」**：见 §1.1，打字会被卡片截走，`1`/`return` 会误批准。这是假实现。

### 3.2 D6：步骤回执只留 assistant 摘要

**复用**：`ChatMessage.synthetic` 的既有契约（`domain/message.py:181-190`，落盘只在 True 时出现，见 `domain/session.py:71-110`）；replay 既有的「跳过/改写」分支形状。

1. `_record_on_parent`：marker 消息 `synthetic=True`（根因）。summary 保持普通 assistant。
2. `PlanStepReceipt` 删 `prompt`；bridge payload 只发 `summary`。**理由**：marker 是记账，不是显示材料；前端不再消费 prompt，留着就是死字段（用户规则：说不清作用的契约砍掉）。
3. live：`plan.receipt` 只追加一条 assistant text。
4. reload：`WireMessage` 加 `synthetic?: boolean`；`messagesToState` 里 synthetic 且非 `[steering]` 的用户消息**不画**（记账不显示）；`[steering]` 仍剥前缀显示为普通用户发言（那是用户自己说的话）。
5. 顺带修好同类：`[notice]` 之外的 synthetic nudge（`decision.inject`、`_CLOSING_PROMPT`、`_STREAM_CONTINUE`）重量时不再冒充用户。

**为什么不是「marker 画成 muted notice」**：那会把 `只做这一步，不要做别的：` 这种 harness 话术直接怼给用户，且 live/reload 都要为一段不服务用户的话保留渲染路径。

### 3.3 D7：终局事件带 turnId

**复用**：`_launch_turn` 已维护的 `state.turn_id`、ack 已经带的 `turnId`、bridge 已有的 `command_run` 状态位（同层加一个 `turn_id`）。

后端：

1. `bridge.py`：`self.turn_id: int | None = None`；`on_event` 在 `turn.finished`（未改名为 `turn.step` 的那些）上戳 `data.turnId`。
2. `handlers.py::_launch_turn`：`turn_id = state.turn_id` 在自增后立刻捕获（异常兜底事件也要用），`bridge.turn_id = turn_id`，异常事件的 payload 带 `turnId`。
3. `_notify_terminal_turn(…, turn_id)` + payload `turnId`；三个调用点各自传自己的 id（`session_command` 的 `:810`、`_launch_armed_run` 的 `_launch_turn` 返回值）。
4. `session_prompt` 的 ack 不变（早已带 `turnId`）。

前端：

5. `SessionState.turnId?: number`；新 action `{kind:"turn-started", turnId}`；`turn.finished` 规则：

   ```
   data.turnId 存在 且 != state.turnId  ⇒ 整条忽略（不是当前回合的终局）
   否则                                 ⇒ 落 content、busy=false、turnId=undefined
   ```

   没有 `turnId` 的旧事件照旧处理（兼容混合版本与既有测试夹具）。
6. 登记点：`dispatch()` 的 ack（含命令与 prompt、自动派发）、`session.resume` 的 ack。**prelude 的 ack 不登记**（静默 posture 命令，不拥有 busy）。`session.steer` 的 ack 没有 turnId ⇒ 不登记（busy 仍归正在跑的回合）。
7. 队列排空加 `|| state.busy` 守卫：陈旧终局不再清零 busy，但路由的排空逻辑仍会跑，必须自己看 busy。

**不变量**：`initialPrompt` 只在 Home 提交、随新建会话挂载时出现 ⇒ 挂载瞬间 `turnId` 未登记，任何终局都属于更早的回合，必被忽略；等本题的 prompt ack 登记后，才可能清 busy。

**已知例外（可接受）**：服务端自发的 boot resume 没有 ack ⇒ 本端没有登记 id ⇒ 它的终局被忽略。该事件的 payload 不含 `note`/`handoff`（`_notify_terminal_turn` 不产生这两个字段），`reload`/`compacted`/`undo` 在路由层照旧消费 ⇒ 没有内容损失。

### 3.4 E1：Home 常驻键位提示

**复用**：oc `prompt/footer.tsx:97` 的「键 + muted 标签」形状；Home 已有的 `mode` signal。

- composer 下方一行：normal `shift+tab 计划模式`；plan `shift+tab 退出计划`（同一位置，两态同一行，避免文案漂移）。
- 不移 `ToastProvider`（全局结构调整只为一条瞬时提示，不划算）。

## 4. 数据流的影响

### D7（提交时序）

```
Home 提交(plan)
  └─ Session mount ─┬─ prelude = null ─────────────────────► submit(text)
                    └─ prelude = /plan
                         ├─ ack {turnId: N}                 ← 不登记（静默命令）
                         ├─ console.line("已进入计划模式")
                         └─ turn.finished {turnId: N}       ← 本端 turnId=∅ ⇒ 忽略
                         （客户端提交）submit(text) ⇒ submitted(busy=true)
                         ├─ ack {turnId: N+1}               ⇒ turn-started(N+1)
                         └─ turn.finished {turnId: N+1}     ⇒ 匹配 ⇒ busy=false
```

### D6（同一份事实，两条读法）

```
_record_on_parent ─┬─ user(marker, synthetic=True)   ← 记账（/resume 的 marker）
                   ├─ assistant(summary)
                   └─ PlanStepReceipt(summary) ─► bridge ─► plan.receipt
live  : reducer → assistant(summary)
reload: replay  → 跳过 synthetic(非 steering) → assistant(summary)
```

### D4（按键归属）

```
keypress ─► keymap(卡片层, priority 0) 命中 ⇒ 卡片动作，止
          └ 未命中 ─► keymap(posture 层, priority -1) 只有 shift+tab ⇒ cycleMode
                     └ 仍未命中 ─► app 层
```

### E1

```
Home: mode signal ─► ComposerMeta("PLAN")（已有）
                  └► 提示行（新增）：shift+tab 计划模式 / shift+tab 退出计划
```

## 8. 自核

- **契约消费**：`PlanStepReceipt.prompt` 删除后，`grep` 必须为零引用；`WireMessage.synthetic` 必须被 replay 真实读取；`state.turnId` 必须被 `turn.finished` 真实读取（不是只为测试存在）。
- **无假实现**：D4 不假装「可输入但不可见」；D7 不靠概率顺序，规则必须对两种到达顺序都成立（测试里显式覆盖「陈旧终局先到」）。
- **无新配置项、无新命令**。
- **不修改既有测试**（唯一例外：D6 删字段导致 `tests/test_server_bridge.py:481` 的精确 dict 期望必须同步，这条在拍板记录里明示）。

## 9. 非目标

- 不做 composer 的富文本/多行草稿保留（D4 只保文本，text parts 之外的输入态不在本批）。
- 不做卡片的键位自定义；不把 posture 层扩成别的快捷键。
- 不改 replay 的内容前缀匹配（`PLAN_MARK` 等保留给旧会话数据）。
- 不清理历史会话里已落盘的合成消息。

## 10. 最终模样推演

- **D4**：评审卡出现 ⇒ 输入框还在（灰显），刚打的一半需求不丢；shift+tab 能把计划关掉再打开；按 `1` 仍然是「开始执行」，按 `esc` 仍然是驳回。
- **D6**：执行一步后，transcript 只出现 `步骤 1 完成：…` 一条 assistant 摘要；刷新后一模一样；模型请求里不再出现 `只做这一步，不要做别的：`。
- **D7**：Home + shift+tab + 提交 ⇒ 占位符从 `Working…` 一直持续到真回合结束，中途不闪回 `Ask anything…`；此时再提交会走 steer/queue 的既有语义，而不是假装空闲。
- **E1**：Home 首屏就能看到 `shift+tab 计划模式`；按下去同一行变成 `shift+tab 退出计划`。

真机（tmux + 真模型 qwen3.7-flash，recording_proxy）走四场景：Home→plan→提交看 busy；卡片期草稿与键位；一步执行后的 transcript 与重载；Home 提示行两态。
