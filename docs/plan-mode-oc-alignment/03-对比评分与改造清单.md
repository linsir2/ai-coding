## 0. 方法与口径

### 0.1 评分规则（复述并执行）

- 维度集：25 个可对比的功能/数据流维度（§1 矩阵）。
- 每维打分：**1** = 与 OC 等价（同机制或同可观察行为；我方"包含 OC 行为且不冲突"也算 1）；**0.5** = 部分对齐（同意图、机制不同或只实现一半）；**0** = OC 行为缺失，或与之冲突。
- 相似度 = Σ 分 / 维度数。报出**当前相似度**与**应用改造清单后的预测相似度**（§3），后者须 ≥65%。
- 我方独有、OC 没有的机制（审批门、PlanRunner、verify/acceptance、收据/回执、boot resume）**不计负分**，归入 §7 保留机制；但凡因其改变了对用户可观察行为的维度（D13 计划产物形态、D14 审批/交接），仍按真实差异给 0.5 并解释。
- 预测分口径：改造清单（§5）完整落地后的稳定态；涉决策的维度（T6 只读语义）给出场景 A/B 两套总账（§3）。

## 2. 当前相似度总评

- **Σ = 10.0 / 25 = 40.0%**（14×0.5 + 3×1 + 8×0）。
- 与 65% 的关系：**差 25 个百分点**。
- 最拉低分的 3 个维度（均 0 分）：
  1. **D09 shell 可用性**——硬只读墙与 OC 软只读直接冲突（亲验 §0.2#1）；
  2. **D10 subagent 可用性**——同上根因（D11 网络访达同根因）；
  3. **D16 研究型请求出口**——我方无出口且守卫负 note（D15 同根因）。
- 结构归纳：8 个 0 分中 5 个来自两根因（硬只读墙、强制提交/无研究出口）；其余 3 个（D21 自定义 agent、D23 计划文件、D25 敏感读边界）是小的形态缺口。

## 3. 改造后预测相似度

预测分 = 改造清单（§5）完整落地后的稳定态。涉用户决策的 T6 给两套账：

| 场景 | 假设 | Σ | 相似度 | 达标 |
|---|---|---|---|---|
| **A（推荐）** | T6 软对齐：shell/subagent/网络规则 allow（prompt 劝阻） | 23.0/25 | **92.0%** | ✅ ≥65% |
| **B** | T6 保留硬墙：`shell/subagent/web * deny` | 20.0/25 | **80.0%** | ✅ ≥65% |

- 场景 A 的 4 个 0.5：D13/D14（保留执行层的可观察差异）、D21（轻量 agent 深度）、D25（保留沙箱）。

- 灵敏度：若再砍 T4（研究出口），A→21/25=84%，B→18/25=72%，仍达标；若只做 T1/T2/T3 形式三件套（不做 T4/T6/T7/T8/T9），约 68–70%，贴着线。结论：**65% 门槛的关键是 T1/T2/T3，上限提升的关键是 T4/T6**。

### 6b. 叙事（并两分支）

用户 shift+tab 把 agent 切到 Plan（S-01）：空闲时立即落地（S-02），会话文件写入 `agent:"plan"`，转录出现 "Switched agent: plan"，模型收到 enter reminder（T3）。接着用户发一条消息，走两条分支之一：

- **研究分支（S-04，新增出口）**：模型按 reminder 做只读探索——软对齐下可用 shell/webfetch/subagent（T6-A），用 read/grep/glob 读码——然后直接用对话回答。停步时守卫检查 `plan_touched`：没有碰过计划载体 → 干净收尾，无 NUDGE 无负 note。这正是 OC 的"讨论式规划"体验。
- **计划分支（S-05→S-07）**：模型调研完调 `present_plan`，评审卡弹出（保留 UI）；用户 keep 则带反馈继续规划（循环）；approve 则**列表被整表替换 + armed**（保留语义），回合收尾后前端静默 `/plan run`（保留自动执行），PlanRunner 以 fresh 步会话逐步执行、verify 机械判定、收据回填（全部保留）。

途中任何写工作区文件的调用被规则拒绝，模型收到"只能写到 `<plan_dir>`"的结构化文案（T5）继续回合；run 结束或用户 `/plan off` 时 agent 回到 build，leave reminder 注入，工作区恢复可写。

```
用户消息 ─► agent=plan?
  否 ─► build 回合（不动）
  是 ─► plan 回合（工具面 = 规则快照）
           ├─ 研究型：只读探索 → 直接回答 → 守卫放行（无 note）      [新出口]
           ├─ 计划型：present_plan → 评审卡
           │       ├─ keep → 反馈继续 ─┐（循环）
           │       └─ approve → 替换列表+armed ─► 前端 /plan run
           │                              └─► PlanRunner 步执行/verify/收据 [保留]
           └─ 越权写 → deny → "只能写到 <plan_dir>"（模型继续）        [改]
```

### 7.2 明确非目标（不做与理由）

1. **不引入 Effect/TS 架构、不做事件溯源**——我们保持 JSON 白名单文件 + wire 事件近似（C-05）；相似度已达标，架构迁移收益不成比例。
2. **不照抄 `session_v2` schema / `agent-switched` durable 事件流**——用"会话字段 + 消息记录"近似（T1/T7），可观察行为等价即可。
3. **不做自定义 `.md` agent 加载与配置合并**——（§8-Q4 选 A 时）本期无用例，D21 停在 0.5。
4. **不移植 OC 的 MCP resource 专属工具与 codemode `execute`**——与 plan 对齐无关，工作量独立。
5. **不改执行步 fresh/ephemeral 会话设计**——C-11 契约；OC 无对应物，属于保留增强。
6. **不引入 `external_directory` ask**——保留沙箱硬边界（§8-Q6），只做规则可表达。
7. **不照抄 OC"子会话继承父 session 权限而非父 agent 权限"的怪癖**——该行为在 OC 内部是权宜（oc.md §7 注 3），我们按 agent 规则解析子代理权限更一致。
8. **不删任何 PlanRunner/审批/verify 机制**——用户边界已拍板。

## 8. 实施前仍需用户拍板的决策点

### Q1（核心）软/硬只读：shell/subagent/网络在 plan 下如何取舍

- **选项 A（推荐）**：软对齐——规则 allow + 提示词劝阻 + `plan_strict_readonly=false` 默认。相似度 92%。
  - 理由：OC 的 plan 生态位就是"只读探索+讨论"，shell 是探索主力（git log/find/ls 等）；研究出口（T4）需要探索能力支撑才完整。
  - 权衡：写风险回流（`git commit`/`rm` 等只能靠提示词劝阻，OC 同款）；需配套一次评测（规划质量、越权调用率）。
- **选项 B**：保留硬墙——`shell/subagent/web * deny`。相似度 80%（仍达标）。
  - 理由：结构性防写，安全姿态明确；与现有"墙"的直觉一致。
  - 权衡：3 个维度永久 0；规划探索能力受限（无 shell 的 read/grep/glob 足够做码内规划，但缺外部信息）。
- **选项 C**：混合（shell 逐次 ask / 只放行只读子命令白名单）——相似度介于 A/B（D09 只能 0.5，且白名单判据脆、易漏），不推荐，除非安全要求高且愿意维护命令解析。
- **推荐理由**：先落 A 的开关、跑评测，用数据定默认值；A/B 两账都过线，风险偏好决定即可。

### Q2 研究出口的判据怎么定

- **选项 A（推荐）**：运行时信号——`plan_touched`（本轮碰过 present_plan/todo_write 或列表非空）才催交。确定性、零新协议。
- **选项 B**：显式出口协议——present_plan 加 `kind: plan|research` 或新工具。语义最清晰，但新增模型负担与协议面。
- **选项 C**：废除守卫。最少代码，但失去"计划进行中忘交"的兜底（历史两次静默失败，`turn_policy.py:205-207` 注释）。
- **权衡**：A 下"用户要计划、模型纯文本答完"不再拦截（OC 同行为），自动执行的触发率可能下降；可先 A 上线，B 作为后续增强。

### Q3 todo_write 在 plan 下留还是藏

- **选项 A（推荐）**：藏——plan 快照排除 todo_write；列表唯一作者是 present_plan（执行层语义不变）。
- **选项 B**：可见但只读（仅 list）。
- **选项 C**：维持现状（可 add/update pending，批准时被替换）。
- **权衡**：A 对齐 OC 且消掉"预写列表被替换"的毛刺，代价是模型失去草稿工具（需评测长计划质量）；B 是 A 的回退位。

### Q4 agent 抽象引入到什么深度

- **选项 A（推荐）**：轻量内置表（build/plan + 规则 + 切换语义），不做自定义加载。
- **选项 B**：完整自定义生态（`.md`/配置扫描合并、`default_agent`），D21 可到 1，但 L 成本且本期无用例。
- **选项 C**：只加名字不加规则/存储（仅 UI 标签）——只拉动 D20 一小格，不建议（形式半拉子）。
- **权衡**：A 的 D21 停在 0.5；若未来要做多 agent 产品形态，B 另立项目更干净。

### Q5 计划文件目录放哪

- **选项 A（推荐）**：工作区 `.ai-coding/plan/`——沙箱内、随会话审计、无需 external 例外。
- **选项 B**：家目录 `~/.ai-coding/plan/`——与 OC 字面一致（`~/.opencode/plan`），但需 external_directory 例外，触碰沙箱边界。
- **选项 C**：不做计划文件（D23 保持 0；OC 的这个能力本身也只是提示词约定）。
- **权衡**：A 与 OC 路径不同属可忽略差异；B 的一致性收益被安全成本抵消。

### Q6 敏感读/外部路径边界

- **选项 A（推荐）**：保留沙箱硬禁 + 仅加 `.env` ask（T9），D25 到 0.5。
- **选项 B**：对齐 `external_directory` ask，D25 到 1，但打开工作区外读取审批链（攻击面/实现复杂度上升）。
- **选项 C**：完全不动，D25 保持 0。
- **权衡**：A 把"审批面"限制在文件敏感度（.env）而不打开路径维度；B 属安全边界变更，建议独立安全评审再立项。
