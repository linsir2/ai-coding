### 2.2 今天 plan agent 的规则

### 2.3 缺口一：`items[].verify` 没进 workspace gate（真缺陷）

`tools/present_plan_tool.py:227-236`（审批前）与 `core/plan_runner.py:732-749`（执行前）
都只检查了 `content`，没有检查 `verify`。

而 `verify` 会在 `acceptance.verify_items` 里由 shell 直接执行、**绕过 dispatch gate**
（`acceptance.py:86-140`）。`_needs_a_human`（`:41-79`）确实检查它，但：

1. 发生在**执行期**——人已经批了计划，破坏"批准内容 = 你看到的内容"；
2. 调 `outside_workspace_paths` 时**没传 `extra_roots`**（`:62-71`），
   `tools.extra_workspace_roots` 里声明的目录会被误报。

这是 `08` §0 C05 列的必须修复项。

### 2.4 缺口二：plan 目录例外会被 `/readonly` overlay 挡死（设计冲突）

`core/dispatch.py:345-351`：

```python
if verdict is PermissionDecision.DENY:
    return self._denied(call, reason), True, False
if ctx.readonly and item.tool.mutates_world:
    return self._readonly_denied(call), True, False
```

`/plan` 进入时设 `agent="plan", readonly=True`（`app/commands.py:617`），
`write/edit` 的 `mutates_world` 默认 `True`（`tools/base.py:163`）。

实测：加了 `edit .ai-coding/plan/* allow` 后 gate 返回 ALLOW，但 overlay 仍然拒绝。
**只加规则，plan 目录依然写不进去。** 解法见 §4.3。

### 2.4b 缺口二续：`write`/`edit` 连工具表都不在

`core/agent_loop.py:2673-2688` 的 `_surface_tools`：

```python
if readonly:
    tools = [tool for tool in tools if not tool.mutates_world]
```

plan 会话是 `readonly=True`（`commands.py:617`），而 `write`/`edit` 的
`mutates_world` 默认 `True`（`base.py:163`）。实测 plan 请求的工具面：

```
ALL:      bash, edit, finish_research, glob, grep, history_search, job_kill,
          job_list, job_output, read, start_goal, subAgent, subagent_list,
          todo_write, update_goal, webfetch, websearch, write
MUTATES:  bash, edit, job_kill, subAgent, webfetch, websearch, write
plan 面:  去掉所有 MUTATES ⇒ write/edit 不可见
```

所以 T5 要成立，**工具面**也必须从"按 `mutates_world` 剪"改成
"按规则剪 + overlay 只剪没有具体允许的"。否则规则层永远收不到 call。

同时 `PLAN_PROMPT`（`core/plan_runner.py:120`）里那句
"bash/write/edit are unavailable in plan mode" 会变成**假话**，必须一起改。

### 2.5 缺口三：`..` 可以绕过 scoped allow（越权）

规则比较的是**词法路径**（`permissions.py:243-254`，只剥 `./`、换 `\`）：

| 模型写的 path | 匹配 `.ai-coding/plan/*` | 真在 plan 目录 |
|---|---|---|
| `.ai-coding/plan/x.md` | 是 | 是 |
| `/abs/ws/.ai-coding/plan/x.md` | 否（安全方向） | 是 |
| `.ai-coding/plan/../../src/app.py` | **是（越权）** | 否 |

实测 `glob_match` 的 `*` 跨斜杠、`..` 是普通字符，所以一条 `allow` 规则把工作区任意文件都放开了。
修法：规则资源先做纯词法归一（§4.1）。归一后
`.ai-coding/plan/../../src/app.py → ../src/app.py`，不再匹配；`Sandbox.resolve` 仍是真正的边界。

### 2.6 T9 的落点与顺序（最容易做错的一处）

opencode 的默认规则（`packages/schema/src/agent.ts:44-52`）：

```ts
{ action:"*", resource:"*", effect:"allow" }
{ action:"read", resource:"*.env", effect:"ask" }
{ action:"read", resource:"*.env.*", effect:"ask" }
{ action:"read", resource:"*.env.example", effect:"allow" }
```

example 必须**在 ask 之后**（last-match-wins）。本仓 base 层是派生的
（`permission_gate.py:658-674`），`read` 在 `_allow_tools` 里，所以三条 `.env` 规则
必须追加在 base 层**最后**。

`test_m1a_gate.py:47-50` 断言了 `len(base) == len(_allow_tools)+len(_warn_tools)`，
加三条会导致它失败——这是**契约变更导致的机械迁移**（§8.2）。

实测 `.env` 匹配（本仓 glob）：

| 文件 | `*.env` | `*.env.*` | `*.env.example` |
|---|---|---|---|
| `.env` / `a/.env` | 是 | 否 | 否 |
| `.env.local` | 否 | 是 | 否 |
| `.env.example` | 否 | 是 | 是 → 最终 allow |

两条 pattern 就够。`08` §1.7 写的 `**/.env*` **是错的**（`**` 无特殊语义，
会漏掉根目录 `.env`）——本方案修正旧文档。

## 3. 目标设计

### 3.1 T5 计划目录

plan agent 的软档规则：

```python
edit * deny                       # 一切文件修改被拒
edit .ai-coding/plan/* allow      # 例外，必须排在 deny 之后
```

四条不变量：

1. `write`/`edit` **仍在工具表里**（最后一条匹配 `edit` 的规则是 allow，resource≠`*`）
   —— 拒绝发生在执行期，模型能读到原因（opencode D06 的形状）；
2. 目录外写入被拒，文案指向 `.ai-coding/plan/`；
3. 目录内写入成功，父目录按需创建（`write_tool.py:102` 已有）；
4. **plan 姿态下**，`/readonly` 的 `readonly=True` 不再否决规则已明确 allow 的调用；
   人手动开的 `/readonly` 仍然绝对（§5.3）。
5. `write`/`edit` **重新出现在 plan 请求的工具表里**（否则 1-4 都无从发生）。

不变量 4 不是"放宽只读"：规则层是更具体的那一层，agent 的 deny 仍是绝对的；
人手动开的 `/readonly on`（无规则意见时）完全按原样工作，文案断言不变。

### 3.2 T8 隐藏 todo

```python
_PLAN_SOFT_DENY = ("edit", "shell", "subagent", "webfetch", "websearch", "todo_write")
```

效果链：`todo_write * deny` → `hides()` 为真 → `_surface_tools` 剪掉 → 请求 schema 里没有它。

**一并修正**：`ai/prompt.py:158` 与 `core/plan_runner.py:111` 都写着
"do not track the planning with todo_write"。工具都看不见了还教它别用，是自相矛盾
（`08` C14 的错误形态）。两处一起删。

边界：build 不受影响；执行 step 的 session 是 build（`plan_runner.py:845-850`）不受影响；
**不做** `turn/start` 清空（N04）。

### 3.3 T9 `.env` ask

`PermissionGate._base_rules()` 尾部追加，顺序即语义：

```python
Rule("read", "*.env",         Effect.ASK)
Rule("read", "*.env.*",       Effect.ASK)
Rule("read", "*.env.example", Effect.ALLOW)
```

| 调用 | 结果 |
|---|---|
| `read .env` / `read config/.env` | WARN |
| `read .env.local` | WARN |
| `read .env.example` | ALLOW |
| `read src/app.py` | ALLOW（不变） |

两个边界：**不碰 bash**（读 `.env` 已是硬拒，`permission_gate.py:118-127`，比 ask 更严）；
**不改 sandbox**（工作区外仍硬禁，Q6 保留）。

"Always" 的粒度是 `read:.`（按目录，`grant_key:369-377`），与 opencode 的 `save:["*"]` 一样粗，
属于既有契约，M3 不改。

### 3.4 T11 三态评审回读

保留（已验证正确）：approve 严格同意 + arm + 结束回合；keep 工具错误带 feedback；
dismiss 成功且结束回合；300s 超时。

新增最小两件：

1. **tool part 保留 `present_plan` 的 params**：live 从 `tool.started` 的 `params`、

## 4. 数据流

### 4.1 T5 写入计划目录

```
model: write({path: ".ai-coding/plan/design.md", ...})
  dispatcher._check
    subjects_of → (".ai-coding/plan/design.md",)      ← normpath
    evaluate → edit .ai-coding/plan/* ALLOW
    → Decision(ALLOW, specific=True)
  _decide
    verdict == ALLOW
    ctx.readonly && mutates_world && not specific_allow?  → 否，继续
    precheck → Sandbox.resolve 成功（工作区内）
    WriteTool.execute → mkdir(parents=True) + write_text
```

### 4.2 T5 越权写入

```
model: write({path: "src/app.py", ...})
  evaluate → edit * DENY（最后一条匹配）
  _decide → _denied(..., plan-aware reason)
  → "只能修改计划目录内的文件：<abs>/.../.ai-coding/plan/"
```

### 4.3 T5 `..` 逃逸（修复后）

```
model: write({path: ".ai-coding/plan/../../src/app.py", ...})
  subjects_of → posixpath.normpath(...) → "../src/app.py"
  evaluate → .ai-coding/plan/* 不匹配 ⇒ edit * DENY
    → 拒绝
```

### 4.4 T9 读 `.env`

```
model: read({path: ".env"})
  _check → base 的 read *.env ASK
  → Decision(WARN)
  approval.approve("read", {...})
    yes → allow_once → 执行
    always → grant("read:.") → 执行
    no → not_approved
```

### 4.5 T8 plan 工具面

```
session.agent == "plan"
  _agent_rules → todo_write * deny
  _surface_tools → gate.hides("todo_write", ...) == True
  → schema 列表里没有 todo_write
```

### 4.6 T11 回读

```
live:   tool.started { callId, toolName:"present_plan", params:{plan,items} }
          → session.ts 的 tool part 保存 params
replay: session.load → messages[].toolCalls[].arguments
          → replay.ts 已解析 params → tool part 保存 params
展开     → ToolCard 渲染 markdown(plan) + 条目表(verify/depends_on)
```

真实闭环：`arguments` 是模型真实提交的原文，由 `agent_loop` 原样落盘（`assistant_message`）；
live 与 replay 走的是**同一条数据**（params），所以两条路径不可能漂移。

## 5. 逐文件改动（TDD 顺序）

### 5.1 规则资源归一化（修越权）

**`ai_coding/security/permissions.py`**

```python
import posixpath

def _lexical(path: str) -> str:
    text = str(path or "").replace("\\", "/")
    while text.startswith("./"):
        text = text[2:]
    # 清掉 a/b/../c 这种绕法。纯词法，不碰文件系统；
    # 绝对路径保持绝对（真正的边界仍由 Sandbox 判定）。
    normalized = posixpath.normpath(text) if text else text
    return "" if normalized == "." else normalized
```

为什么 `""` 而不是 `"."`：`subjects_of` 的 `_named("")` 退化成 `"*"`，
保持"叫不出名字就当通配"的既有保守语义。

回归风险：既有 `subjects_of` 测试（`test_m1a_permissions.py:171-227`）无 `..` 输入，
`./src/app.py → src/app.py` 行为不变，**零迁移**。

### 5.2 计划目录规则 + 文案分派

**`ai_coding/agents/registry.py`**：加 `PLAN_DIR = ".ai-coding/plan"`，
在 `plan_rows` 里追加 `{"action":"edit","resource":f"{PLAN_DIR}/*","effect":"allow"}`
（在 `edit * deny` 之后）。

**`ai_coding/paths.py`：不加 `plan_dir`。** 自审后砍掉：它唯一的用途是拒绝文案，
而 dispatch 已经持有 `ctx.workspace`，`workspace + "/.ai-coding/plan"` 是两行字符串
拼接。加一个 `Paths` 属性会引入第二个"计划目录在哪"的定义，却没有第二个读者。
规则资源仍用相对 pattern（保证规则文件可跨机器复用）。

**`ai_coding/core/plan_reminders.py`**：`PLAN_ENTER_REMINDER` 增补一句
（照 opencode `plan.ts:11-22`）：

```
Do not create or update plan files unless the user explicitly asks you to;
when they do, write them only under .ai-coding/plan/.
```

**为什么必须有这句**：T5 把 `write` 放回了工具表。没有这句，模型很可能
"写个 plan.md 交差"，而不是调用 `present_plan`——`08` T5 的风险栏
"误诱导写文件交差"说的就是这个。opencode 的 enter 提醒里正是这句话。

同时把 plan agent 的 `description` 从 "Read-only planning agent."
改成 "Planning agent; writes only the plan directory."——
`/agents` 显示的就是这句，它不能和规则说反话。

**`ai_coding/agents/registry.py`**：`AgentSpec(id="plan", description=...)` 同步改。

**`ai_coding/core/dispatch.py`**：deny 分支的文案按 action 分派。
加一个**纯函数**：

```python
def _plan_denial_reason(tool_name: str, reason: str, ctx: ToolContext) -> str:
    """In plan mode a file tool says where it CAN write; others keep their rule text."""
```

只有 `posture == "plan"` 且工具是 write/edit 时改写为指向 plan 目录；
其余（shell/subagent/web）保留规则自己的 reason（它已经说了是哪条规则）。

`ToolResult.error` 保持 `"denied"` 不变——前端已有它的中文标签；改 error code 会牵连
`toolmeta.ts` 与若干测试，无收益。

### 5.3 修 overlay 否决规则 allow（关键）

#### 5.3.1 工具面（`core/agent_loop.py::_surface_tools`）

今天：

```python
if readonly:

```

改成：**plan 姿态下，overlay 只剪"没有被规则具体允许"的 mutating 工具；
其他姿态原样**。

```python
if readonly:
    plan = mode == "plan"
    tools = [
        tool for tool in tools
        if not tool.mutates_world
        or (plan and self.gate.partially_allowed(
            tool.name, session_rules=session_rules,
            agent_rules=agent_rules, posture=posture,
        ))
    ]
```

新增的 `PermissionGate.partially_allowed` 是一个**静态**问题
（没有 params）：这个 action 在规则链里，最后一条匹配的规则是不是
`ALLOW` 且 `resource != "*"`？

```python
def partially_allowed(action: str, *layers: Ruleset, posture: str = "build") -> bool:
    """The last rule for this action is a scoped allow (not ``*``)."""
    winner = None
    for layer in layers:
        for rule in layer:
            if not rule.postures or posture in rule.postures:
                if any(glob_match(action, alias) for alias in actions_for(rule.action)):
                    winner = rule
    return winner is not None and winner.effect is Effect.ALLOW and winner.resource != "*"
```

它是 `wholly_disabled`（`permissions.py:215-236`）的**逐行镜像**：
同一个 action 别名表、同一套 posture 过滤、同一个 last-match-wins。
唯一的差别是最后一行（`ALLOW + resource != "*"` vs `DENY + resource == "*"`）。
**不给 `Rule` 加方法**——`wholly_disabled` 也没有，保持一致。

`PermissionGate.partially_allowed(...)` 只是用 `self._layers(...)` 调这个纯函数，
与 `hides()` 调用 `wholly_disabled()` 的写法完全对称。

**但要注意 `hides()` 还有一个 agent-veto 分支**（`permission_gate.py:756-760`：
先查完整层，再单独查 agent 层）。`partially_allowed` 不需要那一半——
agent 的 deny 只会让工具更不可能出现，不会让它出现。所以它只看完整层。

它和 `wholly_disabled` 是同一形状的两个问题（"整个砍掉" vs "留一条缝"），
共用同一张别名表与同一套层序，所以工具面与执行期不会漂移。

**为什么必须带 `plan` 条件**：`/readonly` 是人手动开的绝对开关。
若只写 `partially_allowed`，一个会话里同时有 `/readonly on` 与
`/permissions allow write src/*` 时，write 会重新出现——那是放宽了 `/readonly`。
带 `mode == "plan"` 之后，`/readonly` 的语义**逐字节不变**。

**这也是"同一谓词"而不是再造一个**：工具面回答的是静态问题
"这个 action 有没有任何可能被允许的路径"（有 scoped allow 就有）；
执行期回答的是运行时问题"这一次调用是否被允许"。两者都由同一批规则派生。
agent 的 `edit * deny` 是绝对 veto，所以那条缝只可能是**计划目录**，
不可能是工作区其他文件。

**为什么这是安全的**：plan 的 agent 层有一条绝对 veto
（`edit * deny`，`permission_gate.py:564-582`，session allow 不能重开）。
所以 scoped allow 只能把**计划目录**放出来，其余任何路径仍是 DENY。
这正是 opencode 的形状（`whollyDisabled` 因 scoped allow 不剪除，执行期拒绝）。
plan 不是安全边界：真正的收窄靠 agent 规则 + gate + sandbox + 审批，而不是靠模型不越界。

#### 5.3.2 执行期（`core/dispatch.py:345-351`）

```python
if verdict is PermissionDecision.DENY:
    return self._denied(...)
# 规则层明确允许时，overlay 不再否决：plan 目录例外靠这条成立。
plan_exception = (
    posture_of(ctx.mode, ctx.readonly) == "plan"
    and item.tool.mutates_world
    and item.specific
)
if ctx.readonly and item.tool.mutates_world and not plan_exception:
    return self._readonly_denied(call), True, False
```

**`item.specific` 从哪来**：`PermissionGate.check` 返回的 `Decision`
加一个字段 `specific: bool = False`（默认值让 11 处既有构造点与所有测试不用改）。
只有在**所有 resource 的 winner 都是 ALLOW，且每个 winner 的 resource 都不是 `*`** 时
才置 `True`。

自审后**不再加**一个同义字段。`_Prepared.specific` 就是那个
布尔（从 `Decision.specific` 拷贝，默认 `False`）；再加一个同义字段是重复。

这是**新契约**，作用只有一个：让 dispatch 区分"base 的 `write * ask`"
与"agent 的 `edit .ai-coding/plan/* allow`"。它不进入 wire、不落盘、只被一个分支消费。

为什么不用 `matched_resource: str`：dispatch 只需要一个**布尔**问题
（"这次允许是不是有边界的"），resource 字符串没有第二个读者。
一个字段要有能说清的作用，否则就是冗余。

等价性：

- `/readonly on`（无 agent 规则）：`specific == False` → 仍拒，文案不变
  （`test_mode_gate.py:271-289` 通过）；
- `/readonly on` + `job_kill`（`mutates_world=True`，没有 scoped allow）→ 仍拒；
- **`/readonly on` 在 build 下即使有 session 的 scoped allow，也仍拒**
  （`mode != "plan"`）；这是与上一版的差别，更窄；
- plan + 用户把 plan agent 换成空规则：没有 scoped allow → overlay 仍拒（fail-closed）；
- plan agent + 工作区文件：DENY → 走 deny 分支（`test_mode_gate.py:257-269` 通过）；
- plan agent + plan 目录：ALLOW + 具体 resource → **放行**（T5 目标）；
- build：`readonly=False` → 不进这个分支。

### 5.4 `verify` 进 gate

**`ai_coding/tools/present_plan_tool.py:227-236`** —— **两次调用**，不要混：

```python
workspace = str(getattr(ctx, "workspace", "") or ".")
extra = tuple(getattr(ctx, "extra_workspace_roots", ()) or ())

# prose：plan 正文与步骤描述

    [plan, *(content for content, _, _ in items)],
    workspace, extra_roots=extra,

# shell：verify 是命令，路径候选由 shell 语法读

    offenders = outside_workspace_paths(
        [verify for _, verify, _ in items if verify],
        workspace, extra_roots=extra, from_shell=True,

```

**为什么不能合并**：`outside_workspace_paths` 的 `from_shell` 是**整批**的开关。
把 prose 用命令语法读会误报（路径后面的普通词被当成参数），
把命令用 prose 读会漏报（变量、命令替换里的路径）。两次调用各用各的语法，
是唯一的正确读法。

**`ai_coding/core/plan_runner.py::_workspace_offenders`** 同样两次：

```python
open_items = task.open_items()
offenders = outside_workspace_paths(
    [item.content for item in open_items], workspace, extra_roots=extra,
)

    offenders = outside_workspace_paths(
        [item.verify for item in open_items if item.verify],
        workspace, extra_roots=extra, from_shell=True,

```

（调用点 `:122` 与 `agent_loop.py:1997-2020` 的 `self.extra_workspace_roots`）。

注意：content 是 prose（`from_shell=False`），verify 是命令（`from_shell=True`）——
**不能共用同一个开关**：prose 里的 `/api/v1/users` 不是路径，命令里的 `/data/x` 是。
上面两处都按这个规则拆成两次调用。

**一处必须说清的边界**：execution 期的 `_needs_a_human`（`:122`）不是

### Q1 · 规则资源归一化的范围

## 10. 实施后的最终形态

plan 模式下，模型：

1. **看不到 `todo_write`**（T8），不会拿它当计划；
2. 试图改 `src/app.py` → 立刻被拒，文案指向 `.ai-coding/plan/`（T5）；
3. 写 `.ai-coding/plan/design.md` → 成功，文件真的出现在工作区（T5）；

6. 提交计划时若某 `verify` 指向工作区外 → **卡都不弹**，工具直接拒绝（T5）；
7. 提交成功的计划：卡片展示全文 + 条目 + verify + 依赖；批准后自动执行（T11 保留）；
8. 重开会话：历史 `present_plan` 卡可展开，看到**当时提交的原文**（T11）。

build、`/readonly`、执行 step 全部零变化（除 `.env` ask 是全局的，见 Q3）。
