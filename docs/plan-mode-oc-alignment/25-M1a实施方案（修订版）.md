## 2. 逐文件影响分析

> 每条给：**今天是什么** → **契约是什么** → **怎么改** → **为什么这么改**。

### 2.1 新建 `ai_coding/security/permissions.py` —— 规则语言

**今天**：没有这个东西。最接近的是 `security/permission_gate.py` 里那张「档位表」（工具名 ⇒ allow/warn），它不认资源、不认层、不认姿态。

**契约**（这个模块**只**做规则语言，不认 gate / 工具 / 判决 / 文件位置之外的东西）：

| 名字 | 作用 | 消费者 |
|---|---|---|
| `POSTURES = ("plan", "readonly", "build")` | 姿态阶梯，最严 → 最宽 | `posture_of`、授权展开 |
| `class Effect(ALLOW/ASK/DENY)` | 规则的效果 | gate |
| `@dataclass(frozen=True) class Rule(action, resource, effect, reason="", postures=())` | 一条规则；`postures=()` ⇒ 全姿态生效 | gate |
| `Ruleset = tuple[Rule, ...]` | 一层的规则 | gate |
| `glob_match(value, pattern) -> bool` | `*` 跨 `/`、`?` 匹配一字符、其余字面量、整体锚定 | `rule_matches` |
| `rule_matches(action, resource, rule, *, posture) -> bool` | 动作通配 + 资源通配 + 姿态过滤 | `evaluate` / `wholly_disabled` |
| `evaluate(action, resource, *layers, *, posture) -> Rule \| None` | **拼接后 findLast**；无命中 ⇒ `None`（**不是** allow）。**一次只问一个资源** | gate 的执行查询 |
| `wholly_disabled(action, *layers, *, posture) -> bool` | 只看**动作**：最后一条匹配该动作的规则若是「整动作 deny」⇒ True | gate 的目录查询 |
| `subjects_of(action, params) -> tuple[str, ...]` | 这次调用**碰什么**（资源维度；bash 按段 ⇒ 多项） | gate |
| `posture_of(mode, readonly) -> str` | `(mode, readonly)` ⇒ 姿态：`plan` ⇒ `plan`；否则 `readonly` ⇒ `readonly`；否则 `build` | gate / dispatch / loop |
| `load_rules(path) -> (Ruleset, errors)` | 读偏好类 YAML | gate |
| `load_policy(path) -> (Ruleset, errors)` | 读策略类 YAML；**非 deny 的规则报错跳过** | gate |

**为什么这样切**：规则语言是**纯数据 + 纯函数**，可以脱离 gate 单独测；gate 只做「把层拼起来 + 把结果翻译成 `Decision`」。

**`subjects_of` 的资源词表**（照 oc 的动作→资源映射，配上我们自己的路径立场）：

| 动作 | 资源 |
|---|---|
| `read` / `write` / `edit` | `params["path"]`（**词法**归一：去 `./`、`\`→`/`） |
| `glob` / `grep` | `params["pattern"]`（grep 的 `path` 是搜索根，不是被碰的东西） |
| `bash` | **按段**：`shell_parse.command_views(command)` 每个 `CommandView` 一段。一段的资源 = ①**该段的形状**（`program` + 参数，空格分隔——与 `bash_redlines` 现有的 `_shape` 同一套写法，提到 `shell_parse.command_shape()` 共用）＋ ②**该段每个重定向目标**（各算一个资源）；语法读不完的命令算**一段不透明的**（整条原文一个资源，Codex 的保守退化）；不是命令（注释/散文/没有语法）⇒ `*` |
| `skill` | skill id（`params["name"]`；`action=list` 时没有 ⇒ `*`） |
| `webfetch` / `websearch` | url / query |
| `subagent` | `*`——**我们没有 agent id**（`subagent` 的 `name` 是模型自己起的标签，规则拿它当目标没有意义） |
| 其余（含 `server__tool`、`mcp_call`） | `*` |

**命名不出来 ⇒ `*`**：资源为空串时不能当成空串——那样 `skill "*" deny` 这类规则在"没有点名 skill"的调用上**静默不触发**。命名不出来就是"不知道碰了什么"＝`*`。

**为什么 bash 按段**：`24` §4.1 L3——我们**已经有** `shell_parse.command_views()`（tree-sitter，含 `&&`/`;` 之后与命令替换里的），不按段匹配的话一条 `bash: "rm -rf *"` 规则**拦不住** `cd /tmp && rm -rf x`。Claude Code 与 oc 都是按子命令独立匹配的。

**为什么重定向目标是独立的资源**：形状（`program` + 参数）里**没有**重定向——`cat a > /dev/sda` 的形状是 `cat a`，目标 `/dev/sda` 整个不见了。一条只按形状匹配的规则永远看不见这次写；而「重定向是在写一个地方」正是资源维度存在的理由（`bash_redlines` 现有的红线规则也是单独看 `view.redirects` 的）。所以目标**各算一个资源**：规则可以写 `bash: "/dev/*" deny`，也可以写 `bash: "cat *" deny`。
**代价与取舍**：多资源合并是**不对称**的——任一资源 deny ⇒ 整体 deny；任一资源 ask ⇒ 问；只有**全部**资源都 allow 才算 allow。所以一条 `bash: "cat *" allow` **盖不住** base 的 `bash * ask`（目标 `/dev/sda` 仍是被问的那个）。这是**故意的**：deny 方向放开、allow 方向收紧，失败方向永远是"多问一次"而不是"少拦一次"。

**为什么归一只做词法**：沿用 `grant_key` 的既有立场（`permission_gate.py:318-327`：「路径解析是 Sandbox 的事，不是规则匹配的事」）。**边界裁决者仍是 Sandbox**，规则只比字符串。

### 2.2 改 `ai_coding/security/permission_gate.py` —— 装配与判决

**今天**（`check()` 的顺序，`permission_gate.py:476-572`）：bash 红线 → 配置 deny → **saved grant** → skill 策略 → allow 名单（含工作区外特判）→ 配置 allow → warn 名单 → trusted server → 未知 ⇒ 问。

**问题**（`24` §2）：三张表不是规则语言；「工作区外」是资源级的**特判**；没有资源维度；没有层。

**改后**（`check()` 的新形状）：

```
1. 硬拒层（代码，规则层之上，I3 不变）
   1a. bash 红线 → DENY                     （不变）
   1b. 配置 deny 的工具 → DENY              （不变）
   1c. skill 策略 → DENY/ASK/落回           （不变）
2. 规则层：findLast over L0 base → L1 standing → L2 用户文件 → L3 项目文件 → L4 会话层 → L5 策略类
   - 逐个资源独立求值，再合并（合并规则见下）
   - 任一资源命中 deny → 整体 DENY（带 reason）   （新能力）
3. saved 授权（只含 allow）：命中 ⇒ ALLOW
   - 位置在「规则的 deny 之后、规则的 allow 之前」（理由见下）
4. 规则的 allow → 工作区外检查 → ALLOW/ASK（不变）
5. 规则的 ask → WARN（带 reason）；无意见 → WARN（unknown tool，不变）
```

**saved 授权为什么夹在中间**：今天 saved 在 allow 名单**之前**（`:510-512` 早于 `:537`），所以「saved 命中 ⇒ 直接 ALLOW（连工作区外检查都跳过）」是**今天的行为**，新形状必须保住（§7.3 的那个角落）。但它**不能**救规则层的 deny（R17：规则 deny 压过 saved）⇒ 它只能夹在中间：**规则的 deny 之后、规则的 allow 之前**。这个位置两边都对：deny 赢 grant，grant 赢 allow。

**动作名归一契约**（`24` §2.1 R4 的根因）：`action = permission_name(params).lower()`，**两个查询都用它**。
- 今天 `check()` 小写化（`:478`），而 `_denied_tools`/`_allowed_tools`/trusted 用**原样**（`:500`/`:551`/`:564`）——三个名字空间。规则语言只留**一个**。
- 为什么小写可行：`_allow_tools` 的 22 个名字**本来就全是小写**（实测），只有工具真名 `subAgent` 是驼峰（`subagent_tool.py:137-138`）⇒ 小写化后 `subagent` 正好对上 base 的 `subagent`。
- 配置里的 deny/allow 用**原样**拼 `server__tool`（`:719-725`）⇒ 翻译成规则时**一并小写**，两侧都小写 ⇒ 匹配关系不变。
- **操作者手写的规则也要小写 action**（`permissions.yaml` 装载时）：否则写 `action: Edit` 是一条**永不触发**的静默规则。**resource 不小写**——Linux 上路径大小写是另一个文件。

**一处顺序变化（今天行为中性，写在明处）**：今天 saved 授权在 **skill 策略之前**（`:510-512` 早于 `:517`），新形状把硬拒层整体提到 saved 之前。因为 `grant_key("skill", …)` 恒为 `None`（skill 既不是路径类也不是目录类，`permission_gate.py:351` 的兜底 `return None`）⇒ **skill 的 deny 今天就压不过任何授权**（没有 skill 的授权可压）⇒ 今天行为不变。但顺序变了，R13 的语料表要显式覆盖这一格。

**base 怎么来**（`24` §0-1 的回归）：**从 `_allow_tools` / `_warn_tools` 派生，不手抄**：

```python
def _base_rules(self) -> Ruleset:
    """The base layer, derived from the two lists that are the truth today."""
    return tuple(
        [Rule(action=n, resource="*", effect=Effect.ALLOW) for n in sorted(self._allow_tools)]
        + [Rule(action=n, resource="*", effect=Effect.ASK) for n in sorted(self._warn_tools)]
    )
```
⇒ **条数相等是构造出来的**，不是抄出来的 ⇒ 以后再加工具，base 自动跟着走（`24` §2.4 E4 的修法）。

**多资源的合并规则**（`subjects_of` 可能返回多项，只有 bash 会）——照 oc 的多资源语义：
**逐个资源独立求值；任一资源命中 deny ⇒ 整体 deny；否则任一命中 ask ⇒ 问；否则（**每个**资源都命中 allow）才 allow。**
（oc：`effects.includes("ask") ? "ask" : "allow"`，外加一条「任一资源 deny ⇒ 整个操作 deny」。）
**为什么要求"每个资源都命中 allow"**：一个资源"没人管"就是**不知道碰了什么**——按 fail-closed 应当**问**，而不是当成 allow。（实践中这条只在 bash 上可能出现，而 base 的 `bash * ask` 覆盖了每个资源 ⇒ 真正触发的是"任一 deny ⇒ deny"与"任一 ask ⇒ 问"两条。）

**`Decision` 不改语义**（`24` §0-4）：保留手写 `__eq__`/`__hash__` 的类，**一个字都不加**。
- 复核后砍掉了初稿里的 `Decision.action` / `Decision.resource`：**没有消费者**——拒绝文案由 gate 在**判决当场**拼（它手里有 action 与 resource），不需要把这两个字段挂在返回值上。
- 这样 `__eq__`/`__hash__` 一个字不动 ⇒ 86 条 `== PermissionDecision.X` 断言与 `hash` 全部不受影响。

**新增一个方法给目录查询用**：
```python
def hides(self, action: str, *, session_rules=(), posture="build") -> bool:
    """Whether the catalogue drops this action entirely (Gemini/Claude semantics)."""
    return wholly_disabled(action, *self._layers(session_rules), posture=posture)
```
—— 与执行查询**同一批层、同一套匹配**（I1）。

### 2.3 改 `ai_coding/security/grants.py` —— 授权带姿态

**今天**：`{"version": N, "workspaces": {ws: [key, ...]}}`，一个 key 一个字符串；`load() -> set[str]`。

**改后**：一条授权 = `key@posture`（只记**当时**的姿态；「更宽松也能用」在匹配时由阶梯推出，不把集合写进文件）。旧格式（没有 `@`）⇒ 视为**全姿态**（向后兼容）。

**谁算适用范围**：`gate.grant(tool_name, params, *, posture)`——**dispatch 的 `_ask` 在 ALWAYS 分支调用它**（`dispatch.py:531`），而 `_ask` 手里有姿态 ⇒ 写 `key@build` 这类单姿态。`check` 匹配时：在 `X` 写的授权对 `X` 及所有更宽松姿态生效（Gemini 的阶梯）。`grant(...)` 不传 `posture`（旧调用/测试/回放）写**裸 key**，仍是全姿态。

**为什么**：Gemini 的授权语义是「在 X 做的授权适用于 X 与所有更宽松的姿态」（`24` §3.3）。我们的阶梯 `plan < readonly < build` ⇒ 在 build 做的授权**不**适用于 plan/readonly。

**今天的行为变化**（§7.3 有推导）：**只有一处**——「已授权的工作区外读」在严格姿态下会重新问一次（今天 grant 直接 ALLOW，连工作区外检查都跳过）。

**格式兼容**：`load()` 遇到旧格式条目按全姿态处理 ⇒ 已有用户的 `grants.json` 不用改。

**`@` 的歧义方向**：路径本身可以以 `@build` 结尾，旧格式无法区分。我们按**作用域**读（`src/a@build` ⇒ `src` 下的 `a`，仅 build），方向是**丢授权而不是放宽**。新授权给这种路径会写成 `...@build@build`，内层是路径、外层是姿态，可无歧义还原。

### 2.4 改 `ai_coding/tools/base.py` + `ai_coding/core/request_builder.py` —— 会话层随请求走

**今天**：gate 是**进程级**的（`cli.py:112` 建一个，全会话共用）；会话里没有规则。

**问题**（`24` §2.1 R3）：蓝图说「把 `session.permissions` 灌回 gate」，但 gate 是全局的、三个 gate 各自一份、会话加载有 3-4 条路（`handlers.py:410` 的 `session_load`、`handlers.py:610/731` 的 `resume_turn`、`commands.py:801` 的 REPL `/session`）⇒「一处灌回」不成立，而且灌进去的会**过期**。

**改法**：**会话层不进 gate**，它**随请求走**：
- `ToolContext` 加一个字段 `permissions: tuple[Rule, ...] = ()`（会话规则，L4）。
- `tool_context(...)` 加同名参数，由 `agent_loop._run_tools` 用**当次会话**的规则填。
- gate 的 `check()` / `hides()` 收 `session_rules=` 参数。

**为什么这样更好**：请求携带的规则**天然是最新的**（会话刚改完就下一次请求生效），没有过期、没有注入点；子代理继承父的会话层也只是「把父的规则传下去」（§2.9）。

### 2.5 改 `ai_coding/core/dispatch.py` —— 求值时带上姿态与会话规则

**今天**：`dispatch_batch` 有 `ctx`（带 `mode`/`readonly`），但 `_prepare()` **拿不到 ctx**（`:235-241`），于是 gate 的判决**不知道姿态**。

**改法**：
- `_prepare(call, *, ctx, iteration=0)` ⇒ `gate.check(action, params, session_rules=ctx.permissions, posture=posture_of(ctx.mode, ctx.readonly))`。
- guard 重写后的**再检查**（`:342`）同样带上姿态与会话规则（重写可能换了工具/资源）。
- 只读结构拒绝（`:323-324`）**位置与文案不变**（`readonly_denied` + 那段 G9 文案，三个测试钉着）。

### 2.6 改 `ai_coding/core/agent_loop.py` —— 目录查询 + 会话规则进 ctx

**今天**：`_surface_tools(mode, readonly)`（`:2376-2390`）按 `plan_only` / `mutates_world` 裁剪；`_surface_schemas(session)`（`:2392-2405`）按 `(mode, readonly)` 缓存。

**改法**：
1. 目录查询**加一条**规则层谓词：`not gate.hides(action, session_rules=..., posture=...)` ⇒ 整动作 deny 的工具从目录消失（今日新增能力）。
2. `_surface_tools` / `_prompt_tools` 需要**会话规则** ⇒ 签名加 `session_rules`（`_surface_schemas(session)` 本来就有 session ✓；`_prompt_tools(mode, readonly)` 的调用点 `:2363` 在 `self.prompt.build(...)` 里，而 `mode`/`readonly` 就在同一个函数里由 `session` 算出（`:2351-2355`，`session` 可能为 None ⇒ 无会话规则）⇒ 两个调用点都拿得到 session ✓）。
3. **缓存键**必须含会话规则：`_surface_cache` 的键 `(mode, readonly)` ⇒ 加**规则指纹**（会话规则变了，目录要重算）。

**为什么缓存键要改**：目录现在**依赖**会话层了；不把指纹放进键，`/permissions deny edit "*"` 之后目录不会变（今天也没有这个能力，所以这是**新能力**，不是回归）。

**MCP 的粒度**（用户拍板）：按**容器动作**。一条 `mcp_call` 的整动作 deny 让整个 MCP 容器从目录消失；不按 `server/tool` 逐条隐藏（那需要从 params 反推权限名，规则与目录的映射会分叉）。规则谓词查询前把目录名小写化（`subAgent` → `subagent`），与 gate 的动作命名空间一致。

### 2.7 改 `ai_coding/domain/session.py` —— 会话层落盘

**今天**：`SessionData.to_dict()` **只写非空字段**（`:536`「an empty ring is not worth a key in every file」）。

**改法**：`SessionData` 加 `permissions: list[dict]`（会话规则的 JSON 形态）；`to_dict` 按同一条约定**非空才写**。

### 2.8 改 `ai_coding/app/commands.py` —— `/permissions` 的读与写

**今天**：`/permissions` 只列 policy + 已记住的 grant；`/permissions clear` 清 grant（`:733-748`）。

**改法**：
- `/permissions`（读）：多列**当前生效的规则**（按层分组：base / standing / 用户文件 / 项目文件 / 会话层 / 策略类），并把坏文件的原因说出来。
- `/permissions deny <action> <resource>` / `/permissions allow <action> <resource>`：**写会话层**（L4）。
- `/permissions reset`：清会话层（`clear` 继续只清 grant —— 两个词各有各的职责）。
- `/permissions clear` 的文案按现状（`commands.py:729` 真实文案是「…clear removes them」，蓝图 §8.4 抄错了）。

**为什么需要写入口**：08 §7.6 明确「代码存在但没有消费者按 0.5 记」——会话级权限层若只能读不能写，D05 到不了 1。

### 2.9 改 `ai_coding/core/subagent.py` —— 子代理继承会话层

**今天**：子代理**自己**建一个 gate（`_child_gate()`，`:480-505`，`from_config` ⇒ 只有 L0/L1/L2/L3，没有 L4）；approval 是 `AutoApproveCallback` ⇒ **WARN 一律自动 yes**（子代理没法问人——这一条**今天已经成立**）。

**改法**：父的会话层规则**传给子代理的 loop**（`AgentLoop(..., session_permissions=父的规则)`）⇒ 子代理的 gate 在求值时看到同一批 L4 规则。

落在哪：`ToolContext.permissions` 已经在父请求里（§2.4）；`subAgent` 工具把它放进 `ParentContext.permissions`（新字段），且**即使没有 messages/instructions 也要建 ParentContext**（只继承规则也是一种上下文）；runner 在 `_run_in` 里把它交给 `AgentLoop(session_permissions=…)`。

**为什么**：④ 的「继承」；也堵住「子代理是规则的盲区」。

**不做的**：把 approval 改成 dsh 的 `never`（ask 一律拒）——那会让子代理**连 bash 都不能跑**（今天的 WARN 自动 yes 是子代理能干活的前提）。**保持自动 yes，并在文档里写清**。

### 2.10 改 `ai_coding/core/acceptance.py` —— 验收命令走规则层（③）

**今天**（`:34-70`）：`_needs_a_human()` 只查 `bash_denied`（红线）与工作区外；**绕过整个 gate**（`agent_loop.py:1746-1750` 明说）。

**改法**：`verify_items(...)` 多收一个**窄回调**（默认 `None`），对每条 verify 命令先问它：「这条命令按规则层会被拒吗？」命中 deny ⇒ 该 item 判失败（`passed=False`，输出写明被哪条规则拒）。

**怎么问**：回调背后是 `gate.check("bash", {"command": cmd}, session_rules=…, posture=…)`，**只看 DENY**——`ask` 在这里**不算**（今天的普通验收命令（`pytest`、`test -f`）是**不问就跑**的，base 的 `bash * ask` 若被当成「要问」会把验收变成处处要人点）。DENY 才拦。

**为什么**：③；否则「规则文件是边界」的承诺有个大洞（红线的第二个消费者也在 `acceptance.py:57`，蓝图没列）。

**为什么用回调而不是把 gate 传进去**：`acceptance.py` 现在**不依赖 gate**（只 import `bash_denied`）⇒ 传一个窄回调（`deny_reason(action, params) -> str`）保持它的依赖面不变。

### 2.11 改 `ai_coding/server/handlers.py` —— 对话框的读数

**今天**：`permissions_state` 返回 `{policy, grants, storePath}`（`:922-940`），前端 `PermissionsState` 是 `{policy: string; grants: string[]; storePath: string}`（`frontend/src/util/permissions-dialog.ts:13-17`）。

**改法**（用户拍板：**扩展 TUI**）：现有三个键保持不变；新增 `rules`：

```json
"rules": {
  "layers": {"base": 25, "standing": 1, "user": 2, "project": 1, "session": 1, "policy": 1},
  "session": [{"action": "edit", "resource": "*.env", "effect": "deny"}],
  "errors": ["..."],
}
```

`layers` 是每层的**条数**（不是逐条规则：用户拍板「分层计数」），`session` 是会话层本身（要能看见自己刚加的规则），`errors` 是坏文件/坏会话行的原因。TUI 对话框显示这三者，并新增 `r` 键发 `/permissions reset`——仍然**只走命令通道**，没有第二个写入点。`grants` 仍是字符串数组（渲染 `grantLine`，把 `tool:path` 显示成 `tool · path`）。姿态不进这个读数（它是**授权的内部细节**，显示出来反而让人以为可以编辑）。

```

  → 人选「不再问」 → gate.grant() 记下 edit:src/app.py@build
  → 下次同一调用：saved 命中 → ALLOW（不问）
```

## 7. 最终模样（实施完之后）与中途细节核对

### 7.1 一次 `/permissions` 长什么样

```
[permissions] policy=auto  store=~/.config/ai-coding/grants.json
  base       25 条（22 allow + 3 ask，由活名单派生）
  standing   1 条（config-allow: fs__write_file）
  用户文件    2 条（~/.config/ai-coding/permissions.yaml）
  项目文件    1 条（<ws>/permissions.yaml）
  会话层      1 条（本会话 /permissions deny 加的）
  策略类      1 条（~/.config/ai-coding/policies.yaml，只 deny）
  已记住的授权  edit:src/app.py@build
```

### 7.2 中途细节核对（每一步都要对得上）

| 步骤 | 对不上的话会怎样 |
|---|---|
| base 派生 | 少了 `finish_research` ⇒ 研究出口前多一个审批面板 ⇒ **R12 必须先红** |
| 归一化 | 执行用小写、目录用原样 ⇒ `subAgent` 规则两处不一致 ⇒ **R16 必须先红** |
| 会话层随请求 | gate 是全局的 ⇒ 会话层若存在 gate 里就会**过期** ⇒ 用 `ctx.permissions` ⇒ 天然最新 |
| 缓存键 | 目录缓存键不含规则指纹 ⇒ `/permissions deny` 后目录不变 ⇒ **R15 必须先红** |
| 策略类末位 | 策略类若参与 findLast，项目文件的 allow 能盖掉它 ⇒ 提权面还在 ⇒ **R8 必须先红** |
| 授权姿态 | 授权无姿态 ⇒ build 的授权漏进 plan ⇒ **R18 必须先红** |
| 只读结构拒绝 | 若改成规则 deny，错误码变 `denied`、`readonly_denied` 的三处断言与 G9 文案都变 ⇒ **不改**（§1.2） |

### 7.3 授权带姿态，今天到底改变什么（诚实推导）

能被授权的动作只有：`read`/`glob`/`grep`（按目录/文件）、`write`/`edit`（按文件）、`mcp:<server>__<tool>`。

- `read`/`glob`/`grep` 在 base 里就是 **allow** ⇒ 有没有授权都不问 ⇒ **无差别**。
- `write`/`edit`/`mcp` 在 plan/readonly 下被**结构拒绝**（`mutates_world`）⇒ 授权在严格姿态下用不上 ⇒ **无差别**。
- 唯一有差别的角落：**工作区外的读**。今天的顺序是「saved 命中 ⇒ 直接 ALLOW（连工作区外检查都跳过）」；带姿态后，在 plan/readonly 下 build 做的授权不生效 ⇒ 落到 base 的 allow 分支 ⇒ **工作区外检查会问一次**。
  ⇒ 这是**唯一**的可见变化，方向是**更严**（与 Gemini/Claude 一致）。

## 8. 风险与回归面

| 风险 | 处置 |
|---|---|
| 改了 gate 的判决顺序 ⇒ 行为漂移 | R13 的语料表当**等价性金标准**；任何一行不一致就停 |
| `Decision` 变 dataclass ⇒ 86 条断言 + hash | 不改类，只加两个可选属性（R11 之外单测覆盖 `==` 与 `hash`） |
| 目录裁剪引入规则层 ⇒ 请求不再 byte-stable | 缓存键含**规则指纹**；指纹变了才重算 |
| 授权格式变 ⇒ 老用户的 `grants.json` 读不出来 | v1 条目按全姿态读；R18 覆盖 |
| 规则文件语法错 ⇒ 静默失效 | 装载器**返回错误**（不抛），`/permissions` 与日志里说出来 |
| 策略类被当成 allow 的后门 | 装载器只收 deny；非 deny 报错跳过（R8） |
| 子代理继承规则 ⇒ 子代理突然被拒 | 只继承**会话层**（L4）；base/L1/L2/L3 子代理本来就有（自己的 `from_config`） |
