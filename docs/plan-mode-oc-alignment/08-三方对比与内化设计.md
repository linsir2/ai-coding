## §2 相似度

### 2.1 两套账

B 的剩余 0.5 只有三格：D13（OC 计划=对话回答，我们有结构化 items）、D14（OC 无审批/执行器，我们有）、D25（Q6 保留沙箱，不做 external ask）。这三格是**用户边界决定的保留差异**，不是未完成项。

### 2.2 为什么当前仍是 40%，而适配后从 94% 修正为 88%/94% 两套账

1. **当前 40% 不变**：25 维的评分没变。重审事实改变的是"证据强度"和"执行层缺陷清单"，不是 OC 相似度的算术。上一轮把 D13/D14 记 0.5 是对的；本轮只是把"0.5 的原因"从"保留执行层"精确到"同意粒度/生命周期/回读"。
2. **上一轮 94% 的隐含假设被拆开**：它默认 T1/T2/T3/T7 会把 D02/D03/D04/D05/D19/D20/D24 全部推到 1。重审后，D02/D04/D19/D20 可由 C/A 修正覆盖（入口增强、synthetic 对账、boot 复位、UI），但有三格是 03/04 没有覆盖的硬缺口：
   - **D03**：T1 只加 `session.agent` + 双写，T7 只加 wire notice；没有 durable `agent-switched` 消息、没有 assistant 消息的 `agent` 归属。要 1 必须加 T1b。
   - **D05**：T2 只做 agent 规则 + dispatch；没有 session 级权限层、没有 `permission.evaluate` hook。要 1 必须加 T2b。
   - **D24**：T2 复用现有 `PermissionGate` 的 once/grants；没有 reject-with-feedback、没有 saved deny 优先级、没有 always 的 `save` 语义。要 1 必须加 T2c。
   因此"03/04 原样"是 88%，"补三个硬 parity 子任务"才是 94%。这不是分数缩水，而是把上一轮隐含的工作量显式化。
3. **C01-C09 不改变主分，但改变交付质量**：评审卡 items/verify（C01）、present_plan 劫持（C02）、boot 姿态（C03）、执行期事件/收据（C04）、工作区门（C05）、assembler 旧 policy（C06）、depends_on（C07）、反向互斥（C08）、提交语义（C09）——这些是"做对了但不够安全/不够可审计"的缺陷。94% 是相似度上限，不是交付质量证明；Part 2 必须把它们列为独立验收项。
4. **硬档仍达标**：Q1 硬档会把 D09/D10/D11 从 1 降到 0，B-hard 82%、A-hard 76%，都 ≥65%。所以 65% 门槛不依赖"软只读"这个争议决策；软档是把上限从 82% 拉到 94% 的杠杆。

### 2.3 最脆弱假设（按脆弱度排序）

1. **D04=1 依赖 synthetic 的请求边界投递/去重**：如果只在切换时 append、不做每请求对账，或压缩后重复补挂，D04 只能 0.5（B→92%）。C11/A01/A08 是这条的保险。
2. **D09/D10/D11=1 依赖 T2 同时替换 schema 裁剪谓词**：如果只改 dispatch、不改 `agent_loop.py:344-351` 的 `mutates_world` 过滤，软档下 shell/subagent/web 仍然不可见，三格全 0（B→82%）。这是 T2 最容易"做了一半"的地方。
3. **D15/D16=1 依赖 C09 的严格提交语义**：如果 keep/esc/空答案仍算 `plan_submitted`，守卫仍可被"假提交+搁置"绕过，研究出口名义存在但行为不成立（D15/D16 各掉 0.5，B→90%）。
4. **D19=1 依赖 C03 的 boot 姿态复位 + A10 的 durable pending**：如果只做 `session.agent` 落盘、不做 boot 复位，崩溃恢复仍停在 PLAN·只读，D19 只能 0.5（B→92%）。
5. **D21=1 依赖完整 `.md` 合并/优先级/`default_agent`**：如果只做内置 plan、不做用户/项目覆盖，D21 只能 0.5（B→92%）。
6. **D13/D14=0.5 是边界锁**：除非删除审批/执行器（违反用户边界），否则 94% 就是上限；不要为了"刷分"去动流水线。
7. **Q1 软档的 1 是"行为相似"，不是"安全等价"**：OC 和 dsh 都明确 plan 不是安全边界；软档下 shell/subagent/MCP 可写。真正的安全仍靠 `PermissionGate` 的 hard-deny、沙箱和人工审批。硬档是安全回退，不是低分选项。

### 2.4 结论

- **当前 40.0%；适配后 88.0%（03/04 原样+必改项）/ 94.0%（完整 parity 包）；硬档 76%/82%。全部 ≥65%。**
- 65% 门槛的关键不是 T4/T6，而是 **T1/T2/T3 的同源闭环**：agent 状态、规则裁剪、提醒对账三者必须共用一套谓词/事件；否则 D03/D04/D05/D19 会同时掉 0.5。
- 94% 的关键增量是三个 parity 子任务（T1b/T2b/T2c），不是再加新维度。
- 下一步（Part 2）应按"先修 C01-C09 的正确性，再补 T1b/T2b/T2c 的 parity，最后做 dsh A 项"排序；不要先做 UI 或 prompt 润色。

### 3.3 采纳后的形态约束（冲突裁决）

1. **stance 用 agent，不用 boolean**：A01 的 `plan/mode` 事件必须映射为 `session.agent.selected`（或等价的 `plan.stance` 投影），否则会和 Q4 的 agent 实体形成双源。dsh 的"同一 session + boolean"只借状态机，不借形态。
2. **评审与执行分离**：A02 的"严格 approve"只决定**是否 arm**；A01 的"请求边界翻态"只决定**提醒/姿态何时切换**。两者可以不同步：approve 立即 arm（执行层需要），姿态在下一请求边界翻（避免 in-flight 撕裂）。这是与 dsh 最大的行为差异，必须在 Part 2 写测试。
3. **plan 不是安全边界**：A03 的三轴分离必须让 `Enforcement` 拥有最终否决权；`PlanStance` 不能直接改 sandbox/approval。软档下 shell/subagent/MCP 的 allow 是"行为相似"，不是"安全等价"（N01）。
4. **todo 一分为二**：plan 下隐藏（Q3），执行 task 跨 step 保留；dsh 的 turn/start 清空只适用于独立 scratch checklist，不适用于 `TaskState`（N04）。
5. **产物双轨**：tool args 是权威（A07），Q5 工作区 `.ai-coding/plan/` 是可选文件；两者不一致时以 tool args 为准，文件只作导出/审阅。

### 5.2 叙事（主路径 + 三个分支）

1. **选择 agent**。用户 shift+tab 或 `/agents` 只改前端 draft（S-02）。回车时 `prepareAgent` 比较 `session.agent`：新会话把 agent 放进 `session.create`，已有会话发 `session.agent.select`（S-03）。服务端 `request_posture(agent=...)` 在空闲时立即提交，mid-turn 时写 durable pending 并返回 `queued`（S-04/T10）。提交后写 `session.agent`、追加 `agent-switched` 消息（含 previous），assistant 消息从此刻起带 `agent`（S-05/T1b）。
2. **提醒不是切换瞬间的消息**。enter/leave 先进入 durable `pending_reminders`（S-06）；在下一次 accepted pre-step（turn 开始或 close）drain 成 synthetic 消息（S-07）。每次装配请求时 `plan_reminders` 再对账：如果最后一条提醒与当前 agent 不一致或缺失（压缩/恢复/旧会话），就在最后一条 user 前补挂；exact kind+text 去重，重复不叠挂（S-10/A08）。
3. **请求装配**。`session.agent` 解析成 `AgentSpec`；权限 = 内置 base allow + agent 规则 + session 规则 + saved（S-08）。工具表按 `wholly_disabled` 裁剪：plan 软档下 edit 仍可见（执行期拒），shell/subagent/web/MCP 可见（OC 同款）；硬档才整剪除（S-09/S-11）。system prompt 只保留与当前档一致的指导，不再出现“prompt 说不能写、dispatch 却允许”的矛盾（C14）。
4. **研究分支**。模型按 `PLAN_PROMPT` 探索；纯问答/分析收尾调用 `finish_research({summary})`（S-14）。工具成功置 `research_finished`，不写 task、不 arm、不弹卡；守卫看到它直接 FINISH，**不改变 agent/提醒（仍是 plan，下一轮仍可继续规划）**。若模型不调用，守卫仍有一次 `PLAN_NUDGE` 兜底（双出口文案）。
5. **计划分支**。模型调用 `present_plan`；工具在**问人之前**校验 plan/items/depends_on 与 `core/plan_scope.py` 的工作区可达性（S-15/R02），然后构造 `ReviewRequest(call_id, items, verify, depends_on)` 发给 `ask(intent="plan_review")`。评审卡展示完整 markdown + 步骤表；用户在卡上 approve/keep/dismiss（S-16）。
6. **approve 与姿态分离**。approve 严格匹配、无 custom 文本；工具立即 `items.clear()` + 逐条 add（依赖转 id）、`armed=True/profile=plan`、重置 plan episode 计数（S-17/R10）。**但不立即改 agent**：写 durable `pending_posture={agent:"build", readonly:false}`，在 turn close 提交（S-20）。因此正在跑的规划回合不会被撕裂；crash 时 `task.armed` 已落盘，boot 会先复位姿态再执行（R07）。approve 后 emit TaskUpdated，卡立刻显示新列表。
7. **keep/dismiss**。keep 返回 tool error + 反馈，模型在同一 turn 内改完再提交；dismiss/esc/空答案结束 turn、不算提交、不 arm、不 auto-run，guard 写“未提交”note 但不 NUDGE（S-18/S-19/R08）。`present_plan` 与 `finish_research` 先成功者生效，另一个调用返回 `already_concluded`。
8. **自动执行**。只有 `turn.finished` 是 completed、`approved` 为真、`planRunEligible` 为真且 `report.stopped` 为空时，前端才静默 `/plan run`（S-21/R11）。`/plan` run 入口确保 agent 已切 build；`PlanRunner` arm 并持久化，`TaskDriver` 选 ready（含依赖），每步 fresh ephemeral + `agent=build` + 全量工具（S-22/S-23/S-24）。
9. **执行期可审计**。每步开始/结算/fiat/arm/disarm 都 emit `TaskUpdated`；结算写 `StepDelivery` 到 parent，发 `plan.receipt`；前端 live 更新卡和收据（S-26/R06/R05）。verify 失败→repair 一次；预算切断且未完成→continue 一次；修复/续跑共享一次机会（S-25）。
10. **停止与恢复**。blocked 立即停，stalled 继续，budget/deadlock 在 report 里写止因；finally disarm。boot 只选 profile∈{plan,goal} 的 armed 会话，跳过坏 profile，touch `lastAccessTime`，把父会话置 build/readonly=false 再 resume；resume 失败 disarm+note，5 次 breaker 保留（S-28）。`session.load`/replay 从 JSON 重建 plan card、收据与 agent 标签（S-29）。

## §6 决策收口

> 每条给“推荐 + 理由 + 权衡”。标 **【必须】** 的项是执行层/同意质量的红线，不能用“相似度已经够了”绕过。

### 6.1 Part 1 待决点

#### D-01 parity 包是否纳入

**推荐：纳入（T1b/T2b/T2c 全做，目标 94%）。** 理由：三个子任务各补一个硬缺口（D03 消息级 agent 归属、D05 session 级权限层、D24 完整 ask 语义），不是“再刷 6 分”的装饰；不做的 A 账 88% 仍达标，但 D03/D05/D24 会永久停在 0.5，且 T2c 的 reject 反馈/always 语义是实际审批质量问题。成本：T1b S/M、T2b M、T2c M；风险集中在消息 schema 与审批资源归一化。**排期建议**：T1b 跟 T1 同里程碑；T2b/T2c 跟 T2 同里程碑；若只能做一个，先 T1b（D03 最可见、成本最低）。

**权衡**：T2b 的 session 级权限目前没有 UI/API 来源，先做成可持久化字段 + hook，不急着做选择器；T2c 的 `always` 资源归一化要处理路径/命令两种 resource，测试量比代码量大。

#### D-02 approve 立即 arm vs 请求边界翻姿态

**推荐：分离——approve 立即 `task.armed=True`，姿态（agent/提醒）在下一个请求边界提交。** 理由：
- 执行层需要 `armed` 立即持久化：批准后、`/plan run` 派发前崩溃，boot 必须能续跑（`plan_runner.py:295-303` 的崩溃点①）。
- dsh 的“下一个 accepted pre-step 才翻态”解决的是 in-flight 请求撕裂；我们的 `present_plan` 在规划回合内，立即改 `session.agent` 会让同一回合的后续工具/提醒变成 build，违反“批准内容 = 用户看到的内容”。
- 实现：approve 写 `task.armed/profile` + `session.pending_posture={agent:"build",readonly:false,reason:"plan_approved"}`（durable，T10）；turn close 的 `_apply_pending_posture` 提交；前端 auto-run 发生在 terminal 之后，所以 run 一定看到 build。
- keep/dismiss 不写 armed、不写 pending。

**权衡**：turn 结束前状态栏仍显示 PLAN（可加“已批准，回合结束切换”的提示）；如果用户在批准后立刻发消息，pending 在下一个 turn 入口提交，仍安全。**测试必须覆盖**：approve→crash→boot 走 build + armed；approve→turn close→前端 auto-run 看到 build；approve 后同一 turn 的 reminder 仍是 enter（不是 leave）。

#### D-03 Q1 默认档与回退口径

**推荐：目标默认软档 `plan_strict_readonly=False`；但先以硬档 `True` 合并，T6 评测通过后再改默认。** 理由：
- 软档是 D09/D10/D11=1 与 94% 的杠杆；OC 本身就是软边界，硬档是“安全等价”而不是“行为相似”。
- 但默认值不应由文档拍脑袋：T6 的 12 回合真机评测（3 类任务 × 2 run × 软/硬）必须先回答“越权写尝试 ≤1/回合且无实际落盘破坏”。不达标就保持硬档。
- 回退口径：硬档是**受支持配置**，不是降级失败；A-hard 76%、B-hard 82%，都过 65%。`/readonly on` 是独立 overlay，任何档位都可叠加。
- 合并顺序：`True`（现有行为，测试不变）→ 两档规则全绿 → 评测 → 达标后默认 `False`，并在 release note 写明“plan 不是安全边界”。

**权衡**：软档下 shell/subagent/MCP 可写，安全靠 `PermissionGate` hard-deny + 沙箱 + 审批；这会改变用户对“PLAN=只读”的直觉，UI 必须显示“软只读/硬只读”而不是只显示 PLAN。

#### D-04 `finish_research` 命名、判别与优先级

**推荐：命名 `finish_research`；仅 plan agent；参数 `{summary: str}` 必填；与 `present_plan` 先成功者生效。** 理由：
- `finish_research` 是动词-对象，和 `present_plan` 并列，模型更容易区分“收尾研究”与“提交计划”；`conclude_research` 也可，但 `finish` 与现有 `finish` 语义（结束回合）一致。
- 判别：**有可执行步骤** → `present_plan`；**纯问答/分析/评估结论** → `finish_research`。不允许用 `finish_research` 逃避计划（prompt 明示；守卫仍要求两个出口之一）。
- 优先级：同一回合先成功者生效；另一个调用返回 `already_concluded`。`present_plan` 的 keep 不算成功，所以之后仍可 `finish_research`；`finish_research` 成功后不能再 `present_plan`。
- 守卫：`approve || research_finished` 放行；dismiss 单独结束；两者都无 → NUDGE 一次。
- 传输：`finish_research` 的 summary 落 tool 结果/转录，不写 task、不 arm。

**权衡**：模型可能把“研究完了，顺便给个计划”拆成两次调用；prompt 要写“一个回合只选一个出口”。命名变更成本低，但如果已有前端文案/测试用 `conclude_research`，统一改一处。

#### D-05 boot 续跑父会话姿态 + plan card 回读是否本期

**推荐：boot 续跑前把父会话置 `agent=build`/`readonly=false`/`mode=normal`；plan card 回读本期做最小版（R05）。** 理由：
- boot 是自动执行，不是规划；保持 PLAN 会让状态栏、提醒、工具面全部错位（F-46/D19）。执行 step 本身是 fresh `agent=build`，父会话也应是 build。
- 回读是 C01/D19 的一部分：重开后用户必须能看到“批准了什么、执行到哪”。最小版只返回 `agent/task/stepDeliveries` 并重建 plan card/收据；不重放 step 的每个工具调用（那是完整 replay，成本高）。
- 失败语义：`resume_turn` 或 runner 异常 → disarm + persist + note，不留下 armed；5 次 breaker 保留。

**权衡**：boot 后用户看不到“PLAN”标签，可能误以为计划模式丢了；用 plan card + “恢复执行”提示补偿。若本期砍掉回读，D19 只能 0.5，且用户重开后计划不可见——不建议砍。

| 2 | `present_plan` 是否限 plan agent | **【必须】是**：仅 `session.agent=="plan"` 且（未 armed 或 `armed_profile=="plan"`）；normal/step/goal 一律结构化拒绝 | 防 C02/C08 劫持；step 会话显式 `agent=build`。自定义 plan-like agent 本期不支持；未来加 `capabilities: ["plan_exit"]` 再放开。权衡：用户自定义只读 agent 不能提交计划；先保证内置 plan 的正确性。 |
| 3 | dismiss 语义 | **显式 dismiss/esc/空答案 = 结束 turn、不算提交、不 arm、不 auto-run、不 NUDGE；写“未提交”note；plan agent 保持 active** | dsh 的 dismiss 是“用户想自己说”，不是拒绝计划。keep 才是“改完再来”（tool error + 反馈，同 turn 重做）。strict approve 只认精确 `{"choice":"approve"}`；approve+custom 文本按 keep 处理。权衡：多一个 `review_dismissed` snapshot 字段；前端 esc 与空答案要统一映射。 |
| 4 | 执行期 TaskUpdated 频率 | **step 开始（in_progress）、settle（completed/blocked/stalled）、fiat 回填、arm/disarm 各一次；同一轮内合并重复状态** | 前端已有 `plan.updated` 消费者；不做每 token/每工具事件。权衡：step 开始事件会让卡短暂显示 in_progress；如果太吵，可只保留 settle + arm/disarm（但用户看不到“正在跑哪步”）。 |
| 5 | 收据是否进 wire | **保留 `plan.receipt` 并补最小字段（statement/status/ac/attempts/attested/turns/usage）；同时 R05 做 durable 回读；不把 verify 全文/工具输出放进 wire** | 收据是审计/UI 的稳定契约，已有 `plan.receipt` 消费者；回读解决重开。wire 只传摘要与判定，完整输出留在 JSON/收据文件，避免体积与敏感信息。权衡：字段增加要同步前端类型；旧客户端忽略新字段即可。 |

### 7.4 T6 评测附件更新

**场景**：3 类任务（项目评估 / bug 修复 / 重构）× 2 run × {软, 硬} = 12 回合；真实模型；同一提示词/同一仓库快照。可加 4 个定向探针（不混入主 12 回合）：

1. 评审卡 items/verify 可见性（approve 前截图/转录检查）。
2. keep/dismiss/空答案/超时后的 auto-run 假阳性。
3. 压缩后提醒重复/丢失（统计 enter/leave 条数）。
4. approve→kill→boot 的姿态/armed/回读。

**指标**（在 04 §5.3 基础上补）：

| 指标 | 定义 | 用途 |
|---|---|---|
| 越权写尝试 | bash 中 `rm/mv/重定向写/git commit` 等 + edit/write 被拒次数 | 软档安全判据 |
| 实际落盘破坏 | 工作区外/非计划文件的真实变更 | 一票否决 |
| bash 调用总数 | 每回合 | 软档探索成本 |
| 探索有效率 | 有信息产出的工具调用占比 | 计划质量 |
| 回合步数/token | 每 run | 成本 |
| 计划 items 可执行率 | `verify` 干跑通过率 | 计划质量 |
| 同意准确率 | 批准后 task.items == 卡上 items/verify 的比例 | R04 必过 |
| auto-run 假阳性 | dismiss/keep/abort/timeout 后仍执行的比例 | 必须 0 |
| 提醒重复/丢失 | 每回合 enter/leave 期望条数 vs 实际 | T3 锚点 |
| 计划质量（1-5） | 人工盲评（decision-complete/可执行/无实现） | 软硬对比 |

**判据**：
- 软档默认成立需同时满足：越权写尝试 ≤1/回合、实际落盘破坏 = 0、auto-run 假阳性 = 0、同意准确率 = 100%、计划 items 可执行率不低于硬档 − 10 个百分点。
- 任一不满足 → 默认保持硬档 `True`；软档仍可作为显式配置。
- 计划质量若软档显著低于硬档（>1 分），先修 T12 prompt，再谈默认值。

**产物**：`/tmp/opencode/t6-eval/`（逐 run JSON + 汇总 md + 关键截图/转录片段）；结论回填 03 §9 与 04 §5.3。

### 8.3 执行层保留契约（不可删/不可降级）

**保留**：
- `present_plan` 批准 → `task.items.clear()` + 逐条 add（整表替换）；approve 后 `armed=True/profile=plan`。
- `PlanRunner` / `TaskDriver` 的分步执行、fresh ephemeral step session、task 共享、seed。
- `acceptance.verify_items` 的机械验收；verify 失败 → blocked；repair/continue 各一次。
- `StepDelivery` 收据、`PlanStepReceipt` 事件、父会话两气泡；`step_deliveries` 持久化。
- boot resume：armed 扫描、`resume_count` 5 次 breaker、`resume_turn`、plan/goal profile。
- Esc：先 disarm 再 cancel；所有出口 disarm。
- 前端 approve 后的自动 `/plan run` 路径（TUI）；CLI 手输 `/plan run` 的平台差异保留。
- 审批卡/问题通道（`user_prompt.ask`）与 300s 超时。

**允许改**（修缺陷，不删流水线）：
- 评审卡内容/三态/严格同意；approve 后的姿态提交时机；TaskUpdated 发射点；收据回读；工作区门时序；boot 姿态复位；`depends_on`；episode 计数；auto-run 资格。
- 计划的工具可见性/规则（T2/T6）、提醒载体（T3）、agent 归属（T1/T1b）。

**明确不做**：
- 不把 `PlanRunner` 改成单回合“模型自己执行”。
- 不删除 verify/收据/boot resume/审批卡。
- 不把 plan 变成纯 prompt（N01）。
- 不用 `turn/start` 清空 `TaskState`（N04）。

### 8.4 迁移期双写边界

| 数据 | 权威源 | 迁移期兼容 | 退出条件 |
|---|---|---|---|
| agent | `session.agent` | 继续写 `mode`（派生：agent=plan→`"plan"`，否则 `"normal"`）；旧文件 `mode=="plan"` → `agent="plan"` | 一个 release + 所有客户端读 `agent` 后，停止写 `mode`；`mode` 只读兼容 |
| readonly | `session.readonly`（显式 `/readonly` overlay） | **不再由 plan 派生**；旧文件保留原值（旧 plan 会话仍偏硬，fail-closed）；新 `/plan` 写 `readonly=false` | 前端/统计改用 `agent + planStrict + readonly` 三字段；`readonly` 永久保留为 overlay |
| pending | `session.pending_posture`（durable） | 旧文件无此键=空；写入 `schemaVersion`/`updatedAt`；turn close/entry 提交 | T10 稳定后仍保留；崩溃窗口测试 |
| 切换记录 | `session.agent_history` + `session.messages` 的 `agent-switched` + assistant.agent | 旧消息无 `agent` 字段→UI 隐藏标签，不默认 build | T1b 稳定后仍保留；重放测试 |
| 权限 | agent 表 + `session.permissions` + grants | 旧 `grants.json` 继续读；agent 规则先生成，session 规则为空 | T2b 稳定后仍保留；不做第二套审批 |
| 提醒 | `session.messages` + `pending_reminders` | 不另存“last reminder”字段；每次从消息派生 | T3 稳定后仍保留；压缩/重启测试 |
| 计划产物 | tool call args | 工作区 `.ai-coding/plan/` 只是可选导出，不权威；两者不一致以 tool args 为准 | 永久 |
| 收据 | `session.step_deliveries` | `plan.receipt` 是事件，不是存储；`session.load` 增加只读投影 | 永久 |
| 前端 wire | `session.agent` + 旧 `mode/readonly` 同时发 | 旧客户端忽略新字段；新客户端优先 `agent` | 一个 release 后旧字段可标记 deprecated，不删除 |

**T1/T2/T6 的迁移红线**：T2 规则引擎与 dispatch 谓词全绿之前，`/plan` 仍写 `readonly=true`；T2 完成后 T6 才把 `/plan` 改为 `readonly=false`（软档）。否则会在迁移窗口直接打开 `mode=plan/readonly=false` 的全量工具洞（F-50）。旧 session 文件中的 `mode=plan,readonly=true` 保留 `readonly=true`（偏硬、fail-closed），直到用户 `/readonly off` 或 `/plan off` 后重新进入才进入软档。

**双写纪律**：
1. 只双写“旧读者需要、且能从权威源派生”的字段（`mode`）；不双写权限/提醒/收据。
2. `readonly` 不派生自 agent；否则软档会被旧逻辑误判为只读。
3. 任何双写必须在同一 save 内完成，避免崩溃窗口出现“agent=plan 但 mode=normal”的撕裂。
4. 迁移测试覆盖：旧 `mode=plan,readonly=true` 文件加载；旧 `mode=normal` 文件；无 `agent` 字段的消息；无 `task` 的会话；坏 agent id。
