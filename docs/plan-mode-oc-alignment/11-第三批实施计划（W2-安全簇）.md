## 0. 目标与最终模样

W2 落成后：

1. **不可达路径在花钱之前被处理**：`present_plan` 在**问人之前**校验——`plan` 文本与 items 内容里的工作区外路径 → 结构化拒绝（模型当场改）；`verify` 里引用的工作区外路径 → 作为**警告**随评审卡展示（不阻断，用户自会判断）。
2. **roots 三处一致**：`present_plan`、`plan_only` 两道门、执行器前置门**共用** `tools.extra_workspace_roots`（operator 已授权的目录不再被误报为"工作区外"）。
3. **被拒的计划哪条路都执行不了**：`PlanRunner.run` 起始前置门——越界项 → 不 arm、不跑、disarm 持久化、`report.stopped` 返回；`/plan run` 打印原因；前端自动派发/boot 恢复同样被这道门拦住（boot 的"续跑"提示与实际不跑存在轻微文案差，见 §8 已知边界）。
4. **auto-run 只在干净完成时触发**：前端只在 `turn.finished` 且 `status === "completed"` 时才派发 `/plan run`（aborted / error / timeout 不派发；dismiss 已由 R08 排除；approve 才置 pending）。

## 2. 契约与复用

### 2.1 roots 管线（一条链，三处消费）

```
cli/装配根（已有）→ AgentLoop(extra_workspace_roots=...)   [已接收，:253]
   → self.extra_workspace_roots                            [本批新增：存为属性]
   ├─ tool_context(...) → ToolContext.extra_workspace_roots  [R02]
   ├─ plan_only 两道门 extra_roots=loop.extra_workspace_roots
   └─ PlanRunner 前置门 extra_roots=getattr(loop, "extra_workspace_roots", ())
```
- 复用 `outside_workspace_paths(texts, workspace, *, extra_roots=())`（`plan_runner.py:104-133`，已支持 roots——缺的只是调用方没传）。
- 不新造路径解析；不引入 `external_directory` ask（Q6）。

### 2.2 `present_plan` 预校验（ask 之前，顺序固定）

```python
# 1) 内容/plan 文本：硬拒（模型可当场改）
texts = [plan] + [content for content, _, _ in items]
offenders = outside_workspace_paths(
    texts, str(getattr(ctx, "workspace", "") or "."),
    extra_roots=tuple(getattr(ctx, "extra_workspace_roots", ())),
)
if offenders:
    return ToolResult(success=False, output=_OUT_OF_WORKSPACE.format(paths=...),
                      error="workspace_paths")
# 2) verify：警告，不阻断（用户拍板）
verify_texts = [verify for _, verify, _ in items if verify]
warnings = outside_workspace_paths(verify_texts, workspace, extra_roots=roots)
data = {"items": [...], "warnings": warnings}   # warnings 可为空列表
```

- 拒绝文案复用 `_outside_workspace_message` 的语义（"文件工具无法访问工作区外路径；改为工作区内路径"），但因不再 from plan_runner import 私有函数，案文放 `present_plan_tool` 内或把 helper 提升为公共名（实现期二选一，取最小：先在同文件写等价文案并加注释指向源头）。
- 警告文案（前端显示）：`verify 引用了工作区外路径：<paths>（命令由 shell 执行，仅提示）`。

### 2.3 执行器前置门（`PlanRunner.run` 顶部，arm 之前）

```python
task = getattr(session, "task", None)
if task is not None:
    workspace = str(getattr(self._loop, "workspace", "") or ".")
    roots = tuple(getattr(self._loop, "extra_workspace_roots", ()) or ())
    offenders = outside_workspace_paths(
        [item.content for item in task.open_items()], workspace, extra_roots=roots
    )
    if offenders:
        report = self.new_report()
        report.stopped = _outside_workspace_message(offenders)
        # 被拒的计划不 arm、不 echo、不留可续跑态
        if getattr(task, "armed", False):
            task.armed = False
        self._persist(session)
        return report
    task.armed = True
    task.armed_profile = "plan"
    ...（原 arm 块）
```

- 覆盖四个入口：`/plan run`（命令）、前端自动派发（走 `/plan run`）、boot 恢复（`_launch_armed_run` → `PlanRunner.run`）、任何直接调用。
- `report.stopped` 由 `/plan run` 分支打印（§2.4）；boot 路径不打印（见 §8 已知边界）。
- 与 W3 的 R06 协同：本门不发射（未发生状态变化时）；disarm 若发生了 armed→false 的变化，经 `_emit_task(observer, task)`（实现期对齐 R06 的 finally 语义，避免重复事件）。

### 2.4 `/plan run` 展示 stopped（`commands.py` run 分支）

```python
report = await PlanRunner(loop).run(session, console, on_delta=console.delta, observer=observer)
if report.stopped:
    console.error(f"[plan] {report.stopped}")
```
- 现状：run 分支忽略返回值（`:481-484`）；plan_only 的 stopped 已打印（`:534-536`），补齐 run 侧。

### 2.5 R11 前端状态门（纯函数，可单测）

```ts
/** 只有干净完成的回合才值得派发自动执行：aborted/error/timeout 都不算。 */
export function shouldDispatchPlanRun(pending: boolean, status: unknown): boolean {
  return pending && status === "completed"
}
```
- 使用点：`session.tsx` 的 `turn.finished` 分支（`:485-508`）——`pendingPlanRun` 归零逻辑保持；只有 `shouldDispatchPlanRun(...)` 为真才 `dispatch("/plan run")`；否则按既有逻辑处理排队行。
- `status` 来源：正常回合= bridge `to_wire(TurnFinished)`；命令回合= `_notify_terminal_turn`（两者都有 `status` 字段，零后端改动）。

## 3. R02 · 详设小结与依据

- **根因**（06 底稿 C05）：两道 `outside_workspace_paths` 不传 roots；gate #2 在 approve/arm 之后且只查 `content`；`present_plan` 完全不查。→ 三个消费点一次修齐（§2.1-2.4）。
- **verify 的选择**（用户拍板）：verify 由 **shell** 执行，与文件工具的"可达性"前提不同；硬拒会误伤 `/tmp`、`mktemp` 等合法用法 → 只标注。
- **执行器门的位置选择**：08 原设"前端看 `planRunEligible` 字段"；本稿改为执行器门——理由：(a) 前端字段只拦 UI 派发，拦不住 boot/手动；(b) 执行器门把"被拒的计划不得运行"变成**结构性保证**；(c) 少一个 wire 字段。

---

## 4. R11 · 详设小结与依据

- **根因**（08 C04/C05 交集）：`pendingPlanRun` 只看"答案是不是 approve"，不看回合怎么结束；abort/error/timeout 之后仍会派发（F-55 的前端半边）。
- 状态门 + 执行器门（§2.3）双保险：前者不派发脏回合，后者被拒计划即便被派发也不运行。
