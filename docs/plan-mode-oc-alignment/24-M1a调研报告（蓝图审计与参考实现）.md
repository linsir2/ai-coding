## 1. 今天的真实形状（先自己量一遍）

蓝图的前提有几处与现状不符。以下是**实测**（不是推断）：

### 1.1 三个 gate，不是一个

| # | 位置 | 它是什么 | 谁的规则对它生效 |
|---|---|---|---|
| G1 | `cli.py:112` → `agent_loop.py:384` | 执行期的主 gate | 规则层若接在这里，全生效 |
| G2 | `builder.py:164` | **只**当 sandbox 的 grantor 用 | 规则层若不进它，sandbox 看不到规则 |
| G3 | `subagent.py:503` | 子代理自己的 gate | 子代理**不继承**父的规则层（除非专门做） |

⇒ 蓝图的「唯一写入口、一处灌回」（§4.6）在三个 gate 的前提下不成立。

### 1.2 三套谓词，不是两套

| 谓词 | 位置 | 问什么 | 后果 |
|---|---|---|---|
| `plan_only` | `base.py:151-157`；裁剪于 `agent_loop.py:2386-2387` | 这工具属于计划姿态吗 | 计划外**不广告**它（不是拒绝） |
| `mutates_world` | `base.py:150`；裁剪于 `:2388-2389`，拒执行于 `dispatch.py:319-324` | 这工具改世界吗 | 裁掉 **或** 结构拒绝 |
| gate 档位表 | `permission_gate.py:404-572` | 这个调用危险吗 | allow / warn / deny |

蓝图的 I1 说「目录裁剪与执行判定问同一个问题」——今天它们**本来就不是同一个问题**，蓝图要把三者并成一个，需要**三个查询**不是一个 `wholly_disabled`。

### 1.3 两条进 shell 的路，其中一条绕过 gate

| 路 | 位置 | 过 gate？ |
|---|---|---|
| 工具调用 | `dispatch.py` | ✅ 过 |
| **验收/verify 命令** | `core/acceptance.py:57` 只查 `bash_denied`；`agent_loop.py:1746-1750` 明说「the proof commands are shell and **bypass the dispatch gate**」 | ❌ **不过** |

⇒ 规则文件的 `bash * deny` **拦不住**验收命令。蓝图 §5.2 的数据流图只有一条进 shell 的路。

### 1.4 三个名字空间

| 空间 | 谁在用 | 例 |
|---|---|---|
| **小写** | `_allow_tools` / `_warn_tools` / `grant_key`（`check()` 第 1 行 `name = tool_name.lower()`，`permission_gate.py:478`） | `subagent` |
| **原样** | `_denied_tools` / `_allowed_tools` / trusted server 前缀（`:500`、`:551`、`:564`） | `subAgent`（`subagent_tool.py:137-138`） |
| **复合** | MCP 承载 | `fs__write_file` |

⇒ 真实工具名是 `subAgent`（驼峰），gate 执行时用 `subagent`（小写）。蓝图 §4.3 的目录查询用 `permission_name()`（**原样**），与执行查询**不同字符串** ⇒ I1 按构造就破。

### 1.5 名单：22 + 3 = 25（蓝图写 21 + 3 = 24）

`_allow_tools` 实测 22 个：`read glob grep webfetch websearch todo_write skill subagent memory_search history_search job_list job_kill job_output subagent_list memory_write ask_user checkpoint_write present_plan finish_research start_goal update_goal mcp_call`。
`_warn_tools` = `write edit bash`（3 个）。

⇒ 正确的锚点是 **「规则条数 == 名单大小」**（蓝图 §2 E3 自己写了这个锚点！）——**从活名单 import，不要手抄**。手抄就必然漂移。

### 1.6 skill deny 有三张脸

`skills/policy.py:1-8` 写明：「A deny is an operator boundary and must mean the same thing at every judge: the gate, the catalog, and the mention block.」
- gate：`permission_gate.py:517-534`（且**只**判 `action == "read"`）
- 目录：`agent_loop.py:2334-2339`
- mention 块：`request_assembly.py:490-495`

⇒ 蓝图把 skill policy 留在「硬拒层」（对），但 §4.3 的 `_keeps` 只查**规则层** ⇒ 被 deny 的 skill 会**重新被广告出去**（R1 的具体后果）。

## 2. 蓝图审计

### 2.1 阻断级（照抄就会出事）

**R1 · 目录裁剪的设计前提是错的**
蓝图 §4.3 写「今天（:369）`self._readonly_schemas = ...`」并提议换成 init 时算的 `_tool_schemas` / `_readonly_schemas`。今天**没有**这两个属性，目录是每请求算的。两个后果：
1. **丢掉 `plan_only` 裁剪**（蓝图的新属性里没有它）⇒ build 模式会广告 `present_plan` / `finish_research`。
2. **丢掉按姿态缓存**（`agent_loop.py:373` / `:2400-2404`）⇒ 请求不再 byte-stable，且会话级规则改不动目录。
3. **skill deny 的目录那张脸会破**（§1.6）。

**R2 · `Decision` 不能变 dataclass**
`permission_gate.py:50-73` 的手写 `__eq__` 让 `decision == PermissionDecision.ALLOW` 成立（86 处断言）；dataclass 的 `__eq__` 对非 dataclass 返回 `NotImplemented` ⇒ 全部变 False；`eq=True` 还会把 `__hash__` 设成 `None` ⇒ 不可哈希（今天可哈希）。
⇒ 修法：保留自定义类，加 `action` / `resource` 两个属性。

**R3 · 会话层（L4）落在错的对象上**
蓝图 §4.2.6 **说对了一半**：L1–L3 由 `from_config` 装配，而 `from_config` 被三处调用（`cli.py:112`、`builder.py:164`、`subagent.py:503`）⇒ **L1–L3 三个 gate 都拿得到**，这部分蓝图是对的。
问题在 **L4（会话层）**：
- L4 是**每会话**的，但三个 gate 里只有 G1 属于当前会话；G2（sandbox grantor）与 G3（子代理）该不该看见会话规则，蓝图没定。
- 蓝图 §4.6 说「落在 `AgentLoop.resume_turn`（`agent_loop.py:529`）附近，**一处**」——但 `resume_turn` 只在 `handlers.py:610`（boot 续跑）与 `:731`（session.resume）被调；**切换/打开会话走的是 `handlers.py:410-412` 的 `session_load`（`world.sessions.load`）**，REPL 的 `/session` 走 `commands.py:801` ⇒ 「一处灌回」不成立，至少 3-4 处，或者需要一个今天不存在的汇合点。

**R4 · 两个查询用不同的 action 字符串**
执行用小写、目录用原样（§1.4）⇒ `subagent * deny` 会在执行期拒、但**不会**把工具从目录里剪掉 ⇒ I1 破。
蓝图通篇**没有写归一化契约**——这是 R1/R4 的共同根因。

## 3. 参考实现

> 本地已有上游源码可查：`/tmp/opencode/oc-config.ts`（opencode v2 配置）、`gemini-policy.md`（Gemini CLI 策略引擎文档）、`c.json`（Codex 树）、`g.json`（Gemini 树）。仓库自带的前期底稿：`07-重审-opencode事实底稿.md`、`05-dsh事实底稿.md`。

### 3.1 opencode v2

- **规则格式**：`{action, resource, effect}` 数组；`action` 是**开放字符串**（插件可加）；`effect ∈ {allow, deny, ask}`。
- **文件**：全局 `~/.config/opencode/opencode.json`；项目 `<dir>/opencode.json`（从 cwd 向上找）+ `<dir>/.opencode/`；agent 级 `agents.<id>.permissions`。
- **匹配**：`util/wildcard.ts` —— `*` 跨 `/`、`?` 匹配一字符、其余字面量；末尾 `" .*"` 特例让 `git status *` 也匹配 `git status`。
- **求值**：`permission.ts:87-97` —— `rulesets.flat().findLast(匹配)`，**没有匹配就是 ask**（fail-closed）。
- **层序**：base → 全局配置 → 项目配置 → agent → session → saved（**只在最后**，且**只存 allow**）→ **policy 层（只能否决）**。
  ⇒ **saved 永远打不开配置的 deny**；**项目配置压全局配置**（对 `permissions`），而 **policy 层反过来：全局压项目**。
- **多资源**：任一资源 deny ⇒ 整个操作 deny；否则任一 ask ⇒ ask。
- **bash**：**真 shell 解析**（tree-sitter），**按段**切，每段是一个独立 resource；匹配是整段全文通配。
- **plan 是一个 agent**（4 条规则：`question * allow`、`edit * deny`、`edit <home>/.opencode/plan/* allow`、`external_directory <home>/.opencode/plan/* allow`）⇒ **plan 的 shell 完全不拦**（软只读）。
- **工具不可见 ≠ 调用被拒**：`whollyDisabled` 要求「最后一条匹配规则的 resource 是 `*` 且 effect 是 deny」。所以 `edit * deny` + `edit <plan>/* allow` ⇒ 工具**仍然可见**，拒绝发生在调用时（模型能读到可读的原因）。

### 3.2 dsh（DeepSeek-Harness）

- **没有规则语言**，是三条独立轴：sandbox 模式（`read-only` / `workspace-write` / `danger-full-access`，闭集）、approval 策略（`ask` / `never`）、预设（把前两者打包成一个名字：`read-only` = {sandbox: read-only, approval: ask}）。
- **批准不是授权**：plan 评审走 user-questions，不走 approval；批准只把 `plan/mode` 翻成 false，**sandbox/approval 一个字都不改**。
- **plan 评审不是审批**：它要「精确产物 + 自由文本 + 工具调用」三样，所以 `approval=never` 拦不住它。
- **升级阶梯**：`read-only → workspace-write → danger-full-access`，**只往宽走**，且 `sandbox_permissions` 与 `justification` **必须同时出现**。
- **子代理继承**：只继承父的**显式** sandbox override；**approval 被钉死为 `never`**（子代理不许向人求助）；`fork` 继承 plan，`spawn` 不继承。
- **软层是真软**：dsh 自己说 plan 是 guidance，`workspace-write` 下能写、能 spawn、能用 MCP 绕。

### 3.3 Gemini CLI 的策略引擎

- **层 = 5 个 tier**（Default 1 / Extension 2 / Workspace 3 / User 4 / Admin 5），**最终优先级 = `tier_base + toml_priority/1000`** ⇒ tier 永远压过 tier，toml priority 只在层内排序。
- **用户层内部还有一条硬编码的带序**（`plan.toml` 头注释）：4.95 UI 里勾的「Always Allow」 > 4.9 MCP 服务器黑名单 > 4.4 `--exclude-tools` > 4.3 `--allowed-tools` > 4.2 trust 的 MCP > 4.1 MCP 白名单；toml 那边 10 写工具默认 ask / 40 plan catch-all deny / 50 只读工具与 plan 显式 allow / 70 模式切换覆盖 / 999 yolo 全放。
  ⇒ **两个轴**：tier 轴 + 用户层内的固定带序。
- **规则字段**：`toolName`（可数组、可用 `*` / `mcp_server_*` / `mcp_*_tool`）、`subagent`（谁在调）、`mcpName`（推荐，别用 FQN 通配）、`toolAnnotations`、`argsPattern`（对**参数的稳定 JSON**做正则）、`commandPrefix`、`commandRegex`、`decision ∈ {allow, deny, ask_user}`、`priority 0-999`、`denyMessage`、`modes`（空 = 恒生效）、`interactive`、`allowRedirection`。
- **deny 的两种语义**：**不带 `argsPattern` 的全局 deny ⇒ 工具从模型记忆里彻底消失**；带 `argsPattern` 的作用域 deny ⇒ 调用时被拒。
- **模式感知的授权**：`plan < default < autoEdit < yolo`。**在 plan 里做的授权适用于所有模式**（那是对工具的全局信任声明）；**在 default 里做的授权不适用于 plan**。
- **plan 模式本身就是一个 policy tier**（`plan.toml`）：catch-all deny（40）+ 只读工具 allow（50）+ 只允许往 plans 目录写 .md（70）。

### 3.4 Claude Code

- **规则格式**：`Tool` 或 `Tool(specifier)`，放在 `permissions.allow` / `ask` / `deny` 三个数组里；**三个数组跨文件合并**（不是取一个）。
- **求值顺序：deny → ask → allow，首个匹配胜出，**与具体程度无关**（`Bash(aws *)` 的 deny 压住 `Bash(aws s3 ls)` 的 allow）。
- **跨作用域同理**：「If a tool is denied at any level, no other level can allow it.」
- **Bash 匹配**：整条命令文本；`*` 匹配含空格的任意文本；`&&` `||` `;` `|` 复合命令**按子命令拆**，**每个子命令独立匹配**；前置 wrapper（`timeout`/`nice`/`nohup`…）**先剥掉再匹配**；`find -exec/-delete` 不能用前缀批准；重定向的目标按文件规则判。
- **Read/Edit 用 gitignore 语法**，四种锚点（`//` 根、`~/` 家、`/` 相对**设置来源目录**、无锚点相对 cwd）；符号链接：allow 要求**请求路径与解析路径都匹配**，deny 命中任一即拒。
- **两种 deny 语义**：裸工具名 ⇒ **工具从 Claude 的上下文里消失**；带作用域 ⇒ 工具还在、调用被拒。
- **授权持久化**：「don't ask again」写进**仓库根**的 `.claude/settings.local.json`；**Bash/WebFetch 永久，文件修改不持久**（只到本会话结束）；一条复合命令最多存 5 条规则。
- **`PreToolUse` hook 只能收紧不能放松**（exit 2 拦在权限规则之前；hook 返回 allow 也不能压过 deny/ask）。
- **模式**：`default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`；`dontAsk` 是**自动拒绝**不是自动允许。

| deny 语义 | 调用时拒；`resource=="*"`+deny 才隐藏工具 | 不筛工具，sandbox 拒文件效果 | **裸名 deny ⇒ 工具消失** | **裸名 deny ⇒ 工具消失** | `wholly_disabled`（与 oc 同） | 落后于 Gemini/Claude |
| 授权持久化 | 项目级、durable、只存 allow | **没有授权存储** | 用户层 4.95，**带模式集** | 仓库 `.claude/settings.local.json` | `grants.json`，**路径级**（`edit:<file>`） | **领先**：路径级授权四家独一份 |
| 命令匹配 | **真 shell 解析，按段** | 只管文件效果 | prefix / 正则 / 参数正则 | 按子命令拆 + 剥 wrapper | **整条原始字符串** | **落后最大**：我们已有 `shell_parse.command_views()`，几乎白捡 |
| 模式交互 | plan 是 agent，不是模式 | plan 与 sandbox/approval 正交 | 规则带 `modes`，授权带**宽松阶梯** | 6 个模式 | **规则语言里没有模式** | **落后**：我们已有 plan/build + `/readonly` |
| 子代理继承 | 继承 session 权限 | 只继承显式 override，**approval 钉死 never** | 子代理名可当 toolName deny | `Agent(X)` deny | 推给 M1b | 可抄 dsh 的「子代理不许向人求助」 |

## 4. 要偷的三个 / 要避的三个

### 4.1 该偷

**L1 · 把「策略」与「许可」分成两层，策略层只能否决，且全局压项目**
*来源*：oc 的 `config/plugin/policy.ts:19-33`（「Authored documents reverse so user-global policy outranks repository policy」）+ Gemini 的 Admin(5) > User(4) > Workspace(3)。
*我们要做的*：把 `mcp.servers[].permissions.deny` 与 `ai.skill_permissions` 从「代码里的硬拒」升级成**可配置的策略层**（deny-only、全局压项目、可以有 managed/org 层）；`bash_redlines` 留在**代码层**（它是安全属性不是策略）。
*为什么*：蓝图的层序是「项目文件 > 用户文件」（同 oc 的 `permissions`），于是**一个签进仓库的 `permissions.yaml` 可以把操作者的全局 `edit:*.env deny` 变成 allow** ⇒ 克隆即提权。今天没有规则文件所以无害，**上线那一刻就是漏洞**。

**L2 · 把模式放进规则里，授权也带模式集（宽松阶梯）**
*来源*：Gemini 的 `modes = [...]` + `plan < default < autoEdit < yolo`；Claude Code 的 `defaultMode` / `dontAsk`。
*我们要做的*：`Rule` 加 `modes: tuple[str, ...] = ()`（空 = 恒生效）；`always` 时把「当前模式 + 所有更宽松的模式」一起存；**在宽松模式里做的授权绝不能适用于 plan / readonly**。
*为什么*：我们已经有 `plan`/`build` 两个 agent、`/readonly` 覆盖、`ctx.readonly`——「这条规则只在 build 生效」「这条规则在 readonly 下不生效」今天就表达不了，而它恰恰是用户最想要的（「计划模式别问我写文件，但平时随便」）。

**L3 · 命令按段匹配；「匹配」与「记住」分开**
*来源*：oc 的 `shell/parse.ts`（tree-sitter 分段，每段一个 resource；持久化的是另一张**元数表**推出的前缀）+ Claude Code 的复合命令拆分与 wrapper 剥离（每条子命令各存一条规则）+ Codex 对拆不动的脚本**保守退化**成一次调用。
*我们要做的*：`subject_of("bash", params)` 返回 `command_views(command)`（**一个列表**），gate 逐段独立求值，**最坏者胜**（与其余三家的 any-deny/any-ask 同）；「always」记住的是**段前缀**而不是整条原文。
*为什么*：`shell_parse.command_views()` 我们**已经有了**（tree-sitter，每条命令一个 view，含 `&&`/`;` 之后与命令替换里的），几乎是白捡。不做的话，一条 `bash: "rm -rf *"` 规则**拦不住** `cd /tmp && rm -rf x`。

### 4.2 该避

**T1 · 别让仓库文件削弱操作者的全局规则**（见 L1）。要么分「策略类（deny-only、全局压项目）」与「偏好类（allow/ask、项目压全局）」两类，要么直接抄 Claude Code：**deny 永远压 allow，跨层也一样**（这样层序对 deny 就不重要了）。**上线前必须定，不能上线后补。**

**T2 · 「工具不可见」与「调用被拒」必须由同一个谓词回答**
*来源*：Gemini「全局 deny ⇒ 工具从模型记忆里消失」；Claude Code「裸工具名 ⇒ 工具从上下文消失；作用域规则 ⇒ 工具还在、调用被拒」；oc 的 `whollyDisabled` 要求 `resource === "*"` 且 `effect === "deny"`。
*我们的暴露*：蓝图的 `wholly_disabled(action, *layers)` 只读**规则层**——硬拒层（红线、配置 deny、skill deny）对它不可见 ⇒ 红线里的 `bash * deny` 不会把 bash 从目录里拿掉（但每次调用都被拒）；而且它算在 `AgentLoop.__init__`，**执行期是每次调用**⇒ 会话规则改了之后，两个查询问的不是同一个问题（正是 I1 禁止的）。
*修法*：`wholly_disabled` 拿**和执行期同一组层**（含硬拒层），并且要么每请求重算目录，要么明说「目录只是提示、判定才是真相」，并让错误文案这么讲。

**T3 · 别把 bash 模式规则当强制边界卖**
*来源*：Claude Code 整节「What a Bash rule doesn't match」——`Bash(curl *)` 拦不住 `/usr/bin/curl`、拦不住 `sh -c 'curl …'`；`Bash(git push *)` 拦不住 `git -C . push`；它明确警告「Bash permission patterns … are fragile … 用 **sandbox** 做文件/网络强制」。oc 的 v2 文档同调：「prefer a narrow shell allowlist instead of patterns intended to recognize every dangerous command」。Codex 对拆不动的脚本保守退化。Gemini 的 `allowRedirection` **默认问**，即使规则匹配了命令。
*我们要做的*：规则文件能**收紧**不能**放松**红线；但文档与错误文案要说清「模式规则不是沙箱」，并把 `command_views` 拆不动的命令**保守当成一条不透明命令**。

## 5. 我们领先 / 落后的清单

**领先（四家都没有）**
1. **一个求值器、一组层、两次查询**（I1 的目标形态）：oc 的 `whollyDisabled` 不看 saved 也不看 policy 层；Claude Code 的「工具消失」与「调用被拒」是两条代码路；Gemini 的排除只看 policy 规则；dsh 根本不筛工具。
2. **比所有参考都细的授权粒度**：`grant_key()` 记 `edit:<file>` / `read:<dir>` / `glob:<dir>` / `mcp:<server>__<tool>`——oc 对所有文件工具只存 `*`，Claude Code **拒绝**持久化文件修改类授权。
3. **每条规则带作者写的理由**（`Rule.reason`）+ 判定结果里带 `action`/`resource`（机器可读）：oc 的 `BlockedError` 有 rules 但没有操作者写的理由，Gemini 有 `denyMessage`，Claude Code 指名规则。
4. **效果语言与判定枚举分开，只有一处映射**（`ASK → WARN`）：规则语言能单独测，不动几十处 `PermissionDecision` 断言。

**落后**
1. **规则语言里没有模式轴**，授权也没有模式集（Gemini 最可移植的一条）。
2. **没有策略层**：硬拒全在代码里，操作者的全局 deny 与仓库的 deny 分不开。
3. **没有 admin/managed 层**（Gemini Admin 5 / Claude Code managed-settings）。
4. **bash 按整条原始字符串匹配**（我们已有 `shell_parse` 却没用）。
5. **findLast 让后层 allow 压前层 deny**（跨层）；Claude Code 与 Gemini 都不允许。
6. **`wholly_disabled` 读的层与判定读的层不同**，且在 init 时算（I1 只在 t=0 成立）。
7. **saved 授权在规则语言之外** ⇒「当前生效的规则」不是全部真相，交互式授权也表达不成一条规则。
8. **没有 headless/interactive 之分**（Gemini `interactive`）：headless 的 ask 今天**自动 yes**（`AutoApproveCallback`，`approval.py:108-124`）⇒ 「ask」不是安全边界。
9. **没有「子代理不许向人求助」**（dsh 把子代理的 approval 钉死为 never）。

## 7. 需要拍板的

1. **模式轴做不做**（L2）？做 ⇒ 规则与授权都带模式集，`/readonly` 可以**变成规则**而不是今天的特判；不做 ⇒ M1a 只做「资源维度」，模式留给 M2 的 T6。

3. **「工具不可见」的语义**：跟 Gemini/Claude（裸名 deny ⇒ 工具消失）还是跟 oc（`resource=="*"`+deny 才消失）？蓝图选了 oc，但四个参考里有两个选了「消失」。
4. **验收命令要不要走规则层**？走 ⇒ 多一处执行路径的规则注入；不走 ⇒ 必须在文档里写明「规则文件不是沙箱」。
5. **子代理的规则继承**（M1b/T14）现在就要不要留口子？dsh 的做法（子代理 approval 钉死 never）很便宜。
