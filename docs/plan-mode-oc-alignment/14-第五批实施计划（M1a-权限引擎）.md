### 3.2 本批建立的新契约（后续批次必须遵守）

**C-1 · 规则语言**

```yaml
# <workspace>/permissions.yaml（项目，可提交） / ~/.config/ai-coding/permissions.yaml（用户）
rules:
  - action: edit          # 必填；支持 * 通配
    resource: "*.env"     # 必填；支持 * 与 ?，* 跨 /
    effect: deny          # 必填：allow | ask | deny
    reason: "环境变量文件不能改"   # 可选；没有就用生成的文案
```

- **顺序即优先级**：同一个 `(action, resource)` 命中多条时，**最后一条生效**（findLast）。
- `*` 匹配任意字符（**含 `/`**），`?` 匹配一个字符；**不支持 `**`**（`*` 已经跨 `/`，`**` 无意义）。
- `resource` 归一化：POSIX 相对路径，去掉 `./`，统一 `\` → `/`。
- **不支持** opencode 的 `" .*"` 结尾可选怪癖（`git status *` 能匹配 `git status`）——最小可用，不抄怪癖。
- 规则文件**坏掉时跳过并记录**，不崩、不静默（错误出现在 `/permissions` 的输出与日志里）。

**C-2 · 层序（更具体的一层先说话）**

```
具体性从高到低（先说话的一层说了算）：
  1. 会话规则          session.permissions（/permissions 命令写入）
  2. 项目本地          <workspace>/permissions.local.yaml        （gitignored，个人覆盖）
  3. 项目共享          <workspace>/permissions.yaml              （**可提交**，团队共享）
  4. 用户              ~/.config/ai-coding/permissions.yaml      （与 grants.json 同居）
  5. 既有配置翻译      config.local.yaml 的 mcp.permissions / trusted / skill_permissions
  6. BASE_RULES        内置代码：今天的档位逐条翻译
```

（`saved` 不在层序里 —— 它是 grant key 的精确匹配集合，见 C-2c。）

**层间与层内的规则**：

- **层内**：同一个 `(action, resource)` 命中多条 → **最后一条生效**（findLast）。这让 `edit * deny` + `edit .ai-coding/plan/* allow` 这种「先全禁、再开一个口子」的写法可用（M3 的 T5 要用）。
- **层间**：从最具体的层开始找，**第一个有话说（命中任何规则）的层说了算**；该层的 findLast 结果即结论。更一般的层不再参与。
- **saved 单独处理**：它是「已记住的放行」，只有 allow。规则层若判 deny → **直接拒绝，saved 救不了**（I2）；规则层若判 ask → saved 命中则升级为 allow。

> ⚠️ **为什么不是「任一层的 deny 都绝对」**：那样 `edit * deny` + `edit <plandir>/* allow` 就永远解不开口子——M3 的 T5（plan 目录）依赖这个写法。层内 findLast 是必须的。
> ⚠️ **为什么 legacy deny 不绝对**：它是最不具体的一层，所以项目/用户的显式规则可以覆盖它。这与今天不同（今天的配置 deny 在代码顺序上绝对）。**是有意的差异**：显式规则文件是操作员/团队自己的显式行为；且 deny 仍然挡住 saved。要不要更严，留给实现时的等价性金标准裁决（见 §7 的风险表）。

**规则文件的位置（三层，与本仓的配置分层同构）**：

| 层 | 路径 | 是否提交 | 依据 |
|---|---|---|---|
| 用户 | `~/.config/ai-coding/permissions.yaml` | 否 | 与 `grants.json` 同居（`config_home()`，`security/grants.py:36`）——权限是设置，不是状态 |
| 项目共享 | `<workspace>/permissions.yaml` | **是** | 与 `config.yaml` 同层（项目里可提交的那份配置）——**规则要能随仓库分发给团队** |
| 项目本地 | `<workspace>/permissions.local.yaml` | 否 | 与 `config.local.yaml` 同名法（gitignored，个人覆盖） |

> ⚠️ **为什么不放 `.ai-coding/`**：该目录被 gitignore（`.gitignore:29`，注释是 "R4a: traces and the hook plugin directory are per-workspace runtime state"）。放那里的项目级规则文件**永远无法提交**，项目层就只剩本机意义，白做。
> ⚠️ **为什么不放 `skills/` 那样的一层**：skills 的用户层在 `data_home`（`~/.local/share/ai-coding/skills`，因为 skill 库是「数据」），而权限规则是「设置」，与 `grants.json` 同居更一致。

**C-2c · saved 不是规则层**

`saved`（已记忆的放行）**不是规则层**，它是一组 **grant key**（`edit:src/foo.py` / `read:src` / `server__tool`），按**精确相等**匹配，不走通配。

理由（三条都是硬的）：

1. **粒度不能被通配吞掉**。今天的 `read:.` 表示「工作区根目录下的文件」；若把它翻译成规则 `read:*`，而 `*` 跨 `/`，它就变成「任何路径」——**读任何文件都不用再问**。这是安全倒退。
2. **`grants.json` 的格式与前端 wire 都不该动**。前端 `permissions-dialog.ts` 读的是 wire 上的 `grants: string[]`，并按 `tool:path` 解析（`grantLine`）。saved 保持字符串，前端与磁盘格式零改动。
3. **今天的粒度判定已经很对**。`grant_key()` 从 `params["path"]`/`params["pattern"]` 重算，read 按目录、edit 按文件、glob/grep 按最深静态目录、bash 永不记忆。这是 08 §4.2 T2c 定的口径，且**超越 opencode**（opencode 存工具自己传的 `save`，edit/read 是 `["*"]` = 所有路径）。

所以 saved 与规则层的关系是：**规则层先判 deny（saved 救不了）→ 判 allow → 判 ask 时才查 saved。**

**C-3 · 求值顺序（不可协商）**

```
1. bash 硬拒（gate 层）          → DENY。规则 allow 不能降级它。
2. legacy 硬拒（配置 deny 的工具）  → DENY（绝对，见 §C-2 警告框）
3. 规则层求值（层 1-6，层间更具体先说话，层内 findLast）
     ├─ 命中 deny  → DENY（saved 救不了；I2）
     ├─ 命中 allow → 工作区外？ → saved 有 key？ALLOW : WARN → 否则 ALLOW
     └─ 命中 ask   → saved 有 key？ → ALLOW : 否则 WARN
4. 没有任何一层有话说 → 兜底 ask（fail-closed）→ 同上查 saved
5. 只读 overlay                    → 独立 veto，优先于审批
6. ask → 一次 / always / reject
```

> **第 3 步里 saved 出现两次**：ask 分支（把 ask 升级为 allow）与 allow-但工作区外分支（今天的行为：已记住的读不再重复问）。两处都是「saved 只含 allow」的方向。

**C-4 · 目录裁剪与执行判定同源**

- 裁剪：`wholly_disabled(action, rules)` —— **最后一条匹配该 action 的规则**满足 `resource == "*"` 且 `effect == deny` 才剪除。整条 action 被拒才剪；被资源级规则拒的工具**留在目录里**，执行期给可读的错误（opencode 同款，本仓要的是「模型看得见自己撞了什么」）。
- 执行：`evaluate_layers(action, subject, layers)`（同一批层、同一个求值器）。
- **两者是同一个 `ruleset` 上的两个查询**，不再有第二套谓词。

**C-5 · 会话规则的写法**

`/permissions deny <action> <resource>` / `/permissions allow <action> <resource>` / `/permissions reset` 写进 `session.permissions`（会话级、不落项目、不跨会话）。`/permissions`（无参）列出**当前生效的规则全表**（按层分组）+ 出错的规则条目。

## 4. 逐项详设

### 4.1 T2 · 权限规则引擎

#### 4.1.1 数据结构

```python
# ai_coding/security/permissions.py

class Effect(enum.Enum):
    ALLOW = "allow"
    ASK = "ask"
    DENY = "deny"

@dataclass(frozen=True)
class Rule:
    action: str
    resource: str
    effect: Effect
    reason: str = ""
```

`Ruleset = Sequence[Rule]`。

#### 4.1.2 求值器（唯一）

```python
def evaluate_in_layer(action: str, subject: str, layer: Ruleset) -> Rule | None:
    """The last matching rule in ONE layer, or ``None`` if the layer is silent.

    ``None`` means "this layer has nothing to say about this call" -- the
    caller then falls through to the next, less specific layer.  That
    distinction is the whole of the layer order: a project file that
    mentions ``edit`` decides ``edit``, and a user file never gets a
    say when the project already spoke.
    """
```

命中判定：`matches(rule.action, action) and matches(rule.resource, subject)`。

```python
def matches(pattern: str, value: str) -> bool:
    """`*` matches any run of characters (crossing `/`); `?` matches one.

    Everything else in the pattern is literal.  The pattern is escaped
    first and the wildcards substituted after, so a rule written for a
    path cannot smuggle a regular expression in.
    """
```

实现要点：
- 先把 `action`/`subject`/`rule.resource` 都归一化再比。
- `matches()`：把 pattern 里除 `*`/`?` 外的字符全部 `re.escape`，再把 `*` 替成 `.*`、`?` 替成 `.`，用 `re.fullmatch` 并开 `re.DOTALL`。**`*` 自然跨 `/`**。
- 无命中 → 返回 `Rule(action, "*", Effect.ASK, "no rule matched")`。

```python
def wholly_disabled(action: str, rules: Ruleset) -> bool:
    """Whether the whole action is cut from the catalogue.

    The *last* rule matching the action decides: ``* * deny`` cuts
    everything, ``edit * deny`` followed by ``edit <plandir>/* allow``
    does not -- the tool stays visible and the refusal happens at
    dispatch, where the model can read what it hit.  (opencode does
    the same; the reason is in the docstring of opencode's tool.ts.)
    """
```

#### 4.1.3 资源（subject）是什么

```python
def subject_of(action: str, params: Mapping[str, Any]) -> str:
    """The concrete thing the call acts on — what a rule's resource matches."""
```
- `write` / `edit` / `read` → `params["path"]`（归一化）
- `glob` → `params["pattern"]`；`grep` → `params["pattern"]` 或 `params["path"]`
- `bash` → `params["command"]`
- MCP（action 含 `__`）→ action 本身（`server__tool`）
- 其他 → action 本身（`history_search` 这类没有资源语义的工具，规则只能按 action 匹配）

> 归一化只做词法（去 `./`、统一 `/`），**不做解析**：`Sandbox` 才是边界的裁决者（沿用 `grant_key` 的既有立场，`permission_gate.py:318-327`）。

对照今天的 `_allow_tools`（21 个，`permission_gate.py:402-468`）与 `_warn_tools`（3 个，`:469`）+ 未知工具 → 问（`:563-567`）：**逐条一一对应，无增无减**。

> ⚠️ 顺序陷阱：兜底 `* * ask` 必须**排在 allow 规则之前**。findLast 取最后一条命中，若兜底排在最后，`read` 会同时命中 `read * allow` 与 `* * ask` 而落到 ask —— 今天 read 是免审批的，这会变成回归。

见 **C-2b**。四条既有配置面翻译成第 5 层（最不具体）的规则。

> `skill` 的别名归一（`_skill_resolver`）仍由 gate 做：它把 `params["name"]` 解析成 canonical id 后再当 subject 求值。规则文件里写 canonical id。

#### 4.1.6 gate 的新形状

```python
def check(self, tool_name: str, params: dict[str, Any]) -> Decision:
    name = tool_name.lower()
    action = name
    subject = subject_of(action, params)

    # 1. bash hard-deny — the gate layer, above the rules.  A rule's allow
    #    never reopens a red line (C-3).
    if action == "bash":
        reason = bash_denied(str(params.get("command", "")))
        if reason:
            return Decision(PermissionDecision.DENY, f"bash command blocked: {reason}")

    # 2. rules
    effect, reason = self._evaluate(action, subject)
    if effect is Effect.DENY:
        return Decision(PermissionDecision.DENY, reason)
    if effect is Effect.ASK:
        return Decision(PermissionDecision.WARN, reason)
    # 3. allow — but a path outside the workspace is a question, not an answer
    outside = self._outside_resource_reason(action, params)
    if outside is not None:
        return Decision(PermissionDecision.WARN, outside)
    return Decision(PermissionDecision.ALLOW, "")
```

**`_evaluate`**（层间「更具体先说话」，层内 findLast；saved 是 key 集合，不在层里）：

```python
def _evaluate(self, action: str, subject: str) -> tuple[Effect, str]:
    """The one evaluation.  Two questions, in this order.

    The *layers* answer from the most specific to the least: the first
    layer with a matching rule has the last word, so a project's rules
    beat a user's and a session's rules beat both.  Within a layer the
    last matching rule wins, which is what lets one layer say "edit *
    deny" and then open a single directory again.

    The *saved* grants are not a layer -- they are a set of keys the
    operator answered "always" to, matched by equality, not by pattern
    (C-2c).  They can lift an ask, but they are only consulted after a
    layer has had its say, so a denial is never reopened (I2).
    """
    for layer in self._layers_specific_first():        # 层 1-6
        rule = evaluate_in_layer(action, subject, layer)
        if rule is None:
            continue                                    # 这一层不说话，下一层
        if rule.effect is Effect.DENY:
            return rule.effect, rule.reason or f"denied by rule: {action} {rule.resource}"
        if rule.effect is Effect.ASK:
            if self._remembered(action, params):
                return Effect.ALLOW, ""
            return rule.effect, rule.reason or f"{action} {rule.resource} requires confirmation"
        # allow
        outside = self._outside_resource_reason(action, params)
        if outside is not None:
            if self._remembered(action, params):
                return Effect.ALLOW, ""                # 今天的行为：已记住的读不再重复问
            return Effect.ASK, outside
        return Effect.ALLOW, ""
    # 没有任何一层有话说 —— 兜底就是 ask（fail-closed）
    if self._remembered(action, params):
        return Effect.ALLOW, ""
    return Effect.ASK, f"no rule matched {action}"
```

**顺序说明**：规则层先判（deny 立即返回，saved 根本没被查）→ ask 分支查 saved（把 ask 升级为 allow）→ allow 分支仍要走工作区外检查（但已记住的不再重复问，与今天一致）。**I2 由结构保证，不靠代码顺序。**

**bash 的处置**：base 里 `bash * ask` → 落到 ASK → WARN（与今天的 bash 恒为 WARN 一致）。用户规则可以写 `bash "ls *" allow` 让某些命令免问 —— **这是用户自己的显式配置，红线层仍在上面**。`always` 按钮对 bash 仍不出现（`_NEVER_REMEMBERED` 的立场：bash 的 always 等于对所有未来命令的 always）。

#### 4.1.7 saved grants：不改

**结论：saved 这一层本批一个字都不改。**

- 磁盘格式：`~/.config/ai-coding/grants.json` 的 `{"version": 1, "workspaces": {path: [key...]}}` **不变**。
- wire 格式：`handlers.py:907` 的 `"grants": list(gate.grants())`（`string[]`）**不变**。
- 前端 `permissions-dialog.ts` 的 `grantLine()`（按 `tool:path` 解析）**不变**。
- 匹配方式：`grant_key(name, params)` 算出 key，再看它在不在集合里 —— **精确相等，不走通配**（理由见 C-2c）。

本批唯一要动的是**它被查的时机**：今天在规则表之前查（`permission_gate.py:490`），本批挪到规则层之后（deny 不能被它救 → I2），并且在 allow-但工作区外这一支也查它（与今天一致）。

**T2c 的「always 保存实际 (action,resource)」已由 `grant_key()` 满足**，本批只是把它钉进测试：

| 工具 | grant key | 理由 |
|---|---|---|
| `read` | `read:<目录>` | 按目录记：记单文件会让每个兄弟文件都再问一次 |

#### 4.1.8 裁剪谓词与 dispatch 谓词同源

`agent_loop.py:369` 今天用 `not tool.mutates_world` 裁只读面，`dispatch.py:323` 用 `ctx.readonly and tool.mutates_world` 拒绝。**两处已经是同一个布尔，但与规则引擎是两套体系。**

本批的做法：

```python
# security/permissions.py
def catalogue_keeps(action: str, rules: Ruleset) -> bool:
    """Whether the tool stays in the catalogue the model sees."""
    return not wholly_disabled(action, rules)
```

- **规则层**的裁剪改用 `catalogue_keeps(action, rules)`。
- **只读 overlay** 仍然是独立的 veto（`ctx.readonly` + `mutates_world`），但它的裁剪与拒绝也走同一个判定函数：

```python
def decide(action, subject, rules, *, readonly: bool, mutates_world: bool) -> tuple[Effect, str]:
    """The one predicate: what happens to this call, and why.

    Both the catalogue's decision to hide a tool and the dispatcher's
    decision to refuse one ask this, with the same inputs — so the two
    can never drift apart (I1).
    """
    effect, reason = evaluate_with_layers(action, subject, rules)
    if readonly and mutates_world:
        return Effect.DENY, "this session is read-only"
    return effect, reason
```

只读 overlay 的优先级：**在规则之后、审批之前**（沿用今天的 `dispatch.py:323` 位置：只读拒绝在 gate 之前）。所以顺序是：

#### 4.2.2 `permission.evaluate` hook

```python
# ai_coding/core/hooks.py
PERMISSION_EVALUATE = "permission.evaluate"
# CAPABILITIES[HookPoint.PERMISSION_EVALUATE] = frozenset({"observe", "block"})
```

**位置**：`dispatch._decide` 里，gate 判定之后、审批之前。

```
verdict = gate.check(...)          # 规则求值的结论
if verdict is DENY → 拒绝（hook 不触发，deny 是终局）
hook = await run_hooks(PERMISSION_EVALUATE, call, ctx, view)
if hook blocks → 拒绝（hook 的理由）
if verdict is WARN → 审批
```

**hook 只能收紧，不能放宽**：
- 能力集只有 `observe` + `block`（**没有 `rewrite`**）—— 不能把 DENY 变成 ALLOW，也不能把 ASK 变成 ALLOW。
- deny 短路在 hook 之前 → hook 对已 deny 的调用不触发。

> 两条对照：opencode 的 `permission.evaluate` hook 在 deny 短路**之后**触发（`permission.ts:175` vs `:179`），所以它放宽不了 deny；dsh 的 `ToolGuard` 更严 —— 「守卫没有 allow 结果，所以 listener 顺序不能把拒绝变回允许」（`core/tools/src/index.ts:724-732`）。本批取 dsh 的严格版：**hook 的能力集里没有 allow 语义**。

**payload**：`{action, resource, subject, effect, tool, params}`。

#### 4.2.3 合并顺序与 deny 短路（验收锚点）

- 层序 C-2 生效：会话规则在最具体的一层；agent 规则层本批空（M1b 补上时插在会话与项目之间）。

- **saved allow 不能压过 deny**（I2）。
- **hook 的 veto 在 dispatch 前生效**。

```
一次工具调用
   │
   ├─ dispatch._prepare ──► gate.check(action, params)
   │                          │
   │                          ├─ bash 红线（gate 层）        → DENY
   │                          ├─ subject_of(action, params)
   │                          ├─ 层间求值（会话→项目本地→项目→用户→legacy→base）

   │                          │     └─ 该层命中 ask  → saved 命中？→ ALLOW : WARN
   │                          ├─ 兜底（没有一层有话说）→ ASK
   │                          └─ allow → 工作区外？ → WARN / ALLOW
   │
   ├─ dispatch._decide
   │     ├─ readonly veto（mutates_world）→ DENY（不消耗审批）
   │     ├─ gate verdict = DENY → 拒绝
   │     ├─ permission.evaluate hook → block？ → 拒绝（hook 的理由）
   │     ├─ gate verdict = WARN → _ask
   │     │     ├─ once   → allow_once（会话内，不落盘）→ 执行
   │     │     ├─ always → grant_rule() → 写入 saved 层 → 执行
   │     │     ├─ reject → 附言进 inbox → 拒绝（下一请求可见）
   │     │     └─ stop   → 结束回合
   │     └─ ALLOW → 执行
   │
   └─ 工具目录裁剪（agent_loop 建只读面时）
         └─ catalogue_keeps(action, layers) ∧ ¬(readonly ∧ mutates_world)
              ← 与上面同源：同一批层、同一个求值器
```

## 10. 调研结论：设计稿与实证的冲突（本批据此修正 08）

> 三处冲突全部经源码验证。08 是机制设计权威稿，但**事实层以源码为准**；本批只修正事实层，不改 08 的机制取向。

| # | 08 的写法 | 源码实证 | 本批的处理 |
|---|---|---|---|
| **①** | T2c「`always` 保存**实际** `(action,resource)`（不是工具传入的 `save`）」被列为 **parity** 项 | opencode 存的**就是** `save`：`saved.add({action, resources: existing.request.save})`（`permission.ts:299-305`）；edit/read 的 save 是 `["*"]` = 所有路径 | **定性改为「超越 opencode 的主动改进」**，不进 parity 账。实现保留 08 的口径（§8.1-1）。 |
| **②** | T2b/T2c 的 deny 优先级只说「deny 必须先于 saved」（C12） | opencode 的 deny 短路在 hook **之前**（`permission.ts:175` vs `:179`）→ **hook 放宽不了 deny**；dsh 的 `ToolGuard` 更严：「守卫没有 allow 结果，所以 listener 顺序不能把拒绝变回允许」（`core/tools/src/index.ts:724-732`） | **写进契约 C-3 与 §4.2.2**：hook 能力集只有 {observe, block}，deny 短路在 hook 之前。 |
| **③** | T2「新增 base `* * allow`」 | 今天 read/glob/grep 是**免审批**的（`_allow_tools`），若 base 改成 `* * allow` 打底 + `external_directory ask`，会**改变** read 的工作区外行为 | **拍板「base = 今天的档位逐条翻译」**：base 用 `* * ask` 兜底（未知工具仍 fail-closed），逐条翻译 21 个 allow + 3 个 ask。零行为变更。 |

**dsh 的两条相关发现**（05 底稿未覆盖，本次源码验证）：

| # | 发现 | 对本批的意义 |
|---|---|---|
| 1 | dsh **没有** `{action,resource,effect}` 规则表，也没有 always-allow 记忆（`user-approval/README.md:154` 明写 "no `allow-always`, remembered rule, revocation, or grant store"） | **T2/T2c 的规则引擎是纯自研**，不能指望从 dsh 抄。dsh 值得抄的只有**扩展点形状**（单调守卫、`never` 在 service 内部决定）→ 已落进 §4.2.2 的 hook 纪律。 |
| 2 | dsh 的 `never` 在 service **内部**决定，不在 listener 里（`user-approval/src/index.ts:267-275` 的注释：后注册的 `prepend: true` listener 会插到 gate 前面） | 提醒本批：**deny 短路与 headless fail-closed 必须写在求值器内部，不能做成可被绕过的插件**。本批的求值器就是那个内部。 |

**opencode 的可抄清单（本批用到）**：`{action,resource,effect}` + `findLast` + 通配 + 默认 ask（`permission.ts:87-97`、`util/wildcard.ts:3-13`）；deny 短路（`:165-189`）；三层合并 agent→session→saved；agent 缺失 → 全 deny（fail-closed，`:161-162`）；`wholly_disabled` 只在「末条匹配该 action 的规则是 `resource=="*"` 且 `effect=="deny`」时成立（`tool.ts:292-295`）；强制点在叶子工具而不是注册表；同一谓词复用到 skill/MCP/subagent 列表。

## 12. M 序列的轮次划分（全景）

```
M1a（本批）权限引擎链    T2 → T2b → T2c       ← 本稿
M1b        agent 承载链   T1 → T1b, T1 → T10
M2         姿态与出口     T3 + T4 + T6
M3         边界与评审     T5 + T8 + T9 + T11
M4         UX 与收口      T7 + T12 + T13 + T14
```

**为什么 T2 链在前**（而不是得分更高的 T1 链）：

1. **它是地基**：M2 的 T6、M3 的 T5/T8/T9 全是「写规则」。规则语言晚定，M2/M3 全部返工。
2. **它是消费者依赖的上游**：T1 的 `agent.permissions` 用规则类型；裁剪谓词要跟 dispatch 同源，而 dispatch 的规则层就是本批建的。
3. **它是唯一有行为破坏性的一项**：改的是「每一次工具调用怎么判」。单独一轮 → 爆炸半径可控，出事能定位。
4. **它能纯单测钉死**：裁剪谓词 = dispatch 谓词 / deny 不可降级 / headless fail-closed。不需要真机、不需要前端。
5. **T1 链是纯新增，插在任何一轮都不亏**。

**M1b 的范围预告**（不在本稿）：T1 agent 表（`domain/agents.py` + `.ai-coding/agents/*.md` 发现 + 内置 build/plan/general/explore）、T1b 消息级归属（`agent-switched` + assistant.agent + `agent_history`）、T10 durable pending（`pending_posture` 落盘 + 四态 `committed/queued/cancelled/noop`）。

> ⚠️ T10 在 M1b 里要**重新定性**：opencode **没有** durable pending（pending 是内存 `Map`，`permission.asked/replied` 是 ephemeral 事件）。它的跨重启答案是 **durable 执行 claim（`time_suspended`）+ `resume_attempts` 预算 + at-least-once 重放 + 未结算 assistant 边界结算**。08 的 T10 口径（`pending_posture` durable 落盘）是**自研**，不是 parity —— 这一点在 M1b 开工时要再确认一次。
