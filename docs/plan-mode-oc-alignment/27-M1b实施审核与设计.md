## 1. 必须修订的 6 处

### P1（阻断 · 分层违规）`domain/agents.py` 不能持有 `rules()`

**方案原文**：§3.2 把 `AgentCatalog.rules(id) -> Ruleset` 放进 `domain/agents.py`，
并说「`rules()` 用 `security.permissions.rules_from_dicts` 解析」。

**核验证据**（`grep -rn "^from ai_coding" ai_coding/domain/*.py`）：
只有 `turn_digest.py` 引用 `domain.loop` / `domain.message` / `domain.task`；
`subagent.py` 的 `Rule` 是 **TYPE_CHECKING-only**（它只出现在类型注解里）。

**问题**：`AgentCatalog.rules()` 要在**运行时调用** `rules_from_dicts` ⇒ `domain → security` 的
**运行时 import**。这是本仓 `domain/` 第一次 import 外部模块，直接违反
`docs/architecture.md` 的「`domain` 不被任何层反向 import / `domain` 零业务依赖」。

**修订（拍板 Q1=C；采纳本仓既有先例，不新造层）**：会话层规则就是**同一个形状**——
`SessionData.permissions` 存**原始行**，`core/agent_loop.py::_session_rules()`（`:1628-1641`）
在 `core` 里用 `rules_from_dicts` 解析。agent 层照抄这个形状：

| 层 | 放什么 | 谁解析 |
|---|---|---|
| `domain/agents.py` | `PLAN_AGENT_ID`、`is_plan_agent()`、`AgentSpec`（`permissions` 是**原始行**元组）、`AgentCatalog`（纯映射，**无 `rules()`**） | — |
| `ai_coding/agents/registry.py` | `load_agents(roots)`（frontmatter 解析 + 校验 + 分层合并）、`builtin_catalog()` | `agents` 在上层，可 import `security` ✓ |
| `core/agent_loop.py` | `_agent_rules(session)`：命中 `AgentLoop` 内的 `{agent_id: Ruleset}` 缓存，miss 时用 `rules_from_dicts` 解析 | — |

**分层推导（这是 Q1=C 的关键，不是拍脑袋）**：

1. `domain/session.py` 要派生 `mode` ⇒ 需要 `is_plan_agent()` ⇒ 它**必须**在 `domain` 或更低
   （`domain/` 不能 import 上层）。
2. `AgentSpec` / `AgentCatalog` 是纯 dataclass，**不需要 `Rule`** ⇒ 同样能留在 `domain`。
3. 装载器要用 `rules_from_dicts` 做**整条跳过**的校验 ⇒ 需要 import `security` ⇒ 只能在 `domain` 之上。
4. ⇒ **`domain/agents.py`（契约）+ `ai_coding/agents/registry.py`（装载）**，
   这正是本仓既有的 **`domain/session.py` + `service/session_service.py`** 形状。
5. ⇒ **`core` 不 import `ai_coding/agents/`** —— 它只要 `domain.agents.AgentCatalog`
   与 `security.permissions.rules_from_dicts`。`server/world.py`（组合根）才 import 装载器。

**为什么不是 `config/agents.py`**：`config/` 的实测 import 面只有 `domain.model_config` + `paths`
+ stdlib + pydantic，`config → security` 会破另一条不变式。

**为什么不是 `core/agent_registry.py`**：`core` 在 `security` 之下/之上都可以 import，
但把「agent 文件从哪来」放进编排层会让 `core` 同时负责 IO 与编排；
`ai_coding/agents/` 与 `ai_coding/skills/` 平级，是**同一个角色的两个子系统**（技能库 / agent 表）。

### P2（阻断 · 通路缺失）命令层发出的 `AgentSwitched` 会丢

**方案原文**：§3.4 `commit_posture` 负责 `_emit(AgentSwitched(...))`。

**核验证据**：
- `agent_loop.py:331-332`：`self._base_observer = observer or NullObserver()`；
  `self.observer` 只在 `_bind_observer()`（`:1546-1579`，每回合 `_begin_turn` 调一次）里被换成
  `Braid(base=本次回合传入的 observer, trace, tool_obs)`。
- `world.py:187` 的 `_build_loop(..., observer=None, ...)` ⇒ **本进程还没跑过回合时**，
  `self.observer` 是 `NullObserver`。
- `commands.py:250`：`/readonly` 的分派 `_handle_readonly(loop, session, sessions, cmd.raw, console)`
  —— **没有 observer 形参**；`_handle_permissions`（`:217`）同样没有。
  只有 `_handle_plan`（`:246`）和 `_handle_goal` 有。

**问题**：TUI 刚起来、用户还没说过一句话就敲 `/agents build` ⇒
`commit_posture` 发的事件进 `NullObserver` ⇒ **前端永远收不到 `agent.switched`**。
`/readonly` 更彻底：它连 observer 都拿不到。

**修订**：

    # core/agent_loop.py
    def request_posture(self, session, *, agent=None, readonly=None, reason="", observer=None) -> PostureResult
    def commit_posture(self, session, *, agent, readonly, reason="", observer=None) -> None

事件走 `observer`（若给了），否则走 `self.observer`。
命令层把 `handle_input` **已经有的** `observer`（IPC 的 bridge）一路传下去：
`_handle_readonly` / `_handle_agents` / `_handle_permissions` 三个分派加 observer 形参。
`/plan` 已有 observer，改调用点即可。

### P3（阻断 · 退化路径）`at` 索引锚点会被 `/compact` 悄悄毁掉

**方案原文**：§3.5 `agent_history` 行 `{from,to,ts,reason,at}`，`at = len(session.messages)`；
§8.8「replay 在 `at` 前插入」「`at > len(messages)` 的行丢弃（`/compact` 重写消息列表后锚点失效——登记为已知边界）」。

**核验证据**（`agent_loop.py:2023-2036`）：`compact_session` 的 docstring 明写
「it forces one page and **replaces** the stored history」，实现是
`report = await self.compactor.compact_now(session, timeout=budget)`。
⇒ `/compact` **替换** `session.messages`（L1 snip 裁中间段、L4 摘要合并）。
⇒ 压缩后 `at` 不再指向同一条消息：**在范围内也会插错位置，超范围则整行丢失**。
方案把它记成「已知边界」，但它不是边界，是**静默的数据错误**（切换记录要么错位要么消失）。

**竞品对照**：OC 的切换行是**一条真消息**（`projection.ts:507` 读 `message.type === "agent-switched"`），
所以它跟消息流一起被压缩/摘要，不需要旁挂锚点。

**修订（拍板 Q3=A）**：`agent_history` 行只留 `{from,to,ts,reason}`，**删掉 `at`**，
  replay 用 **`ts`** 定位：「插在第一条 `timestamp > 切换时刻` 的消息之前」。
  - 存活性：幸存消息**保留自己的 timestamp** ⇒ 锚点在压缩后仍然成立；
  - 与 live 一致：live 的通知出现在事件到达处（回合边界），replay 的 `ts` 定位也落在同一边界；
  - 一个锚点、一个真相（`ts` 已经在行里，不需要第二个定位量）；
  - 边缘：`ts` 为空的消息（`plan_runner` 的 step seed 用 `timestamp=""`）不参与比较 ——
    它是 ephemeral 会话，不在主会话里；主会话的消息时间戳都来自 `now_utc()`。

  被否掉的另外两条：加一条 `agent-switched` 消息（OC / `08` T1b 的做法）——`replay.ts` 会
  **跳过 synthetic 的 user 消息**，得新增一套前缀约定 + 前端分支；维持 `at` ——压缩后错位/丢失。

### P4（阻断 · 方案自相矛盾）子代理默认目标：tool 解析还是 runner 解析？

**方案原文** §3.6 两句互斥：

1. 「缺省目标 `general` 由 **tool** 解析后**总是**传给 runner（不在「只在显式给值时传」上做特判）」
2. 「`agents is None`（没接表）时任何显式目标都报「agent table not available」，**缺省目标不受影响**」

**问题**：tool **不持有 catalog**（§3.6 明说「目标解析在 runner（它持有 catalog）」），
所以 tool 无从知道「有没有表」——它若总是传 `"general"`，runner 在 `agents is None` 时就分不清
「用户显式要 general」和「用户没指定」，第 2 句无法成立。

**修订（与本仓既有形状一致）**：**tool 只做透传**，把原始参数交出去；
**runner 负责解析**（它才有 catalog）：

    # tools/subagent_tool.py
    agent = params.get("agent")            # None = 用户没指定
    result = await self._runner.run(..., agent=agent)     # 透传，不解析

    # core/subagent.py
    requested = agent or (self._agents.default_subagent_id() if self._agents else None)
    if requested is None:
        → 老路径（general 行为，无 agent 层）
    target = self._agents.get(requested) if self._agents else None
    if target is None:            → SubagentResult(status="error", error="unknown agent: {id}（可用：…）")
    if target.kind != "subagent": → SubagentResult(status="error", error="primary agents cannot be spawned")

§8.5 的 RIPR 断言随之改写：「未传时 runner 收到 `None`，runner 解析为 `general`」
（原文写的是「未传时 runner 收到 general」，与第 2 句矛盾）。

### P5（次要 · 与 dsh 的可见差异）重复请求已排队目标时的四态标签

**核验**（dsh `plan-mode/src/index.ts:428-441`）：

    const target = pending?.active ?? this.loggedActive(session)
    if (active === target) return 'noop'

⇒ dsh 对「请求的目标 == 已排队的目标」返回 **`noop`**（因为 `target` 把 pending 算了进去）。
26 号方案 §3.4 的判定表用 `current = (session.agent, session.readonly)`（**不含 pending**），
于是同一情形返回 **`QUEUED`**。

**影响**：**状态完全相同**（pending 不变），只有给用户看的那句文案不同。

`evaluate("write", …, agent_layer)` ⇒ `deny * *`。**deny 方向放开、allow 方向收紧**的合并语义成立。

### 2.3 权限链：agent 层 + deny 否决（T1 的规则半边）

**层序**（`_layers` 返回 7 元组，`layer_counts` 的 names **必须**同步成 7 个）：

    base → standing → AGENT → user → project → session → policy

（D1 的理由我复核过，成立：agent 的 allow 只赢 base/standing，输给操作者的文件与 live 会话；

- **否决层**：`check()` 在硬拒层之后、规则链之前，**单独**对 agent 层求值一次
  （每个 subject 一次 `evaluate(name, subject, agent_rules, posture)`）；
  任一 subject 的 agent-alone 裁决是 DENY → 直接 DENY（带该规则的 reason）。
  这是 OC 的「deny 短路」在我们层序下的等价实现（§0.3 F24 已逐例推演）。
- **agent 的 allow/ask** 只作为普通层参与 findLast。
- **`hides()`** = `wholly_disabled(action, *chain) or wholly_disabled(action, agent_rules, posture)`。
  后半句**必须**：否则会话层的 allow 会让被 agent 整动作 deny 的工具重新出现在目录里，
  破坏「裁剪谓词 = dispatch 谓词」的不变式。

### 2.4 姿态请求：四态 + durable pending（T10）

**新 `ai_coding/domain/stance.py`**（唯一内容，08 T10 点名的文件）：

    class PostureResult(enum.Enum):
        COMMITTED = "committed"
        QUEUED = "queued"
        CANCELLED = "cancelled"
        NOOP = "noop"

**`AgentLoop.request_posture(session, *, agent=None, readonly=None, reason="", observer=None) -> PostureResult`**

判定表（`target` 取请求值，未给的轴沿用当前值；`current` = 生效态；`pending` = 已排队项）：

    turn_running:
        target == current:
            pending 存在 → 清 pending + 删 sidecar → CANCELLED
            否则 → NOOP
        pending 且 pending 的目标 == target → QUEUED（幂等，pending 不变）
        否则 → 写 pending + 写 sidecar → QUEUED
    idle:
        target == current:
            pending 存在 → 清 pending + 删 sidecar → CANCELLED
            否则 → NOOP
        否则 → commit_posture(...) + 清 pending + 删 sidecar → COMMITTED

**唯一写入口** `AgentLoop.commit_posture(session, *, agent, readonly, reason="", observer=None)`，
供三条路径共用：`request_posture` 的立即分支、`_apply_pending_posture`（回合 close / 下一回合入口）、
`/plan run` 的 finally 强写回 + boot 复位。它把 `None` 解析成当前值
（`agent = agent if agent is not None else session.agent`，readonly 同），
所以 `/readonly` 这种只给一个轴的请求即使被排队，落地也不会写出 `agent=None`。四件事，顺序固定：

1. `session.agent = agent; session.readonly = readonly;`
2. agent 变了 → `agent_history += {from, to, ts, reason}`；
3. agent 变了 → 发 `AgentSwitched(from_agent, to_agent, reason, ts)`（P2：走传入的 observer）；
4. 清 `session.pending_posture` + 删 sidecar。

**为什么 sidecar 而不是 session 字段**（拍板②）：排队发生在**回合运行中**，此时写 session 文件会跑
`TurnCloser.save → ensure_tool_pairing`，把还没写回结果的 assistant carrier 丢掉
（`service/session_service.py:103-110` 对 pending-approval 的注释就是这条已验证的教训）。
sidecar 不碰 session 文件，保存节奏不变。

**`SessionService` 新增**（与 pending-approval 同型，`session_service.py:112-146` 照抄）：

- `mark_pending_posture(session_id, payload|None)`：原子写/删 `<root>/pending-posture/<id>.json`；
  `OSError` 只吞掉（「append 失败不阻塞 turn、pending 保留」——内存里仍在，进程内照常应用）。
  （`list_sessions` 只 glob 根目录 `*.json`，子目录不可见 ✓ —— 与 `_PENDING_DIR` 同理。）
- `_read_pending_posture(session_id)`；`load()` 回填 `session.pending_posture`（与 `pending_approval` 同一行位置）。
- `delete()` 一并清掉 —— **必须放在「session 文件不存在就提前 return」之前**（`:235-238` 会提前返回，
  否则一个从未落盘的会话的 sidecar 会遗留）。
- `__init__(root, *, default_agent="build", default_readonly=False)`；`create()` 落初值。

**边界语义**：提交点是回合边界（turn close 之前 / 下一回合入口），沿用现有 `_apply_pending_posture`
的两个调用点，**不新造「pre-step」概念**（dsh 在 pre-step 提交；我们在一回合内 agent 恒定，
回合边界与 pre-step 对我们等价，且回合边界更保守）。

## 3. 数据流

### 3.1 一次 `/agents reviewer`（自定义 primary，回合空闲）

    commands._handle_agents
      → loop.request_posture(session, agent="reviewer", readonly=False, reason="/agents reviewer",
                             observer=bridge)
          target=(reviewer,False) != current=(build,False) 且 turn_running=False
          → commit_posture: session.agent="reviewer"; readonly=False
                            agent_history += {from:"build",to:"reviewer",ts,reason}
                            发 AgentSwitched → bridge → wire "agent.switched" → 前端 notice
                            pending=None; 删 sidecar
          → PostureResult.COMMITTED
      → 命令层保存 session

下一次请求：`_agent_rules` = reviewer 的规则 → `tool_context(agent_rules=…)` →
`gate.check`：agent 否决 → 目录 `hides` 同步剪掉；prompt 追加 reviewer 的 body；
`session.mode` 仍是 `"normal"`（非 plan）。

### 3.2 一次回合中的 `/plan`（排队 + 崩溃恢复）

    回合进行中：request_posture(agent="plan", readonly=True, reason="/plan")
      → target != current → pending={agent:"plan",readonly:True,reason:"/plan"}
        + SessionService.mark_pending_posture(id, pending)   # sidecar，不写 session 文件
      → PostureResult.QUEUED
    （进程被杀）
    重启 load：SessionData.from_dict（agent 仍 build）
      SessionService.load → pending_posture = _read_pending_posture(id)   # 恢复排队
    下一回合入口 / 上一回合 close：_apply_pending_posture
      → commit_posture(plan, True, "/plan") → agent 落盘 + 历史 + 事件 + 删 sidecar

### 3.3 一次带 explore 目标的子代理

    SubAgentTool(agent="explore")
      → runner.run(..., agent="explore")
          resolve("explore") → kind=subagent ✓
          child = SessionData(agent="explore", ...)
          child_loop = AgentLoop(agents=catalog, session_permissions=parent.permissions, ...)
      → 子请求：_agent_rules(child) = explore 规则
          gate: agent 否决 → write/edit/bash 被拒；目录里根本没有它们

2. **`visible()` 包含 subagent。** 设计里它只列 primary；实现时按「表要完整可读」放宽为
   「全部非 hidden」——`/agents` 因此也能看到 delegation 目标，`/agents <subagent>` 仍按原规则拒绝。
3. **`test_history_search_tool.py` 的一处测试缺陷。** 该用例用默认 `workspace="."` 扫描
   `./transcripts/archive`，本机存在真实归档时结论翻转（工具若在归档里有命中就不报 `no_transcript`）。
   改为 `tmp_path`。这是测试对环境的隐式依赖，不是断言放宽。

## 12. 审核（2026-10-22，测试工程师视角）

### 12.1 验收脚本

`scripts/m1b_cases.py` —— **25 条**，全部驱动真件（真 `build_world`、真会话文件、
真文件系统、真命令分发），只有模型与网络是替身。七组：
契约 / 回路 / 队列 / 权威 / 目录 / wire / 漂移。

### 12.2 变异测试 —— 脚本本身也要被审

一个全绿的验收脚本可能只是**什么都没测**。所以给实现注入了 10 个语义变异，
每个变一个事实，看脚本是否报错：

| 变异 | 被谁抓住 |
|---|---|
| M1 文件又写 `mode`（第二个真相） | `the_session_file_carries_one_posture_truth` |
| M2 agent 的 deny 不再绝对 | `the_agent_deny_beats_a_session_allow` |
| M3 排队的切换不落 sidecar | `a_queued_flip_survives_a_crash` |
| M4 子会话永远说 build | `the_child_speaks_as_its_target_agent` |
| M5 agent 层从链里被摘掉 | `the_agent_allow_beats_the_base_tier` |
| M6 `hides()` 忘了 agent 层 | `the_catalogue_hides_what_the_agent_denied` |
| M7 切换事件丢了 reason | `the_wire_carries_the_switch_and_the_agent` |
| M8 坏文件半加载（allow 活着、deny 死了） | `a_bad_rule_row_leaves_no_half_loaded_agent` |
| M9 agent 历史被改写 | `the_agent_history_is_append_only` |
| M10 sidecar 不清理 | `a_queued_flip_survives_a_crash` |

**结果：10/10 被抓住。**

### 12.3 变异测试抓出的**真实缺口**（不是脚本的错，是实现的洞）

**M4（子会话永远说 build）最初逃过了全部测试。** 根因：既有用例只断言
「表里有 explore」和「包的 status」，**没有断言子会话实际带的 agent**——
而子 loop 拿到的是整张表，所以它永远能解析出 explore 的规则，
只有子会话自己的 `agent` 字段被改错时才出问题。

修法（测试侧）：新增断言看**子会话实际拿到的工具面**——
explore 子代理的 schema 里不得有 write/edit/bash。
这才是「子代理真的以 explore 身份运行」的可观测证据。
修后 M4 被抓住（`write was offered to an explore child`）。

### 12.4 变异测试暴露的一个**设计事实**（值得记住）

`hides()` 里的 `or wholly_disabled(action, agent_rules, …)` **不是冗余**。
链是 findLast（后层赢），所以「agent deny + session allow」时链说**保留**工具，
而 agent 单独求值说**隐藏**。二者不同是**对的**——它就是 veto 语义在目录面的对应物：
被 agent 拒绝的工具不该因为会话的一次 allow 就回到模型面前。

这个事实原先没有任何测试钉住（M5 与 M6 互为掩护：单摘一个都看不出来）。
现在由 `the_catalogue_hides_what_the_agent_denied` 钉住。

### 12.5 审核结论

- **真相源**：姿态只有一个权威（`session.agent`），`mode` 是派生且不可写；
  `session.agent` / `session.readonly` 的**写点只有一个函数**（`commit_posture`）；
  `session.mode` 全仓**零写点**（AST 扫描）。
- **契约**：会话文件只有 `agent` + `readonly` + `agentHistory`，无镜像 `mode`；
  旧文件读侧迁移；未知 agent 原样保留并 fail-safe 回落。
- **闭环**：切换 → 提交 → 历史 → 事件 → 落盘 → 重启 → 落地 → 清理，**逐段跑通**。
- **权限**：agent 层进链（第 7 层）+ deny 否决；目录面与判决面同源；
  agent 的 allow 赢 base/standing，输操作者的文件。
- **漂移**：规则 reader 与 frontmatter parser 各只有**一个定义**（AST 扫描），
  且都有真实调用方；agent 表只有一个装载模块。
- **未修**：`tests/test_tool_bash.py::test_a_promoted_command_does_send_its_notice`
  的负载偶发（基线同样存在，见 §11.5）。全量复跑 EXIT=0。
