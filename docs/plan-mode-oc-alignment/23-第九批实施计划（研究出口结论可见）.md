# 23 · 第九批实施计划（研究出口的结论要看得见）

> 本批 = **修一个已复现的缺陷**：计划模式走研究出口（`finish_research`）时，用户的结论在屏幕上基本看不见。
> 缺陷已用**真机**复现（会话 `e9f69f99` + 新会话 `05e2da3b`），不是推测。

---

## 0. 缺陷（一句话）

**结论只走「工具结果」这一条有损通道（后端 500 字 → 前端 120 字），而且这条通道没有展开的口子 ⇒ 用户只看到「已运行工具 · finish_research」加 120 个字。**

---

## 1. 证据

### 1.1 真机（`qwen3.7-flash`，TUI 120×40，`/plan 调研…`）

```
     ✓ 已运行工具 · finish_research
     ## 调研结论：会话落盘机制 本仓库（`/tmp/opencode/repro-research/ws`）**不
     包含会话持久化的源代码实现**——源码部分仅有一个空壳文件 `mod.py`（含一个返
     回 `1` 的函数）。所有持久化数据已经存…

     [plan] 研究已收尾：结论已给出（未提交计划、未执行任何工作）。
```

结论实际 **1729 字**，屏幕可见 **120 字**（**93.1% 不可见**）。
用户的原话正是这个现象：「结果都没有输出，就只能看到一点点，归类到这个分类下面而已」。

### 1.2 用户报的那个会话（`e9f69f99`）

两条 `finish_research` 工具消息：摘要 **2957 字** / **4116 字** ⇒ 各自只剩 501 字（后端截断）⇒ 前端再截到 120 字。**97% 不可见。**

### 1.3 通道逐级截断表

| 位置 | 限值 | 文件:行 |
|---|---|---|
| 工具结果 → 事件 | 500 字（+`…`） | `ai_coding/core/events.py:23,538-544`；`core/dispatch.py:298` |
| 事件 → 前端 | 120 字（+`…`） | `frontend/src/state/session.ts:205,507` |
| 前端展开 | **无**——`finish_research` 不发 `ToolChunk`，`lines` 恒空 ⇒ `canExpand` 恒假 | `component/toolcard.tsx:51`；只有 `bash_tool.py:90,392` 与 `core/mcp.py:901` 发 chunk |
| 回合终局 | **0 字结论**——`turn.finished` 没有 `text` 键；`note` 是固定状态行（34 字） | `server/bridge.py:180-192`；`core/turn_policy.py:85` |
| 重载路径 | 同样 120 字 | `frontend/src/state/replay.ts:30,188` |

### 1.4 为什么之前没人看见

- 18 号稿第 62 行写着：「**不做前端专属渲染**：结论就是 tool result 的文本，走既有渲染。」
- 但「既有渲染」就是那条 120 字的有损通道。**这个决定就是缺陷本身。**
- 18 号稿的前端验收项只有一行（F1）：给 `already_concluded` 等**失败码**加中文标签——失败有标签，**成功没有出口**。

### 1.5 对照组：`present_plan` 为什么看得见

它走的是**另一条通道**：`user_prompt.ask` 这个 server→client 的 JSON-RPC **请求**，`detail` 字段**不截断**，前端用专门的 `PlanReviewPanel` 渲染（`tools/present_plan_tool.py:247-253` → `server/handlers.py:128-150` → `frontend/src/util/ask.ts:52-62` → `component/plan-review.tsx:157`）。
**结论没有这样的通道，于是它掉进了工具结果里。**

### 1.6 房规（`docs/opencode-gui-m2-plan.md:160` 与 `a5-design.md:192`）

> 截断纪律：**outputPreview 500（event 已截）/ 120（UI）**；展开体显示尾 4000 字流。

这条纪律是给**工具输出**定的（一次 `read` 能返回 10MB）。**结论不是工具输出，是交付物**，却按工具输出处理了。

---

## 2. 房规：交付物走一等事件，不走有损通道

本仓库已有的两处同款先例：

| 先例 | 通道 | 大小限值 |
|---|---|---|
| `plan.updated`（计划卡） | 一等事件 `TaskUpdated` → `plan.updated`，带**结构化** items | **无** |
| `plan.receipt`（E2/D6） | 一等事件 `PlanStepReceipt(summary)` → `plan.receipt` | **无** |
| `user_prompt.ask`（评审卡） | server→client 请求，`detail` | **无** |

**结论按 `plan.receipt` 的形状做**：一等事件、带全文、画成 markdown 正文。

> **与 D6 的关系**：D6 的裁决是「marker 是记账，不是显示材料；前端不再消费的字段留着就是死字段」。
> 本批**不是**往 `PlanStepReceipt` 上加字段，而是**新开一个事件类型**给另一种交付物——结论不是「计划步骤的收据」。

---

## 3. 本批做什么

### 3.1 后端：一等事件

新增 `ResearchConcluded(summary: str)` 事件（`ai_coding/core/events.py`）：

- **谁发**：`finish_research` 工具成功时，由**工具自己**通过 `ctx.emit` 发——结论是工具的产物，工具最清楚它是什么。工具已经有 `ctx.emit` 这个口子（`tools/base.py:91`）。
- **带什么**：`summary` 全文，**不截断**。
- **wire**：`{"type": "research.concluded", "data": {"summary": …}}`（`server/bridge.py` 的 `to_wire`）。
- **D7 合规**：这是**终局性**的（它带的是本回合的结论），所以必须带 `turnId`——按 `bridge.py:316-349` 的既有规矩，bridge 给它盖上 `self.turn_id`，前端按 `session.ts:731-732` 的同一条归属规则过滤。

### 3.2 前端：画成 markdown 正文

- `state/session.ts` 收到 `research.concluded` ⇒ 在当前 assistant 消息里追加一个 `{kind:"text"}` part（`streaming:false`），走既有的 `<markdown>` 渲染（`component/message.tsx:54-66`）。
- **工具卡片怎么办**：`finish_research` 的卡片保留（它是发生过什么的证据），但它不再承担「显示结论」的职责。卡片仍然只显示 120 字预览——**结论由正文承担**，卡片只是那行「✓ 已运行工具 · finish_research」。

### 3.3 重载路径：live 与 reload 必须一致

D6/E2 的纪律是「live 与 reload 画同一个东西」。本批照做：

- **持久化**：研究结论已经在会话文件里了——它就是那条 `role=tool` 消息的正文（`core/turn_close.py:172-190` → `domain/run.py:49-90`，**全文，无截断**）。
- **重放**：`state/replay.ts` 处理 `role=tool` 消息时，对 `finish_research` 这条**成功的**工具消息，把它的正文（`stripEnvelope` 之后）画成 `{kind:"text"}` part，而不是塞进卡片的 120 字预览。
- 于是 reload 与 live 画出**同一段 markdown 正文**。

### 3.4 CLI（控制台）路径

`ai_coding/app/commands.py` 的 REPL 路径只打印 `note`（34 字状态行），结论同样看不见。本批让 REPL 也打印结论——它读的是**同一个** `research.concluded` 事件（observer 通道），与 TUI 同源，不新增第二套读法。

## 4. 不做什么

| 不做 | 为什么 |
|---|---|
| 不给 `PlanStepReceipt` 加字段 | D6 裁决：那是「计划步骤的收据」，结论不是它；混在一起会让两种交付物共享一个字段 |
| 不动 `present_plan` 的评审卡 | 它本来就看得见（§1.5） |
| 不改 `finish_research` 的成功/失败语义 | 本批只改**怎么显示**，不改**怎么判定** |
| 不改后端 500 字 `output_preview` 的截断纪律 | 那是工具输出的纪律（10MB 的 `read`），结论走新事件，不受它管 |
| 不让模型改用纯文本交结论 | 18 号稿的契约（`ai/prompt.py:141-142`「不能以纯文本收尾」）不动；模型照旧调工具，**我们负责把它写出来** |

### 9.2 一处实施中的自我修正（记录在案）

- **D7 的适用性被修正**：初稿写「`research.concluded` 是终局性的，带 `turnId`」。实施时查证：`bridge.turn_id` 只由 `_launch_turn` 赋值（`server/handlers.py:451`），而 `session_command`（`/plan <topic>` 走的路）**不经过** `_launch_turn`——那里的 `bridge.turn_id` 是上一次 `_launch_turn` 留下的旧值。给结论盖上这个 id 会让 `/plan <topic>` 的结论被前端按归属规则**丢掉**。
  结论：**结论是内容事件，不是终局事件**，不带 turn id——与 `PlanStepReceipt`、`AssistantMessage` 同形。（前端那条归属规则只管 `turn.finished`。）

### 9.4 真机（`qwen3.7-flash`，TUI 130×60）

**修前**（同一条 `/plan 调研…`，会话 `e9f69f99` / `05e2da3b`）：

```
     ✓ 已运行工具 · finish_research
     ## 调研结论：会话落盘机制 本仓库（`/tmp/opencode/repro-research/ws`）**不
     包含会话持久化的源代码实现**——源码部分仅有一个空壳文件 `mod.py`（含一个返

```

⇒ 结论 1729 字，屏幕可见 **120 字**（**6.9%**）；且被归在「已运行工具 · finish_research」这个分类下。

**修后**（两条路都验过：`/plan <topic>` 命令路 与 计划模式里直接发问的路）：

```
     会话落盘在 .ai-coding/ 目录下：.ai-coding/sessions/{id}.json 以 JSON 存储
     完整消息列表与会话元数据（title、timestamps、mode 等）；.ai-coding/
     traces/{id}/turn-{n}.jsonl 以 JSON Lines 记录每次 turn 的结构化事件
     流（IterationStarted、ToolStarted/Finished 等）。Undo 版本通过 .git/refs/
     ai-coding/undo/ 下的 Git 分支引用实现。依据为直接读取了这三个文件的内容与
     schema。

     [plan] 研究已收尾：结论已给出（未提交计划、未执行任何工作）。
```

⇒ 结论**整段可见**（markdown 正文：`##` 标题、列表、表格都正常渲染）；**工具卡不再出现**（结论有自己的位置，不再被归到工具分类下）。

逐字核对（脚本比对屏幕捕获与落盘的结论原文）：**7/7 段散文片段全部在屏**；修前只能给出前 120 字。
