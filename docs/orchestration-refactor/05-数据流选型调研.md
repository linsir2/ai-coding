# 编排层深改 · 05 数据流选型调研

> 背景：上一版方案**直接假定 append-only**，没有先证伪"原层是不是有问题"。这是跳步。本文不带预设立场，调研"新数据流到底该用啥"。

---

## 1. 直接回答：原来的层**坏了吗？没有。**

现状（`service/session_service.py` + `core/turn_close.py`）是一个**很稳的快照**，做对了这些：

| 它做对的 | 证据 |
|---|---|
| 原子写，不会写坏文件 | `tmp.write_text` → `os.replace`（POSIX 原子） |
| 回合中途也落盘 | `TurnCloser.checkpoint()`（长会话每 3 轮节流） |
| 落盘的是一致历史 | `save()` 前先 `ensure_tool_pairing()` |
| 落盘失败不毁回合 | `OSError` → `report_degraded`，不抛 |
| resume 已可用 | `load()` → `from_dict` |
| 历史其实有记录 | `.ai-coding/traces/<session>/turn-N.jsonl`（独立轨迹） |

**结论**：它不是"出问题了"，它是**一个合格的快照**。四场景的缺口是**窄的**（见 §2），不是"模型坏了"。

---

## 2. 它真正缺什么（4 条，窄而具体）

| # | 缺口 | 证据 | 对应场景 |
|---|---|---|---|
| G1 | **无"回合开着"标记** | 全仓无 turn 边界字段；重载后无法判断崩溃时是否有 turn 在飞 | ① 崩溃续跑 |
| G2 | **审批不是 durable** | 审批 await 在 `dispatch_batch` 内（agent_loop:1056），`checkpoint` 在之后（1081）→ 崩在 await 上就丢 | ③ 审批挂起 |
| G3 | **undo/redo 历史半边在内存** | `_undo_tail`/`_undo_state`/`_undo_files` 是 `dict[session_id,…]` | ④ undo/redo |
| G4 | **无请求头记录** | 全仓无 `request_header` 落盘 | ② resume 的可重建 |

**外加一条非缺陷的性能观察**：每次 save 整文件重写 O(N)。但会话 JSON 被 L3 落盘压住了体积，且 checkpoint 已节流 —— **不是真问题**。

---

## 3. 候选数据流（三个，不含预设）

### 模型 A：快照 + 少量字段（最小）
- 保持整文件快照。**加 4 个字段**：`open_turn`、`pending_approval`、`undo_state`、`last_request_header`。
- 在**对的时机**多存几次：turn 开始/结束、审批 await 前、undo/redo 后。
- 覆盖：**四场景全覆盖**。
- 代价：4 字段 + ~4 处保存时机 + dispatcher 加一个 save 回调。

### 模型 B：append-only 事件日志（真相）
- 会话 = `<id>.jsonl`，`SessionData` = 折叠产物。
- 覆盖：四场景 + 历史/审计/fork/增量写。
- 代价：17 事件 + fold + ~18 写入点换算 + `SessionService` 重写 + 15 构造点（id 靠 `__post_init__` 免改）。

### 模型 C：快照 + 恢复 sidecar（折中）
- 状态仍快照（读快）；**只把"恢复事实"**（turn 边界、审批、undo/redo、请求头）append 进 `<id>.events.jsonl`。
- 覆盖：四场景。
- 代价：1 新文件 + ~4 事件 + 保存时机 + load 时两处合并。

---

## 4. 对照四场景（量化）

| | **A 快照+字段** | **B append-only** | **C sidecar** |
|---|---|---|---|
| ① 崩溃续跑 | ✅ +1 字段 + 保存点 | ✅ | ✅ sidecar |
| ② resume | ✅ 已可用 +1 字段 | ✅ | ✅ |
| ③ 审批挂起 | ✅ +1 字段 + 保存前置 | ✅ | ✅ |
| ④ undo/redo | ✅ 持久化 undo 状态 | ✅ | ✅ |
| 新增文件 | **0** | 1 | 1 |
| 改动点 | **~4 字段 + 4 保存时机** | 17 事件 + fold + ~18 写入 + service 重写 | ~4 事件 + 4 保存时机 + load 合并 |
| 读成本 | O(1) | O(N) fold | O(1) + O(K) |
| 全历史/审计 | ❌（轨迹另有） | ✅ | ⚠️ 仅恢复事实 |
| fork / 时间旅行 | ❌ | ✅ | ❌ |
| 增量写 | ❌ O(N) | ✅ O(1) | ⚠️ 状态仍 O(N) |
| 复杂度/回归风险 | **低** | 高 | 中 |
| 数据流是否"跑得通" | ✅ 最稳 | ✅ 但面大 | ✅ |

---

## 5. 结论：数据流**不需要**改成 append-only

**第一性原理**：四场景要的是"**发生过的事实可重放**"，而**不是"一切都要日志"**。快照能重放（它就是状态），**只缺 4 个事实**。补 4 个事实 = 模型 A。

**append-only 只在你要这些时才是必需的**：全历史审计、fork、时间旅行、增量写（长会话）。**它们都不在北极星里。**

**推荐：模型 A（快照 + 4 字段）**。
- 它**最小**（4 字段 vs 17 事件）、**风险最低**（不动读路径、不动 `compress`）、**数据流最稳**（原层已被大量测试证明）。
- 若你日后确需审计/fork/增量，再走 **A→C→B** 的渐进路径（C 加 sidecar，B 换成日志为真相）。

**我之前推荐 B 是过度工程**——被"改成 dsh 的"带偏了，忘了先问"原层坏了吗"。你的追问是对的。

## 6. 模型 A 的落点预览（若选 A）

| 字段 | 写时机 | 读时机 | 覆盖 |
|---|---|---|---|
| `open_turn: int \| None` | `_begin_turn` 后 save；`_finish_turn` 前清 | `load` 时非空 → `interrupted_turn` | ① |
| `pending_approval: dict \| None` | 审批 await 前 save；答复后清 | `load` 时非空 → 重发 | ③ |
| `undo_state: dict \| None` | `undo`/`redo` 后 save | `load` 时恢复 redo 能力 | ④ |
| `last_request_header: dict \| None` | `_model_step` 组装后 | `load` 时可见"当时发了什么" | ② |

**文件半边（undo 创建的文件字节）**仍走 `SnapshotStore`（已持久化），不塞进会话 JSON。
