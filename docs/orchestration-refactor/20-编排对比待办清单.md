## B2. C-1 落地时发现的两件事（真机 + 代码双向核实）

### 调研纠错：压缩并不总是"只改副本"

原以为压缩从不改写 `session.messages`（`context_compression.py` 注释 "copy — never mutate"）。**只对了一半**，两条压缩实现语义不同：

| 路径 | 代码 | `session.messages` | 被丢的原文去哪 |
|---|---|---|---|
| 预算/自动（`context_compression.compress`） | `out = list(messages)` | **不变**（真机实测：自动压缩后仍是 14 条） | 仍在 session.json；若 snip 触发还会写 `transcripts/archive/*.md` |
| 手动 `/compact` + 溢出救援（`compaction.py:334`） | `session.messages = list(result)` | **被摘要替换**（真机实测：11 条 → 3 条） | 短会话（< `max_messages`=50，snip 不触发）**连归档都不写 → 原文不可逆丢失** |

→ `history_search` 当前只覆盖第一行。这是**独立且更大的数据丢失**。**已闭环（D-6，选项 A）**：`/compact` 覆盖前补归档 + `history_search` 搜归档（覆盖全部场景；见 F 表）。

### 发现二：模型不会主动想到用它

真机里，摘要已经够用时模型直接回答，没有调用 `history_search`（工具描述已写明触发条件："当早期内容被压缩掉时"）。是否在压缩后向模型注入一句"早期原文可用 history_search 取回"属于**新增 prompt 行为**。**已闭环（D-7，选项 B `fea226b`）**：仅压缩过的会话注入一行召回提示（volatile tail，正常会话零代价）。

### C-3b 后记（2026-10-18）：按键链人肉核销挖出的两个真缺陷（已修）

|---|---|---|---|
| A | **前端事件订阅被对话框顶掉**（主凶）：对话框停 job 后侧边栏停在 start 快照；且**关掉对话框后全场再无任何事件监听**（流式文本都丢） | `vscode-jsonrpc` 的 `onNotification` 按方法名存 **Map、后注册覆盖**（`connection.js:1006`）；`ipc.ts.onEvent` 每次订阅都往同一 "event" 键注册一个 connection handler | `connect()` 注册**唯一 dispatcher** 扇出到订阅 Set；`onEvent` 只增删 Set。+2 bun 测试（多订阅者互不顶替/退订不伤他人） |

### D-1c 后续（2026-10-17）：wake 被拒即终局 → 闩存+重放（延迟议题核销）

**症状**（真机发现）：job 在回合**尾巴**结算（最后一个迭代边界之后、future 完成之前；尾巴含 memory harvest，本次真机实测 22s）时，wake 因 `turns_in_flight != 0` 被拒且**不重试** → 通知滞留队列，直到下一次人类输入才被 drain。

**根因**：`_request_wake` 的拒绝是终局；而 notice 的唯一消化点是迭代边界（`_take_notices`），尾巴没有边界可 drain。确定性探针（`/tmp/opencode/wake_race_probe.py`）：在飞中 put(wake) → 回合结束后无 wake 回合、通知仍滞留；同一 put 在空闲时正常唤醒（正对照）→ 路径没坏，"拒绝即终局"才是病。

**修正**（对齐 dsh `wakeDriver` 的闩锁语义；落在 server 层——预算所在地）：

| 件 | 落点 |
|---|---|
| `_request_wake` 拒绝分流 | 因在飞被拒 → 闩存 prompt（单槽、后到覆盖）；预算耗尽 → 不闩（链式断路器，dsh 同语义） |
| `_watch_turn`（两处 future 追踪合一） | future 完成即"跑道空"事件 → `_replay_pending_wake`：队列有可投递物（notices 或 next-step 行，对应 dsh 的 hasPending 守卫）才重放；已被在飞回合 drain 则抑制 |
| `_interrupt_running_turns` 清闩 | Esc/promote 打断即停，闩存不越过用户意图（dsh cancel 同语义）；队列内容保持 durable，随下一人类回合送达 |

**证据**：3 个新 IPC 测试（在飞拒绝→重放、队列已 drain→抑制、Esc→清闩）；全量门禁 2994 绿；真机（真 world+真模型）：`sleep 6` 的 job 在模型末步之后、回合结束之前结算 → 22s 尾巴后**无人工输入**自动出现唤醒回合（`[notice] 后台任务的结果到了——查看并继续`）→ 下一迭代边界 drain 出完成通知 → 模型作答。（同场景 `sleep 3` 的一次走的是回合内边界自 drain 的既有路径——两条都合法，修复只补上尾巴这条路。）

**尾巴核销（2026-10-17 续，C2 异步化）**：原"已知权衡"（延迟=尾巴时长，实测 22s；harvest 出关键路径"留单独立项"）本轮落地。设计：harvest 从 `_finish_turn` 的 await 改为 `_schedule_harvest`（fire-and-forget + **链式串行**——delta 惰性捕获，两个重叠的 harvest 会把同一批消息给抽取器看两遍；顺带获得"回合快于抽取时 delta 合并"的合意行为）；`flush_harvest()` 供测试与优雅关闭（`aclose` ≤5s 有界；抽取器需要引擎，所以 flush 在 `engine.aclose` 之前）。**顺带修一个隐藏 bug**：游标推进写 `len(session.messages)` 在异步下会把"抽取期间新到的消息"静默标成已抽——改为 `start + len(delta)`（只推进抽取器真正看过的部分）。事件顺序变化：`MemoryHarvested` 等落在 `turn.finished` 之后（无前端消费者，bridge 测试顺序无关）。测试面：`test_agent_loop_memory.py`（+3 新：先返回/链式不重不漏/游标=捕获端）与 4 个关联文件加 flush。**证据**：门禁 2997 绿；真机两轮（真 world+真模型）——结算→唤醒 **11ms / 13ms**；TurnFinished 后 288ms 才结算的 job 看到的是一个真空闲会话（修复前该窗口=0–22s 的 harvest 时长，正是 3/5 次滞留的形状）；harvest 后台分两段推进（游标 0→4→6/7）。
