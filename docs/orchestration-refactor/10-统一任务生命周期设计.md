## 0. 一句话

给编排层补上缺失的**任务生命周期与驱动角色**：`/plan` 从核外旁路升为内核 `TaskDriver` 的 `plan` 档案；armed 任务获得跨回合驱动、崩溃自动续跑与 durable 输入；日常对话保持 unarmed（一次性回合，用户驱动）。

## 1. 背景与根因（浓缩自 01-06）

| # | 根因 | 证据 |
|---|---|---|
| 1 | 回合是预算容器，不是任务容器：无任何机制让目标"活着" | `turn_policy.py:66-106,186-214`；dsh goal-round-driver 对照（05） |
| 2 | 放弃早于坚持：3 轮无成功即停工汇报 | `turn_policy.py:224-235` |
| 3 | 压缩"一次墙"：第二次溢出直接抛错收尾 | `agent_loop.py:651-674` |
| 4 | 续跑状态不持久：continuations 进程内、恢复手动、输入首 checkpoint 前不落盘 | `turn_policy.py:136-139`；opencode auto-resume 对照（06） |
| 5 | 进度真理源分散；nudge 系是提示词补丁 | `turn_policy.py:236-258`、`request_assembly.py` 注入族 |
| 6 | 驱动角色在核外（PlanRunner 是 app 层过程式代码），两套编排语义并存 | `plan_runner.py:224`；C3/验收/停止条件双份 |

## 2. 目标与非目标

**目标**：一个内核、一套任务语义、一个驱动角色；armed 任务长程可靠（驱动/续跑/输入 durable）；`/plan` 行为逐字等价。

**非目标（不做清单见 §13）**：durable inbox/claim/doorbell、append-only/事件溯源、queue 投递档位、新 arming 命令、UI 改版、CLI 自动续跑对等（延后）。

## 3. 目标架构

```
┌─ 输入层 ──────────────────────────────────────────────┐
│ session.prompt / session.command / initialize         │
│ 变更: _begin_turn 末尾 save 一次（用户消息+openTurn）  │
└──────────────┬────────────────────────────────────────┘
               ▼
┌─ 任务层 ──────────────────────────────────────────────┐
│ TaskState + 生命周期: unarmed│armed│blocked│done       │
│ 新字段随会话文件 task 键持久化                          │
└──────────────┬────────────────────────────────────────┘
               ▼
┌─ 驱动层 TaskDriver（新角色）──────────────────────────┐
│ armed 且 idle → 下一轮; 停止=完成/失败/上限/取消       │
│ 崩后: 启动扫描 armed+open → 自动续跑 + 熔断            │
└──────────────┬────────────────────────────────────────┘
               ▼ 每轮 = process_input(round_profile)
┌─ 内核（基本不动）─────────────────────────────────────┐
│ _run_turn / TurnPolicy / Assemble / Dispatcher /      │
│ write_back / checkpoint / close —— 全部复用            │
└───────────────────────────────────────────────────────┘
```

角色对照：dsh 的 `goal-round-driver` 在核外独立包；opencode 在执行层。我们取二者并集：**driver 是内核角色**（语义唯一、可单测），**启动扫描在 server 层**（对齐 opencode 的 boot scan）。

## 4. 任务生命周期（`domain/task.py`）

### 4.1 字段（TaskState 扩展；只增键，老文件可读）

| 键 | 类型 | 何时写 | 语义 |
|---|---|---|---|
| `armed` | bool | 仅 True 时写 | 显式 arm（`/plan`）后为真；完成/失败停止/Esc 后为假 |
| `armedProfile` | str | 随 armed | v1 仅 `"plan"`；driver 据此选 round_profile |
| `roundsRun` | int | 非零才写 | driver 已开轮数（round cap 用） |
| `resumeCount` | int | 非零才写 | 自动续跑次数（熔断） |

序列化纪律沿用现有规矩：`SessionData.to_dict` 只在 `task.items` 非空时写 task 键（`session.py:430-436`）；armed 任务必有 items，无冲突。

### 4.2 状态机与转移（唯一判定出处）

```
unarmed ──/plan arm──▶ armed ──全部完成──▶ done(=disarm+save+报告)
                        │──失败停止（修复后仍败）──▶ disarm+save（项留 blocked/stalled 状态）
                        │──Esc 中断──▶ disarm+save（当轮取消）
                        │──resumeCount>5 熔断──▶ disarm+save+明说
                        └──崩溃（armed 在盘；openTurn 有无皆可）──▶ 启动扫描 → 自动续跑（resumeCount+1）
```

- `done/blocked` 不新增独立状态位：完成=items 全终态；blocked 是项级状态（现有 `TodoStatus`），disarm 是任务级唯一新增行为。
- arm/disarm 都伴随 `save`（崩溃点安全）。

## 5. TaskDriver（新角色，`core/task_driver.py`）

### 5.1 驱动循环（伪码，精确）

```
run(session, profile):
  while True:
    if not task.armed: break                      # Esc/熔断/外部 disarm
    if roundsRun >= profile.max_rounds: break     # round cap（plan: 现状值）
    item = next_actionable(task)                  # plan: _next_ready 现状逻辑
    if item is None: break                        # 无待办
    round = profile.round_for(item)               # 会话/策略/验收/提示词（5.2）
    with profile.round_context(loop):             # policy 交换（现状 continuations_disabled 模式一般化）
      result = await loop.process_input(round.session, round.prompt, ...)
    verdict = profile.settle(session, item, step_session, result)   # 机械判定（现有 _settle）
    task.roundsRun += 1
    if verdict passed: 记录 receipt
    else:
      if 未修复过: repair 轮（现状一次修复）; continue
      else: break                                 # plan 现状：一步修复后停（项留 blocked/stalled）
    save(session)
  task.armed = False; save(session); profile.report(...)
```

### 5.2 round_profile 契约（参数表）

| 参数 | plan 档案取值（= 现状逐字） | 说明 |
|---|---|---|
| `session` | `ephemeral step session`（`plan_runner.py:384,403`） | 隔离：步骤不污染父 history |
| `prompt` | `_seed()` 现有 step 提示词 | 每步聚焦一项 |
| `policy_overrides` | `max_iterations=_step_budget`、`stop_policy="natural"`、`max_auto_continuations=0`（`:514-516`） | 一般化现有"交换-恢复" |
| `verification` | 每项一条 `AcceptanceItem(verify)`（`:503-508`） | 机械判定，模型申报不算数 |
| `max_rounds` | 现状（`_run_budget`:439） | |
| `repair` | 一次（现状） | |

### 5.3 停止条件表（表驱动、可单测）

| 条件 | 动作 | 落盘 |
|---|---|---|
| items 全终态 | disarm + 报告完成 | task.armed=False |
| 修复后仍失败 | disarm + 报告 blocked 项 | armed=False；项级 blocked/stalled（现有状态） |
| roundsRun 达上限 | disarm + 报告 | armed=False |
| Esc/外部 disarm | 当轮取消路径 + disarm | armed=False（§8） |
| 熔断（resumeCount>5） | disarm + 明说 | armed=False |

### 5.4 单飞与并发

- 进程内**全局单飞**：一个 driver 运行时，第二个 armed 任务的驱动请求被跳过（其 `openTurn`/armed 留在盘上，下次启动/加载再续）。理由：一个进程一个 `AgentLoop`，`_turn_lock` 会串行化跨会话回合——允许并行驱动只会造成交错，v1 从简。
- 防护三层：`task.armed` 落盘（持久） + server running 集合（进程内） + `loop._turn_lock`（运行时）。

## 7. 连续性

### 7.0 输入端路由（契约；证据见 `docs/orchestration-research/07-输入端路由.md`）

- **日常输入永远是普通回合（unarmed）**。没有任何输入解析/自动路由；内容像任务的消息也不例外。
- **任务机制唯一入口 = 显式 `/plan`**（§6.1 的 arm）。模型 `todo_write` 只建 items，从不 arm；启动扫描只认 `task.armed`。
- 对照：dsh 还有一扇"模型工具发起 goal"的门（`create_goal`，提示词限"直接的人类请求"）；opencode 没有。我们 v1 不做模型发起，记录为观察项（07 §4），未来若做走"模型建议 + 用户确认"。

### 7.1 输入 durable（`agent_loop._begin_turn` 末尾 save 一次）

- 顺序：`add_message(user_message)`（:804）→ …… → `session.open_turn = turn_count`（:855，**现状已在 save 点之前，无需挪动**）→ **紧接着 `self.closer.save(session)`** → 再走 `hook_context = await ...`（hook 返回 str、不改 history，save 不等它）。
- 一条 save 同时保住**用户消息 + openTurn**：崩溃后 load 能看见"输入在、回合开着"。
- 仅 `append_user=True`；ephemeral 由 `closer.save` 自身 guard 跳过；**resume 路径不重复加 save**（`resume_turn` 的 M1 save 已覆盖它的注记）。
- **刻意行为变更**：save 计数 +1/回合。夹具更新清单（实施时以 `grep -rn "saves ==\|saves >=" tests/` 全扫为准）：
  - `tests/test_agent_loop_react.py:320`（saves==3）、`:341`（saves==1）→ +1；
  - `tests/test_crash_recovery.py:645,663` 不受影响（直接驱动 `_forget_redo`，不过回合入口）；
  - 其余 save 计数点实施时逐一定夺。
- 与 P2 注释的关系：P2 当年"不新增 save"是因为那时快照层的窗口"没有产出可丢"；本次为长任务可靠性**刻意推翻**该取舍——窗口里有**用户输入**可丢，`openTurn` 也一并提前。

### 7.2 自动续跑（armed 专属）

- **扫描判据**：`sessions/*.json` 中 `task.armed == true`（**不看 openTurn**——clean close 会清掉 openTurn，但轮间崩溃的任务仍是 armed，必须续）。文件先按 key 过滤（json 读一次），只对候选做 `from_dict`。
- **两种续跑分支**（同一 pick 规则下）：
  - `openTurn != null` → 崩在轮中：先 `resume_turn` 补完/收尾被中断的当轮，随后 driver 按 §5.1 循环继续开口；
  - `openTurn == null` → 崩在轮间：直接 driver 循环开下一轮。
- **pick 规则**：取 `lastAccessTime` 最新的一条；多个候选其余留在盘上（不并行驱动，§5.4）。
- **落点**：`server/world.build_world` 完成扫描并存 `world.pending_resume`；`initialize` handler 首次调用时消费——载为 live 会话（替代"永远新建"）并 spawn driver 继续轮；无候选 → 现状（新建）。**变更点**：`initialize` 的"永远新建"对 armed 例外（armed 即同意书）。
- **记账**：每次自动续跑前 `resumeCount += 1` 并 save（先记账后续跑：续跑本身崩溃时计数已落盘，防无限重试）。
- **熔断**：`resumeCount > 5` → disarm + 一条 notice（复用现有 wire 通道；措辞与 `recoveryNotice` 同风格）。
- **清脏**：启动时对候选会话执行现有 resume 清理（marker 读取、死 marker 清除）；压缩层无持久中间态（同步执行），无需清算——**诚实记录：无 opencode 式 settleStale，因为没有等价脏数据**。
- **CLI**：v1 不做自动续跑（延后项，§13）。

### 7.3 压缩：**设计勘误**——机制已就绪，只拆循环层的"一次墙"

写 spec 时逐行核实发现：设计讨论稿里的"滚动结构化检查点"**大部分已存在**，本次**不做**新机制：

- 已有：七段式检查点模板（`## 目标/约束与要求/决策/工作状态/下一步/关键文件/重要上下文`，`llm_helpers.py:145-153`）；旧检查点标注隔离喂给摘要器（`CHECKPOINT_OPEN/CLOSE`+`SINCE_*`，`context_compression.py:_l4_head_text_excluding`）；合并更新语义（`previous` → "更新" 提示 + `summary_within_growth_bound` 防膨胀）；形状校验+重试（`checkpoint_body`）；r15 收缩阶梯（`_SHRINK_STEPS`）；L4 断路器（`_L4_BREAKER_THRESHOLD=3`，`:625`）。证据文档 `docs/r11-analysis.md`、`docs/r15-summary-shrink.md`。
- 本次唯一改动（`agent_loop.py:651-674`）：`reactive_compacted: bool` → `compact_attempts: int`（上限 2）。第二次溢出允许再压一次（合并机制保证它不是"摘要的摘要"）；两次后仍溢出、或 `report["removed"] == 0`（现有诚实退出）→ raise，维持原语义。
- 轮间注入：driver 的继续轮提示复用检查点内容——v1 直接取 history 中最新 `CHECKPOINT_MARK` 消息（存在时）渲染"下一步"，plan 档案不受影响（仍用 `_seed`）。
- **不动**：L1/L2/L3、七段模板、摘要提示词、收缩阶梯、断路器、水位。

## 8. 中断与取消（Esc 语义）

- `session.interrupt`（handlers.py）增：若 live 会话 `task.armed` → `armed=False` + save（best-effort）。
- 时序：先 disarm → 再 `cancel.set()` + futures cancel（当轮走既有 CancelledError 路径持久化部分回合）。当轮 close 的 save 与 disarm save 竞争写同一会话文件——两次都是整文件原子写、同一内存对象（都含 `armed=False`），last-writer-wins，**竞态良性**（写进 spec 以防后人误判）。
- driver 循环每轮开头重读 `task.armed`：Esc 后走完当轮收尾即退出。

## 9. 数据流（armed 任务的一生）

```
/plan ──▶ 规划轮（process_input, C3=0）
       ──▶ arm(save: armed+profile) ──────────────── 崩溃点①安全
            ┌────────── TaskDriver 循环 ──────────┐
            │ 检查 armed → 注入(seed/检查点) →     │
            │ process_input(ephemeral step session) │
            │ → settle(机械) → receipt/修复/停      │
            │ → save(roundsRun)                    │ 崩溃点②: openTurn+armed 在盘
            └─ 全完成/失败停止 → disarm+save → 报告 ┘
启动扫描: sessions/*.json 按 openTurn+armed 过滤
       → initialize 消费 → 载 live → resumeCount+1 → 续跑轮
```

## 10. 错误处理与边界（诚实项）

- **at-least-once**：自动续跑从"最后落盘状态"继续；末轮在途副作用可能被重做一次（模型重新决策，不自动重放工具）——与现有 `[resume]` 注记语义一致。
- **ephemeral**：step session 不落盘（现状）；崩在轮中丢的只是当轮，driver 从项状态重开该轮。
- **熔断阈值** `resumeCount>5` 可配（对齐 opencode countResume>10 的形状）。
- **driver 与 /plan 的同步使用**：`/plan` 命令本身在 spawn 的任务里运行 driver；与 server 自动续跑的 running 集合互斥（同集合）。

## 14. 开放风险与实施期验证点

1. **压缩拆墙的前提复核**（P3 第一步）：确认 `compact_now` 连续调用时合并路径确实生效（`previous` 被传入、增长界通过）——若现状有隐藏假设（如 force 路径不读旧检查点），P3 升级为两小步（先验证、必要时补一行传参）。

3. **save 节奏夹具**（P2）：全仓 sweep 后再改，逐条列入 commit message。
4. 行号漂移；以代码为准。
