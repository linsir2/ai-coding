# 编排层深改 · 01 现状调研

> 目的：在设计改造前，**彻底摸清现有基础架构**，尤其与"持久化与可恢复"相关的部分。不盲目改。
> 方法：源码级阅读（`domain/`、`service/`、`core/`、`security/`、`server/`）。
> 北极星：**持久化与可恢复**（四个场景全要：崩溃续跑 / 跨会话 resume / 审批挂起 / undo-redo 持久化）。

---

## 1. 现状总览

```
用户输入
  → server/handlers.py::session_prompt → run_turn() → world.loop.process_input()
  → AgentLoop._run_turn()  [core/agent_loop.py]
       _capture_snapshot()       ← git stash create → refs/ai-coding/undo/<sess>/<turn>
       _begin_turn()             ← session.add_message(user); turn_count++
       while: TurnPolicy.decide_next_iteration()
              → RequestAssembler.assemble() → _model_step() → _run_tools()
              → TurnCloser.checkpoint()   ← 节流整文件保存
       _finish_turn() → TurnCloser.close()  ← handoff + digest + save
  → SessionService.save()  [service/session_service.py]
       to_json_pretty(session.to_dict()) → tmp → os.replace()   ← 整文件重写
```

## 2. 逐层现状（与持久化/恢复相关的部分）

### 2.1 数据契约（`domain/`）

| 契约 | 现状 | 关键点 |
|---|---|---|
| `SessionData` | **可变 dataclass**，`messages: list[ChatMessage]` 是唯一状态 | `to_dict`/`from_dict` 是**手写白名单**；大量字段标 "NOT persisted"（in-process only） |
| `ChatMessage` | role/content/tool_call_id/tool_calls/reasoning/synthetic/artifacts/images | 无稳定 id（靠位置） |
| `TurnOutcome` | status/text/iterations/reason/usage/handoff | 冻结 |
| `TurnStatus` | COMPLETED/MAX_ITERATIONS/TIMEOUT/BUDGET/STOPPED/ABORTED/ERROR | 终止原因枚举 |

**SessionData 里 in-process-only 的状态**（重启即丢，且**没有持久化路径**）：`continuations`、`thinking_retries`、`harvested_messages`（持久化了）、`tool_observations`、`skill_stats`、`error_recovery_cache`、`constraint_tracking`、`pre_compaction_anchor`、`coactivation_graph`、`loaded_skill`、`listed_skill_ids`、`skill_review_*`。

### 2.2 持久化（`service/session_service.py`）

- **整文件重写**：`to_json_pretty(session.to_dict())` → `.tmp` → `os.replace()`（POSIX 原子）。
- 文件：`<sessions_root>/<session_id>.json`。
- **Java 兼容是明写约束**（"compatible with the Java sessions/*.json shape"）。
- `create`/`save`/`load`/`list_sessions`/`resolve`（前缀匹配）/`delete`。
- **无日志、无版本、无增量 append、无 turn 边界标记。**

### 2.3 回合收尾（`core/turn_close.py`）

- `TurnCloser`：`write_back`（工具消息）、`checkpoint`（节流保存：短会话每次，长会话每 3 次迭代）、`save`（`ensure_tool_pairing` + best-effort，`OSError` → `report_degraded`）、`finalize`、`close`（handoff + digest + save）。
- **持久化失败只降级不中断**（"losing the session file must not lose the answer"）。
- `ephemeral` 会话跳过保存（plan-runner 内部步）。

### 2.4 循环（`core/agent_loop.py`，1675 行）

- `process_input` 用 `_turn_lock` **串行化**（G1-1，前端的 `input.disabled` 之外的编排层闸）。
- `_run_turn`：`_capture_snapshot` → `_begin_turn` → 迭代循环 → `_finish_turn`。
- `_begin_turn`：`session.add_message(user_message)`、`turn_count++`、`_bind_observer`、`_bind_trace`。
- **undo/redo 全在进程内存**：`self.last_undo`、`self._undo_tail`、`self._undo_state`、`self._undo_files`——**都是 `dict[session_id, ...]`，重启即丢**。
- 快照（文件半边）**持久化**：`SnapshotStore`（git refs）。

### 2.5 快照 / undo-redo（`core/snapshots.py`）

- `git stash create` 写一个 commit（**不动 working tree、不动 refs/stash**），`update-ref refs/ai-coding/undo/<session>/<turn>` 钉住防 gc。
- `restore` 逐文件：`git diff --name-only <ref>` → 对每个路径 `cat-file -e` 判断是否在快照里 → `checkout` 或（turn 创建的）删除。
- `RestoreReport(restored, failed, saved)`——`failed` 是证据，`saved` 是 redo 的唯一副本。
- redo 槽：`<session>/redo`。
- **文件半边持久化；历史半边（undo 掉了哪些消息、turn_count/digest）在内存。**

### 2.6 事件 / 观察（`core/events.py` + `core/observers.py`）

- ~30 个冻结 dataclass 事件 + `LoopObserver` 协议（**单个 `on_event`**）。
- `Braid`（扇出，隔离失败）、`SafeObserver`（吞失败、计数）、`ScopedObserver`（子 agent 事件包 `ScopedEvent`）、`EmitObserver`。
- **只有 emit 语义**——无 waterfall、无 serial、无拦截。
- `server/bridge.py` 把事件映射成 IPC `event` 通知。

### 2.7 审批 / 安全（`security/approval.py` + `server/handlers.py`）

- `ApprovalCallback` 协议：`approve(tool_name, params, reason) -> ApprovalResult`。
- `ApprovalResult`：**YES / ALWAYS / NO / STOP**（enum，非封闭 fail-closed 类型）。
- `CLIApprovalCallback`（stdin 线程 或 provider）、`AutoApproveCallback`（永远 YES，非交互）。
- **Server 侧**：`_install_providers` 装一个 provider，发**服务器发起的请求** `approval.request`，await 答案。
- **turn 阻塞在审批 await 上**——进程死了，审批就丢了。

### 2.8 IPC（`server/handlers.py`、`bridge.py`、`world.py`）

- `session.prompt` → `run_turn()`（asyncio task）→ `world.loop.process_input`。
- 审批是**请求/响应**（server-initiated request），**不是 durable 事实**。
- `session.interrupt` 取消 task。
- 组合根：`build_world`。

## 3. 四个恢复场景的差距分析

| 场景 | 现状 | 缺什么 | dsh 的机制 |
|---|---|---|---|
| **① 崩溃后继续未完成 turn** | checkpoint 存了**消息列表**，但**无"turn 开着"标记**；重载后看到一个有半截消息的会话，**无法知道有 turn 在飞、也无法续** | **turn/step 边界标记** + **崩溃修复**（补 turn/end） | `turn/start` 无配对 `turn/end` → `repair.ts` 合成 closer |
| **② 跨会话 resume** | **基本可用**：`load` 恢复 messages/task/digests/usages | **请求可重建**（当时发了什么）；in-flight 状态（continuations 等丢）；**消息无稳定 id** | `request/header` 让请求是日志的纯函数 |
| **③ 审批挂起** | **完全不可用**：审批是内存 await | **审批作为 durable 事实** + **挂起/恢复** | `approval/asked`/`approval/decided` 日志对 + signal |
| **④ undo/redo 持久化** | **一半**：文件半边（git refs）持久化；**历史半边在内存**（重启丢 redo） | **undo/redo 作为 durable 日志操作** | surface `replace` + durable 事件 |

---

## 4. 核心结构性差距

**ai-coding 没有事件日志。** `SessionData` 是一个**快照**（可变状态），靠**整文件重写**保存。dsh 是 **append-only 日志**，一切从它派生。

四个场景本质上都要同一件东西：**"发生过什么"必须落盘且可重放**。当前只有"现在是什么"落盘。

具体缺口：
1. **无 turn/step 边界标记** → 无法判断崩溃时有 turn 在飞（场景①）。
2. **无请求头记录** → 无法重建"当时发了什么"（场景②）。
3. **审批不是 durable 事实** → 无法挂起/恢复（场景③）。
4. **undo/redo 的历史半边在内存** → 重启丢（场景④）。

---

## 5. 设计落点（初步）

要覆盖四个场景，**最小充分**的改造是引入**一个事件日志层**，且**不必是 dsh 的完整 event-sourcing**：

| 落点 | 内容 | 覆盖场景 |
|---|---|---|
| **L1 会话日志** | 在会话文件里加**有序事件流**（turn/step 边界、消息、审批、undo/redo），或独立 `.jsonl` | ①②③④ |
| **L2 持久化接缝** | Service Definition / Provider / Consumer 三角（对标 `SessionPersistence`），支持 append + flush + crash repair | ①②③④ |
| **L3 崩溃修复** | 检测未闭合的 turn/step/审批，合成 closer | ①③ |
| **L4 请求可重建** | 记录 `request/header` 等价物 | ② |
| **L5 审批 durable 化** | `approval/asked`/`decided` 事件 + 挂起/恢复 | ③ |
| **L6 undo/redo durable 化** | 把 `_undo_tail` 等落成日志操作 | ④ |

---

## 6. 关键约束与待决问题

1. **Java 兼容**：会话格式明写"兼容 Java `sessions/*.json`"。引入事件日志**会破坏它**。→ 需要决策：**放弃 Java 兼容？还是日志走独立文件（`.jsonl`）保留 JSON 兼容？**
2. **整文件重写 vs append**：现在是整文件；日志需要 append。→ 决策：**日志用独立 append-only 文件，`session.json` 保留为派生快照？**
3. **事件模型 vs 只加日志**：北极星是持久化/恢复，**不必**同时引入 dsh 的三域事件 + waterfall（那是"可拦截"的目标）。→ 建议**分离**：本轮只做日志层 + 持久化接缝；拦截层留到下一轮。
4. **消息 id**：dsh 消息在创建时铸 id；我们靠位置。→ 决策：**是否给 `ChatMessage` 加稳定 id**（利于恢复关联）。
5. **进程内状态**：`continuations` 等 in-process 字段是否需要持久化。
