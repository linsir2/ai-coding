## 2. 四个"根本分歧"（其余差异都是它们的投影）

### 2.1 历史 = 可变快照 vs 追加日志 vs 行存储

- 我们：`messages` 列表是活的，压缩就地改写，落盘=整份覆盖（request_assembly:139）。
- dsh：日志是唯一真源，`deriveMessages` 每次纯派生；压缩=对日志 append 一个 replace op（02:§3.2/§9）。
- opencode：消息是 SQLite 行，投影器折叠事件更新行；压缩=边界后重放（03:§7/§9）。

**投影到**：崩溃恢复机制（§1.14）、请求装配（§1.6）、压缩形态（§1.15）。
**已拍板**：05/06 已证伪 append-only 全量改造（我们的快照层没坏、append 是过度工程），本对比不翻案——但值得知道 dsh 的 `deriveMessages` 是"日志即状态"的最纯粹形态，它的代价是**每次请求全量派生（缓存增量）**。

### 2.2 循环控制 = 纯策略 vs 机制位

- 我们：`decide_next_iteration`/`decide_after_step` 是唯一"停不停"的地方，可表格测试；nudge/验收/预算都在策略内。
- dsh/opencode：循环继续与否是**结构性事实**（还有工具没跑完 / needsContinuation），策略（retry、compaction retry、goal steer）挂在瀑布/事件上。
**判断**：我们的形态更可测、更内聚（这也是我们 nudge/acceptance/fatigue 一大堆行为的容器）；两家的形态更"内核小、插件补"。不是优劣，是分工位置不同。

### 2.3 输入与审批的 durability 边界

- dsh/opencode 都把**输入**在 ack 前落盘（inbox 表/日志）；都**不**把**审批问题**持久化（崩溃后靠修复合成 closer，问题不重问）。
- 我们相反：输入在首 checkpoint 前有窗口（P2 已接受），但**审批问题**是全仓最 durable 的（marker + resume note + resume_turn）。
**这是最独特的一组取舍**：他们保"用户说了什么"，我们保"系统在问什么"。两者可以同时要，但各自都付出了机制成本。

### 2.4 工具并发的顺序哲学

- dsh：池内乱序执行、**按模型顺序提交结果** + `sourceEventSeqs` 因果链；
- opencode：per-source 顺序（provider 流与每个工具 fiber 各自同步标记）；
- 我们：批次前置 gate，**要么全并发要么全串行**（最保守）。
**投影**：dsh/opencode 的结果顺序靠"提交时刻"保证模型可见历史稳定；我们因为批次级判断，天然没有乱序问题，但并行面窄（一个 WARN 工具就会把整批拽成串行）。

## 3. 每个维度里最值得记住的机制（择要）

1. **dsh 的 `request/header` + developer/message**（02:§3.2）：工具表变化作为日志事件显式记录，请求信封变化理由（initial/resume/change/series）可审计。我们只有 tail 的 canonical 对比——方向相同，粒度不同。
2. **dsh 的 `agent/turn-stopping`**（02:§6.1）：turn 关闭前的最后可插拔点，listener 还能 steer 续跑——"收尾也可拦截"。我们的对应物是 `_ask_for_closing`（rail 内的固定动作），不是可插拔点。
3. **opencode 的 ephemeral/durable 事件二分**（03:§6）：delta 永不落库、只有终态进 message 行——"流式体验"与"持久化体积"解耦。我们的事件层本来就不持久化（Observer 不做 durable），无迁移需求，但这是他们 SQLite 模型成立的关键机制。
4. **opencode 的 defect 隧道**（03:§4.4）：用户拒绝不作为工具输出喂给模型，而是 typed failure——"人说的不"与"工具说的错"分流。我们对应的是 `_not_approved` 产出 denied 的 ToolResult（模型会看到被拒事实）；谁更好取决于产品语义，值得记入产品判断。
5. **dsh 的 `interruptedTurnClosers`**（02:§7.6）：resume 时对崩溃尾巴**合成**缺失的 tool 结果/step/end/turn/end——日志可以补写。我们对应物是 `ensure_tool_pairing`（丢弃孤儿）+ open_turn 事实（不伪造）——**我们选择不合成**，保持"历史只记录真实发生过的事"。
6. **opencode 的 claim（time_suspended）**（03:§7）：执行开始前先写"我占了"意图，崩溃后据此判"这个会话上次死在执行中"。我们的对应物是 `open_turn`（同意图）。

## 4. 可以拿走的 vs 不该拿的（观察，非决策）

### 可能值得评估（留给下一步拍板）

| 候选 | 来源 | 我们现状 | 评估要点 |
|---|---|---|---|
| 输入先落盘（关 P2 窗口） | dsh inbox / opencode inbox | prompt 在首 checkpoint 前崩溃丢用户消息 | 需要"入队即写"的新落点；与现有 save 节奏纪律的冲突要算清 |
| 结果按模型序提交（若未来放宽并发） | dsh | 批次级全并发/全串行，无乱序问题 | 只有在放开"一个 WARN 拉全批"时才需要 |
| 恢复时合成缺失 closer | dsh repair | ensure_tool_pairing 丢弃孤儿 | 与"历史只记录真实"承诺冲突，需产品判断 |
| 收尾可插拔（turn-stopping） | dsh | `_ask_for_closing` 固定 | 收益看插件生态需求，目前没有 |

### 已经论证过、不再考虑（避免重开）

- append-only 日志 / 事件词汇 / fold：05（数据流选型）证伪为过度工程；
- 压缩 range-surface：03（三方比对）论证不配 4 层整列表变换；
- SessionService 重写 / 请求头 / 去 Java 兼容：06 已撤回清单。

### 三家都在做、我们**已经做了**的（防止低估自己）

- 崩溃后有恢复语义：我们快照+marker+sidecar；他们日志+repair / claim+restart；
- 流式输出与工具卡片：三层事件链我们都有（LoopEvent→bridge→reducer）；
- skill：三家形态几乎同构（目录进系统层 + 工具加载 + 用户显式调用），差异只在注入是否 durable；
- 省略号：审批、压缩、并发护栏——每家都有，只是名字不同。

## 6. 未决问题（抛给下一轮讨论）

1. 是否评估"输入 durable 落盘"（补 §2.3 的半边）？代价是与 save 节奏纪律（P2）的正面冲突。
2. 并发策略是否维持"批次级全 ALLOW"？它在安全上更保守、在体验上更窄。
3. 审批被拒的语义：模型可见（我们现在）vs opencode 的 defect 隧道——这是产品语义选择题。
