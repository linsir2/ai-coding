# 07 · 输入端路由：一次用户输入如何进入（或不进入）任务机制

> 背景：设计评审提出的关键问题——"日常输入一个任务，会不会全都直接进 plan/驱动模式？"
> 结论先行：**三家都不会自动路由**。进入任务机制（plan/goal/驱动器）的门全部是**显式手势或模型工具调用**；没有任何一家根据输入文本自动判定"这是个任务"。
> 证据：dsh HEAD `57190202`、opencode HEAD `0a46301e3`，行号相对各自仓库根。

---

## 1. dsh：输入 → 普通回合 → 三扇显式门

```
用户输入 ──▶ session.prompt(mode: queue|steer) ──▶ inbox.splice(durable)
        ──▶ wakeDriver ──▶ kick/turn/step（普通回合，02-报告 §1-§2）
```

普通回合之上，任务机制有三扇门，**没有一扇由输入解析触发**：

| 门 | 谁开 | 怎么开 | 效果 | 证据 |
|---|---|---|---|---|
| **plan 模式** | 用户 | `/plan` 命令（`command/run` name='plan'） | session 级模式：policy section + 限制工具；`/plan off` 或模型 exit 工具（带审批弹窗）退出 | `plan/plan-mode/src/index.ts:142-147,229-270` |
| **goal** | 用户 `/goal <objective>`，**或模型 `create_goal`** | 命令注册 `name:'goal'`（create/edit/pause/resume/clear）；模型工具 `create_goal`（工具描述：*"may infer goal intent from a direct human request in any language"*) | **create 即 armed**（`'…, 'armed')`）；goal-round-driver 在 idle 时自动续轮；装载/resume 后一律 disarm | `goal/command-goal/src/index.ts:20,143-157,191-193`；`goal/tool-goal/src/index.ts:116,208-225`；`goal/goal/src/index.ts:318`；05-报告 §2 |
| **todo_write** | 模型 | 回合中随手调用 | 事件进 UI、**不进请求**、下回合清空；**不触发任何驱动** | 05-报告 §3 |

**路由本质**：普通输入永远走普通回合；"升级为任务"的决策点在**用户命令**或**模型工具调用**（模型被提示词约束为"只在用户直接要求时才 create_goal"）。harness 不做输入意图解析。

## 2. opencode：输入 → 普通回合 → 两扇显式门

```
用户输入 ──▶ client 乐观入队 ──▶ POST prompt(delivery: steer|queue) ──▶ inbox.admit(durable)
        ──▶ wake/doorbell ──▶ drain/step（普通回合，03-报告 §1-§2）
```

| 门 | 谁开 | 怎么开 | 效果 | 证据 |
|---|---|---|---|---|
| **plan 模式** | 用户 | **切换 agent**（Plan agent，`session.agent.selected` 事件） | read-only agent + system-reminder 注入（*"You remain in Plan mode until the user switches agents"*）；压缩剥掉提醒后会重插 | `core/src/plugin/plan.ts:32-36,79-110`；06-报告 §1 |
| **命令层** | 用户 | `/compact` 等 slash 命令 | 控制项入 inbox，步边界执行 | 06-报告 §9 |

opencode **没有 goal、没有 todo**（v1→v2 删除）。任务机制只有"换 agent 模式"这一档，且明确是用户手势。

## 3. 我们的设计对照（11-plan 落地后）

```
用户输入 ──▶ session.prompt ──▶ _run_turn（普通回合；unarmed）
            模型 todo_write ──▶ 只建 items，不 arm，无驱动
任务机制唯一门 ──▶ 显式 /plan ──▶ arm(armed=True, profile="plan") ──▶ TaskDriver 驱动
启动扫描 ──▶ 只认 task.armed==true（不认 todo 是否 open）──▶ 日常会话永不被自动接管
```

| 维度 | dsh | opencode | 我们（11-plan） |
|---|---|---|---|
| 输入自动路由 | 无 | 无 | 无 |
| 进 plan 门 | 用户 `/plan`（模式切换，先规划后退出再执行） | 用户切 agent（模式切换，read-only 规划） | 用户 `/plan`（规划+执行一体，M1-A 既有决策） |
| 模型可发起任务化？ | **是**（`create_goal` 工具，提示词限"直接的人类请求"） | 否 | 否（v1 显式臂动；见观察项） |
| 重启后自动继续？ | 否（goal disarm；仅 schedule 提醒） | 是（claim+扫描，armed 等价物是"未完成执行"） | 是但受限（仅 armed 任务，显式同意的范围） |

**回答设计评审的问题**：不会"输入个任务就全进 plan 模式"。任务机制只在 `/plan` 显式臂动后生效；日常消息（哪怕内容像任务）永远是普通回合，模型建 todo 也不改变这一点。

## 4. 观察项（不进本次实施，记录待未来拍板）

1. **模型提议任务化**（dsh 的 `create_goal` 风格）：未来可做"模型建议 arm + 用户确认"的显式门，比 dsh 的全自动更保守。本次不做（11-plan §13 不做清单一致）。
2. **plan 的两种哲学**：dsh/opencode 的 plan 是"只规划的模式，执行前退出"；我们的 `/plan` 是"规划+执行一体"（M1-A 决策：两命令交接会走味）。保持现状；若未来觉得一体太长，可拆成 `/plan`（规划）与 arm 执行两个显式动作——属于产品语义选择。
