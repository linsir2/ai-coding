# dsh 学习笔记 05 · 与 ai-coding 对照与可迁移清单

> 目的：把 dsh 的 80% 认知价值**收敛成一份可执行清单**——哪些搬、哪些有条件地搬、哪些不搬，各自为什么。
> 立场：dsh 是"生产级 all-plugin harness"，ai-coding 是"本地交互式 CLI + 自持循环"。**形态不同，不是谁更好。**

---

## 1. 定位差异（决定"什么不能照搬"）

| 维度 | dsh | ai-coding |
|---|---|---|
| 形态 | 产品级 harness（Web/Desktop/Headless/SDK/ACP 多入口） | 本地交互式 CLI（Unix socket + bun 前端） |
| 语言/基座 | TypeScript + **Cordis 插件框架** | Python，**刻意无 agent 框架**（R1 决策） |
| 循环 | `agent-loop` 是**可替换插件**，实现零 loop 依赖的 `Agent` 接口 | `AgentLoop` 单类（1675 行），自持 |
| 会话 | **append-only 事件日志**，messages 是投影 | `SessionData.messages` 是**可变状态** |
| 规模 | 58 包、5101 .ts、2526 决策记录 | 单人维护，几十个模块 |
| 团队 | DeepSeek 官方团队 | 大二学生 |

> **结论**：dsh 的**架构规模**（58 包、Cordis、event-sourcing 全套）对 ai-coding 是**过度工程**；但 dsh 的**工程纪律**（决策记录、一种表示、结构不可表示、边界规则、依赖策略）**几乎零成本、可直接搬**。**搬纪律，不搬规模。**

---

## 2. 逐项对照

| 能力 | dsh | ai-coding | 判定 |
|---|---|---|---|
| 循环 | `agent-loop` 插件 + `Agent` 接口 | `AgentLoop` + `TurnPolicy` | **各有胜负**：我们的 `TurnPolicy` 是纯单元（19 条决策表），dsh 抽成接口。**不搬** |
| 会话 | append-only 事件日志 + `deriveMessages()` | `SessionData.messages` 可变状态 | **范式不同**（见 §3-D1） |
| 事件 | 三域 + 5 种派发（含 waterfall） | `core/events.py` + `LoopObserver`（仅 emit） | **可补** waterfall/serial |
| 工具分发 | 6 段流水线（pre-execute/guards/approval/execute/post-execute/finalize） | `ToolDispatcher` + gate + guard | **神似**；可补 pre/post 钩子 |
| 引擎端口 | `LlmAdapter`（成文十条契约）+ 可重建请求 | `ChatEngine`（`step()`） | **我们够用**；契约纪律可借鉴 |
| 压缩 | surface replace + 孤儿锁 + 影子定价 | 四层流水线（改副本） | **各有胜负**：我们的 L1–L4 顺序是不变量；它的可审计性更强 |
| 溢出 | spill（locator + retrievalHint + 0700） | L3 `persist_large_outputs` | **可借鉴** locator 不透明化 + best-effort |
| 子智能体 | provider 三角 + continuable + 父拥有 catalog | `SubAgentRunner`（同步+后台+worktree） | **我们更工程化**（worktree、结构化回包）；它多了 peer inbox + 冷恢复 |
| 审批 | fail-closed 封闭 outcome + 审计对 | `PermissionGate` + `ApprovalCallback` | **可搬** outcome 封闭化 |
| 沙箱 | 每调用策略 + denial vs runner-failure | `Sandbox`（工具内） | **可搬** 两分类器 |
| plan/todo/goal/schedule | **四个独立包** | `plan_runner` + `TaskState` 揉在一起 | **可借鉴** 拆分 |
| 记忆 | L0–L4 + 写入门 | 三层 + 对账式写入 | **我们更强**（对账式 ADD/UPDATE/SUPERSEDE） |
| 决策记录 | 2526 篇，固定格式，随代码更新 | `docs/r*-analysis.md` | **立刻搬纪律** |
| 观测 | OTEL + session-telemetry + 事件历史 | `core/trace.py` + `core/budget.py` | **我们够用**；它的事件历史=durable log 的副产品 |

## 3. 可迁移清单

### 档 A：立刻搬（零/低成本，高回报）

| # | 搬什么 | 怎么搬 | 为什么 |
|---|---|---|---|
| **A1** | **决策记录纪律** | 把 `docs/` 里的分析文档升级为"每决策一篇 + 固定格式（Problem/Decision/**Alternatives considered**/Consequences）+ 随代码更新事实"。含被拒方案是核心 | dsh 最值钱的东西不是任何功能，是**这套纪律**。我们已有 `r*-analysis.md` 的基因，只差制度化 |
| **A2** | **"结构上不可能 > 检测并上报"** | 审我们现有设计：哪些"违规"其实**可被构造**？能改成类型/结构上不可表示的，就改 | D1/D3/D5 的反复模式。例：`RestoreReport` 已朝这个方向走 |
| **A3** | **"消除重复真相"** | 审 `core/events.py` / `LoopObserver` / `trace` / `turn_digest`：**同一事实是否存在于两处**？durable 事实只该有一个位置 | D4 样板：dsh 删掉了四个边界镜像 |
| **A4** | **审批 outcome 封闭 + 类型级 fail-closed** | `ApprovalCallback` 的返回值从"宽松"改成**封闭枚举**（`allowed-once`/`rejected`/`cancelled`/`unavailable`），**非 `allowed-once` 一律拒绝**；无回调 → `unavailable` | dsh 的 `ApprovalOutcome` 让 fail-closed 是**类型级的**，不是靠调用方记得 |
| **A5** | **沙箱两分类器** | 区分"命令被沙箱**正确拦截**"（denial）与"沙箱 runner **自己坏了**"（runner failure）——**后者上报基础设施失败，绝不是任务失败** | 我们 R8c 的 Esc 处理已在朝这个方向；这是完整版 |
| **A6** | **`ContextForm` 语义词汇** | 注入上下文的类型只描述**语义**（instructions/catalog/snapshot/notice/relay/recall），**外观（颜色/图标/排序/折叠）归消费者** | "词汇是语义的，永不是视觉的"——防止类型层混入表现层 |
| **A7** | **依赖策略（有门槛）** | 把"能自己写就不加依赖"的隐式反射，改成**显式策略**：净删除 / 健康 / 边界契合 / 非已定接缝 | D7 的根因诊断直接命中我们："隐式规则比任何人决定过的都更严" |
| **A8** | **"不可信输入不选路由"** | 写进 guard 设计：**模型/用户输入不得选择 Session/租户/沙箱路由** | D8 的安全不变量 |

### 档 B：需要条件（有前置，收益大）

| # | 搬什么 | 前置 | 成本 |
|---|---|---|---|
| **B1** | **请求可重建**（Model-visible ⟺ logged） | 需要先有**日志层**（哪怕不是完整 event-sourcing） | 中-大：给会话加"请求头快照"事件 |
| **B2** | **消息身份在创建时铸造** | 需要把消息从裸 dict 升为有 id 的不可变值 | 中：`ChatMessage` 加 id + 创建/导入两个边界 |
| **B3** | **工具流水线 waterfall** | 现有 `ToolDispatcher` 可加 pre/post 钩子 | 中：把 guard 链升级为可包装/可否决 |
| **B4** | **plan/todo/goal/schedule 拆分** | 现有 `plan_runner`+`TaskState` 需解耦 | 中：拆成独立单元 |
| **B5** | **spill locator 不透明化 + best-effort** | 现有 L3 落盘 | 小：把路径改成品牌不透明值 + 检索提示 |

### 档 C：不搬（形态不匹配，不是"不好"）

| # | 不搬什么 | 理由 |
|---|---|---|
| **C1** | **Cordis 插件框架全套** | TS 的 DI/插件框架，Python 无对应；引入等于重写整个装配层。**但 `inject`（依赖驱动加载）的*思想*可借鉴**——用 Python Protocol + registry 近似 |
| **C2** | **58 包拆分** | 对单人项目是过度工程。**但"按变化速率拆"的原则**可局部应用 |
| **C3** | **surfaceOp 机制** | 只在完整 event-sourcing 下需要。我们不做 event-sourcing 就不需要 |
| **C4** | **profile/bundle/patch/HMR** | 本地 CLI 不需要运行时可组合的插件树 |
| **C5** | **完整 event-sourcing 重写** | 太大，且我们 R1 刻意选了自持循环 + 可变会话。**但 D1 的*心智*（日志当真相源）值得部分吸收** |
| **C6** | **AsyncLocalStorage initiator scope** | 我们用显式传参即可；ALS 是 JS 特有，且 dsh 自己也说"环境存在非授权" |

---

## 4. 一句话总结

> **dsh 教我们的不是"用它的架构"，而是"用它的纪律"**：把每个决策连同被拒方案记下来（A1）、让违规在结构上不可能（A2）、消除重复真相（A3）、失败关闭且类型级（A4）、词汇只描述语义（A6）、依赖有门槛（A7）、不可信输入不选路由（A8）。
>
> 这些**几乎零成本**，且**不依赖任何 dsh 的代码**。真正的架构规模（Cordis、58 包、event-sourcing）**不是我们要搬的**。
