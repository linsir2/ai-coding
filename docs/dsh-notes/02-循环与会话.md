# dsh 学习笔记 02 · 心脏：循环与会话

> 来源：`docs/subsystems/core.md`、`docs/subsystems/session.md`、`docs/tool-execution-pipeline.md`、`docs/architecture.md`。
> 本篇是整个系列最重要的一篇：**会话日志 = 唯一真相源** + **turn/step 生命周期** + **工具流水线**。

---

## 1. 脊柱：一次 turn 穿过六个包

`docs/subsystems/core.md:9` 给出的一句话：

> driver（`agent-loop`）认领一条排队 prompt → 在 session log（`ctx.sessions`）上开一个 turn → 经 `system-prompt`（`ctx.systemPrompt`）装配请求前缀、从日志派生历史 → 经 LLM seam 流式取模型响应 → 经工具注册表（`ctx.tools`）派发工具调用 → **把每个 model-visible 事实追加回日志**，下一个 step 再从它派生。

| 包 | 拥有 | `ctx` key |
|---|---|---|
| `core/session` | append-only 的 `SessionEvent` 日志 + 内存 store（唯一真相源） | `ctx.sessions` |
| `core/system-prompt` | prompt 分节 + 工具 schema 装配 | `ctx.systemPrompt` |
| `core/tools` | 作用域化工具注册表 + 受门控执行流水线 | `ctx.tools` |
| `core/agent` | `Agent` 接口、活体注册表、initiator scope、`agent/*` 事件 | `ctx.agents` |
| `core/agent-loop` | 实现 `Agent` 契约的具体驱动器 | `ctx.agentLoop` |
| `core/scope` | 作用域注册原语（**唯一的非服务包**，无依赖库） | 无 |

> **`agent-loop` 只是 `Agent` 契约的一个实现**。扩展插件依赖 `agent`，**从不依赖 `agent-loop`**，所以循环可换。`scope` 放在模块图 `session`/`system-prompt` 之下，正是为了让它们能消费它而不成环。

## 2. 会话 = 事件溯源的 append-only 日志（最核心）

> A `Session` is an **append-only log** of typed `SessionEvent`s — the single source of truth. The LLM message history is *derived* from the log, never stored separately; replay is re-derivation from the same events.

### 2.1 `SessionEventMap`：13 个核心事件变体（+ `developer/message`）

`docs/subsystems/session.md:27`。**merge-extensible**（插件用 declaration merging 加自己的事件）：

| 事件 | 性质 | 说明 |
|---|---|---|
| `turn/start` / `turn/end` | durable 边界 | `turn/end` 带 `TurnEndReason`；无 step 的 turn 没有 `step/*` |
| `step/start` / `step/end` | durable 边界 | step = 一次模型调用 + 它请求的工具执行 |
| `user/message` | **surface** | 直接人类 prompt / `agent.inject()` 上下文 / goal 续跑；`source` 区分 |
| `developer/message` | **surface** | 增量 agent 会话变更 |
| `system/message` | **surface** | 渲染后的系统提示（surface node 0） |
| `assistant/message` | **surface** | 组装后的 assistant 消息；**内嵌 provider 流**；带 `usage` |
| `assistant/attempt` | log-only | 未提交 surface 消息的一次模型尝试（失败/重试/取消/流错误），**保留内嵌流但不伪造模型历史** |
| `tool/call` | log-only | 模型请求一次工具调用（`callId` 配对） |
| `tool/result` | **surface** | 完成的工具结果 + 可选内部失败身份 `error` + 工具私有 `meta` |
| `request/header` | log-only | 下一个请求的完整头（`EpochHeader`：call config + 工具 schema） |
| `request/context` | log-only | 路由元数据（provider/model/capacity/systemPromptUpdate） |
| `session/end-seed` | log-only | 分隔"继承/恢复的历史"与"本生命周期拥有的工作" |

### 2.2 `SessionEvent` 信封

```ts
type SessionEvent<T> = {
  [K in SessionEventType]: {
    type: K
    seq: SessionSeq      // 单调序号，seq = log.length（连续性契约）
    time: number         // epoch ms
    data: SessionEventMap[K]
    ignorable?: true     // 读者可安全跳过的标记；缺席 = required（不认识就拒读）
  } & (K extends SurfaceEventType ? SurfaceIntent<K> : { surfaceOp?: never; sourceEventSeqs?: never })
}[T]
```

**`ignorable` 的默认是"required"**——一个忘记标 `ignorable` 的纯信息记录会**过度拒绝**（不便），而不是**静默恢复一个被掏空的会话**（危险）。这是刻意的失败方向。

> 因为 `SessionEventMap` 可 merge，**switch 不能用 `assertNever`**——插件加的变体是合法未知值，处理已知 case 后 `default` 落下。

### 2.3 Surface 类型与 `SurfaceOp`（如何进入有序 surface）

只有这五个是 **`SurfaceEventType`**（产生 LLM 消息）：`system/message`、`developer/message`、`user/message`、`assistant/message`、`tool/result`。

```ts
type SurfaceOp =
  | 'append'                                          // 尾追加（普通路径）
  | { op: 'replace'; startSeq; endSeq }               // 遮蔽 [start,end] 闭区间并就地插入
```

- **每个 message-producing 事件必须声明 `surfaceOp`**——surface 是派生模型历史的**唯一来源**。
- `replace` 用于**压缩**：把一段被摘要遮蔽的 surface 节点替换成一个。
- `assistant/message` **不能**带 `sourceEventSeqs`（它的内嵌流就是精确证据）。

### 2.4 `deriveMessages()`：从日志派生模型历史

**cached**（每个 surface 节点只在首次见到时投影一次；surface 重写才重建）、**frozen**（每次调用返回新数组，但里面的 `Message` 是共享且**深度冻结**的）。投影规则：

- `user/message` → user 消息，携带精确 `content`
- `assistant/message` → assistant 消息；**空内容的会被跳过**（max-tokens 截断仍记 `assistant/message` 以承载流/usage，但无内容的 assistant turn 不得进入 provider transcript）
- `tool/result` → 一等 tool-role 消息
- 其余（`turn/*`、`step/*`、`assistant/attempt`）是结构性的，**不投影成消息**

> **可重建性**：`deriveEventMessage(event)` 是逐节点纯函数，**公开**——外部重建器用完全相同的规则投影日志前缀，**不可能与缓存不一致**。

### 2.5 `request/header`：请求是日志的纯函数

> The request envelope — the `EpochHeader` — is logged session state, so **every conversation request is a pure function of the log**.

**渲染后的系统提示不是 header 的一部分**——它是派生历史（`system/message` 在 surface node 0）。所以改 prompt = 替换/追加 system node，**header 不变**。

- `reason`: `initial` / `resume`（每个 loop 实例边界）、`change`（变了）、`series`（未变但显式开新消息系列）。
- `foldRequestHeader(events)` 取最新快照重建 header。

### 2.6 `TurnEndReasonMap`：turn 为什么结束

`completed` / `aborted{reason}` / `blocked` / `error{error}` / `max-tokens` / `interrupted`（崩溃孤儿，resume 时补记）/ `forked`（fork 边界补记）。

- **`max-tokens` 胜过 `completed`**：任何 step 触顶 → 整个 turn 记 `max-tokens`（截断事实胜过后续续跑），消费者能分清"干净停止"与"被截断"。
- **`interrupted`/`forked` 永不由 loop 实时发出**——分别由崩溃恢复、fork 构造合成。

### 2.7 fork

`ctx.sessions.fork(source, boundary?, childSessionId?)`：从源会话的**闭区间边界**（默认最后一个事件）选事件，**要求前缀结束在一个 turn 之外**，否则拒绝（不静默裁剪）。子会话带 `parentSession`、`isSeeded: true`、精确 `inheritedEventCount`、继承 `cwd`。

### 2.8 插件可加事件

- **log-only 事件**（非 Surface）：插件 merge `SessionEventMap`，owner 决定它属于某个开放 turn 还是可站在 turn 之间。
- **`plugin:` 命名空间记录**（实验性）：`appendPluginRecord()`，标 `ignorable: true`。

## 3. Agent handle：面向所有插件的表面

`Agent` 是 UI/hook/orchestrator 编程所对的表面。**具体实现是 `dsh-agent-loop` 包内私有的**。

```ts
interface Agent {
  readonly id: SessionId
  readonly options: AgentOptions
  readonly session: Session          // 活体会话；其日志是 durable 真相源
  readonly inbox: Inbox              // agent 拥有的待处理工作
  readonly status: AgentStatus       // 'idle' | 'running'
  readonly ctx: Context              // agent 作用域上下文

  cancel(cause: AgentCancelCause, options?: CancelOptions): void
  whenIdle(): Promise<void>
  runMaintenance<T>(task: (signal) => Promise<T>): Promise<T>

  send(message: UserMessage, target: InboxTarget, wakeup: boolean): void
  followup(message: UserMessage): void   // 排一个普通后续 turn 并唤醒
  steer(message: UserMessage): void      // 提交给最近一个 step
  inject(message: UserMessage): void     // 排模型可见上下文，不唤醒
}
```

- **`send` 是统一入口**（目标 + 唤醒路由）；`followup`/`steer`/`inject` 是固定预设的别名。
- `cancel(cause)`：清空排队/转向工作（除非 `keepInbox`）并中止活动 turn；**首个 cause 胜出**。
- **`AgentStatus`**：`idle`（无 driver 活动）/ `running`（driver 排空区间，**可跨连续 turn**，不证明某个 turn 仍开着）。disposal 不是第三种状态。
- **`withInitiator(agent, op)`**：把某个异步 driver 链的**因果归属**绑到一个精确 `Agent`。**环境存在既非存活证明也非授权**。

### Inbox：两条有序待处理列表

```ts
type InboxTarget = 'next-turn' | 'next-step'
interface Inbox {
  readonly nextTurn: readonly UserMessage[]
  readonly nextStep: readonly UserMessage[]
  clear(): void
  append / prepend / replace / remove / splice(...)
}
```

- 每个待处理项就是它的 `UserMessage`，`MessageId` 是唯一身份。
- 结构方法记录规范化的 durable `agent/inbox/spliced` 变更，**拒绝重复 pending id**。
- 在 step 边界，`ReactLoopInbox` 移除提议批次（所有 `next-step` + 边界处的**一条** `next-turn`），然后发逐条 claimed 通知。

## 4. turn/step 生命周期

- **step** = 一次模型请求 + 其响应触发的工具执行
- **turn** = 零或多个 step：在第一次 input 被 claim 前打开，在"没有任何欠账"时关闭

### 两个关键 waterfall

**`agent/pre-step`（waterfall）**：决定接受什么输入。listener 可 rewrite 或 reject 被 claim 的消息；reject 或首个 claim 为空 → **无 step 关闭一个 durable turn**。`enter` 决策可设 `startsRequestSeries`（开一个新的消息系列）。

```ts
type PreStepDecision =
  | { kind: 'reject' }
  | { kind: 'enter'; messages: UserMessage[]; startsRequestSeries?: true }
```

**`agent/request`（waterfall）**：替换冻结的 call 配置。`await next()` 得到机器本会用的配置；返回替换即切换路由。**在装配和 `step/start` 之后、系统提示与接受的 user 批次提交之前**运行。此处的取消（或后续 `prepareCall()` 期间的取消）**两者都不提交**。

### 三个"不变量"要点

1. **重试不重跑装配、不重跑 `agent/pre-step`**（`architecture.md:110`）。
2. 首个被 admit 的 step **先占系统头**，即使 prompt 为空（不发线消息）。
3. **取消的语义**：prepared call 能力管辖 prompt 准入；`request/context` 是更早请求的快照，**不参与** header 重建。

## 5. 工具执行流水线（不改循环就能加策略）

`docs/tool-execution-pipeline.md` 给出完整 mermaid。按顺序：

```
模型产出 tool-call block
  → tool/call（执行前就记日志）
  → UI pending card (presentCall)
  → tools/pre-execute waterfall   ← hooks、permission、sandbox
       allow → guards
       deny  → denied
       ask   → ctx.approval（一次性询问；缺席/无法回答 = deny）
  → 注册的单调 guards（deny 或 abstain；身份受保护）
  → tools/execute waterfall       ← timeout、retry、metrics（围绕派发）
  → 工具 execute() 本体
  → fs/write-intent 或 fs/edit-intent（仅 tool-fs 变更）
  → 工具自有的 session 事件（todo/write、fs/observed、hook/invoked、hook/result、tool/ptc-dispatch）
  → ToolDefinition.projectContent（执行准备好的文本与图像）
  → tools/post-execute waterfall  ← accept、block、replace、add context
  → registry 外层规范化（snapshot 失败 → isError）
  → ToolDefinition.finalizeContent（最后的内容不变量）
  → tools/result 同步通知（冻结的权威结果）
  → 活动批次的 additionalContexts FIFO（在记录的 tool result 之后注入 user/message）
  → tool/result session 事件（唯一的模型可见结果）
  → 批次结算完成 → UI completed card (presentResult)
```

关键设计（`tool-execution-pipeline.md:63`）：
- **审批在单调 guards 之前**解决 asks；**不能被重排的 owner 策略保留为注册 guard**。
- 超时这类"围绕派发"的关切**包住** `tools/execute`。
- registry **无损快照**候选结果，并在可见定义的 `finalizeContent` 之前规范化快照失败。
- **让 hook 横跨工具族，而不让工具耦合到某一个策略服务。**

## 6. 两个贯穿全仓的类型模式

### 6.1 `…Map → derived-union`（可扩展和类型的唯一写法）

```ts
interface ThingMap { 'a': { kind: 'a' }; 'b': { kind: 'b' } }
type ThingKind = keyof ThingMap          // 'a' | 'b'
type Thing = ThingMap[keyof ThingMap]    // 判别联合
// 插件扩展：declare module '@deepseek-ai/dsh-llm' { interface ThingMap { 'c': {...} } }
```

五个规范 map：`ContentBlockMap`、`MessageSourceMap`、`FinishReasonMap`（dsh-llm）、`TurnEndReasonMap`、`SessionEventMap`（dsh-session）。

### 6.2 Branded IDs（跨包 id 不可互换）

```ts
type Branded<B extends string> = string & { readonly [BRAND]: B }
```

结构上是 string，但**类型上不可互换**（`SessionId` 不能当 `ToolCallId` 用）。构造用 `brandString<T>()`；比较/日志/JSON 与普通 string 无异。

## 7. 对照 ai-coding

| dsh | ai-coding | 差距 |
|---|---|---|
| session = append-only 事件日志，`deriveMessages()` 派生 | `SessionData.messages` 是**状态**，压缩直接改它 | **根本不同**：我们没有"日志"层，无法纯函数重建请求 |
| `SurfaceOp.replace` 做压缩遮蔽 | 压缩直接替换 messages 列表 | 它的压缩是**日志里的一次可审计操作** |
| `request/header` 让请求是日志的纯函数 | 无 | 我们无法从会话文件重建"当时发了什么" |
| `assistant/attempt` 保留失败尝试的流 | 失败即丢 | 它保留**非模型可见的尝试证据** |
| `ignorable` 默认 required | 无版本化事件契约 | 它的会话格式有迁移链 |
| `Agent` handle + inbox(next-turn/next-step) | `AgentLoop.process_input` 直接进循环 | 它的投递是**有界、幂等、可分目标**的 |
| `pre-step` / `request` waterfall | 无拦截点 | 它把"拒绝一步""换路由"做成可插拔 |
| 工具流水线（pre-execute/guards/approval/execute/post-execute/finalize） | `ToolDispatcher` + gate + guard | 结构神似，但它把每一步都做成 waterfall，**hook 横跨工具族** |
| `…Map → derived-union` + branded id | 直接用 `str`/`dict` | 类型安全纪律强得多 |
| `scope`（两级扁平，子树用 lineage 数据） | 无 | 避免作用域继承复杂度 |

> **本笔记最重要的结论**：ai-coding 的 `SessionData.messages` 与 dsh 的 **event log** 是两种范式。前者把"模型看到的历史"当**可变状态**，后者当**从不可变事件派生的投影**。后者的代价是"加任何 model-visible 输入都要新增事件类型"，收益是 fork/resume/压缩/审计全部免费且可重建。**这是 05 篇对照的核心议题。**
