## 主题一：上下文（compaction / spill / image offload）

### 1.1 compaction 是**接缝**，不是循环的一部分

`compaction` 拆成三角（像 bash）：Service Definition（`dsh-compaction`，`ctx.compaction`）/ Provider（`dsh-compaction-basic`）/ 人类 Consumer（`dsh-command-compact`）。**是可选能力，不在 agent-loop 脊柱上**——所以它的词汇住在自己页里，不进 `core.md`。

### 1.2 压缩 = 日志里一次可审计的 surface 替换

`compaction` 用 declaration merging 给 `SessionEventMap` 加**三个 log-only 事件**：

| 事件 | 作用 |
|---|---|
| `compaction/start {turn}` | **获取日志记录的锁**（数字=自动 turn，`null`=手动独立尝试） |
| `compaction/summary {...}` | 安全摘要投影 + 可选完整 provider 输出 + usage + **被遮蔽的 surface 边界对 + 被遮蔽 seqs + token 估算** + 摘要调用的信封（provider/model/maxTokens） |
| `compaction/end {turn, error?}` | 释放锁 |

**锁的括号包住整个操作**：start 先落 → 摘要 → summary 记录 → `user/message` 替换 → 最后 end。**最后释放锁**把"操作中途崩溃"变成**可检测的孤儿锁**（有 start 无 end），而不是一个**谎称压缩完成**的 end。

**摘要本身骑在一条独立的 `user/message` 上，带 `surfaceOp: { op:'replace', startSeq, endSeq }`**——这是 summary 压缩**唯一**的 surface 变更。`SurfaceEventType` **刻意不被扩展**（只有 message-producing 事件到达模型）。

> `shadowedRange` 是 **surface 位置跨度，不是数值 seq 区间**：先前的 replace 可能把一个高 seq 的 summary 节点落在旧 range 的位置上，所以 `start` 可能**大于** `end`。`shadowedSeqs` 才是权威集合。

### 1.3 三种触发 + 恢复

```ts
type CompactionTrigger = 'pressure' | 'context-overflow'
```

- `compactIfNeeded(agent, trigger, signal)`：自动策略（pressure 或 provider 确认的 overflow）。
- `compactNow(agent, signal)`：即使低于阈值也做一次有用的缩减（`/compact`）。
- `compactRegion(start, end, ...)`：显式闭区间 surface 范围。

**pressure 压缩在 `agent/pre-step` waterfall、请求派生之前运行**。失败请求恢复走 `agent/request-error`，**仅当 surface 替换代数前进时才返回 retry**。区域边界**保留 tool-call/result 配对但不保留整个 turn**——允许压缩一个超大 turn 的早期已关闭 step。

`ManualCompactionErrorCode`：`busy` / `cancelled` / `changed` / `summary` / `commit` / `persistence`。

### 1.4 工具结果剪枝（tool-result pruner）

可选服务，确定性头/中/尾剪枝当前 tool-result surface 节点。`pruneContent` **按 Unicode 码点切**（不是 UTF-16 码元，避免切裂 surrogate pair）。每个替换**保留除 `content` 外的完整事件数据，并引用被遮蔽节点**，且**紧邻一个 `compaction/prune` 影子定价事件**（用注入的 token meter 定价），使纯消费者能直接相减而无需逐节点状态。

### 1.5 spill（溢出存储）—— 你的 L3 落盘的正主

`spill` 是接缝：`ctx.spillStore.saveText(input) → SpillRef`。**存全文、返回不透明 locator + 精确字节数 + 检索提示**。

- `SpillLocator` 是 **branded** 模型可见句柄；本地后端渲染成文件路径，远端后端可渲染成 URI/key/token。**消费者当它不透明**，用 `retrievalHint` 渲染，**不假设 `read` 永远是对的检索方式**。
- 本地后端写 `<root>/session-<hash>/<random>-<safeName>`，私有 0700 根，`sha256(sessionId)` 子目录，**独占 owner-only 写（`open(path,'wx',0o600)`）**——防预埋 symlink 重定向。
- **seam 只管存储**：无保留策略、无工具结果替换、无检索 API。
- **policy consumer（`dsh-spill-policy`）best-effort**：save 失败就保留原始内联结果，**不把一个成功调用变成 isError**。

## 主题二：多智能体（subagent / agent-team）

### 2.1 一个统一激活 API 管本地与外部

`SubagentManager` 拥有启动、消息准入、执行生命周期。Provider 分两类：
- **Spawn / Fork**：贡献"分离的创建输入"给本地 Agent（`prepareContinuable`）。
- **Codex / Claude Code / ACP / DSH SDK**：贡献**一个执行句柄**（`start`），**不获得多轮**。

> **provider 对 continuable 子 agent 的唯一参与**就是 `prepareContinuable` 返回一个 `ContinuableCreateSpec`（只有"是否用父历史播种"）。**continuation manager 拥有身份预留、组合、Agent 创建、prompt 投递、冷恢复、所有权、销毁**——provider **永远看不到**子 agent 的 Agent/handle/turns/teardown。

### 2.2 关键类型

```ts
interface SubagentCapabilities { agentOptions; agentPreset; outputSchema; depthLimit }
interface SubagentActivationSpec { provider; label; childId?; request; signal; delivery: 'parent'|'caller' }
interface SubagentActivation { childId; messageId?; result: Promise<SubagentResult>; dispose() }
```

- `delivery: 'parent'` 通知模型；`'caller'` 只返回结果。**本地子 agent 永远进入父目录**。
- `SubagentResult`：`output`（最后一条非空 assistant 消息内容）+ 可选 `structured` + 可选 `diagnostic`（**限 4096 UTF-8 字节**，provider 须剔除工具输入/文件内容/环境值/凭据/原始协议载荷）+ `stopReason`。
- `SubagentStopReasonMap`：`completed` / `aborted` / `error` / `max-tokens` / `refusal`——**镜像 turn-end 词汇**，让工具层把非 completed 映射成 `isError`。

### 2.3 两条消息来源（刻意区分）

```ts
interface AgentMessageSource { kind: 'agent-message'; form: 'relay'; senderSessionId }   // agent 自己选的内容
interface SubagentSettledMessageSource { kind: 'subagent-settled'; form: 'notice'; summary; senderSessionId }  // 运行时对"子 agent 怎么了"的陈述
```

> **故意不同 kind**：合并它们会把子 agent 从未写过的词归功于它。

### 2.4 父子通信 + 中断 + 目录

- `sendMessage(sender, targetId, content, options)`：**只允许相邻本地 agent**。运行中的子 agent 收到 steering；缺席的 continuable 子 agent 从持久化冷恢复。**外部执行拒绝 follow-up**。
- `interrupt(targetSessionId, authority)`：authority 是 `{kind:'user', parentSessionId}` 或 `{kind:'ancestor', agent}`。**fire-and-return**（取消信号已发，目标可能还在跑）。
- `listChildren(parentSessionId)` / `listDescendants(rootSessionId)`：读**父拥有的 catalog 投影**，**不加载/恢复任何 Agent**。外部子 agent 是叶子；unknown mode 产生 `unsupported` 诊断；不可读的子 catalog 产生 `corrupt`/`unavailable` 并**只停那一个分支**。
- **Agent Teams**（实验性，`ctx.agentTeams`）：隐式 Lead 身份、命名可继续队友、直接 peer inbox 投递、共享 task DAG。经可继续 subagent 之上实现。

## 主题三：安全（approval / sandbox / permission-presets）

### 3.1 approval：一次性、失败关闭

```ts
type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'   // 封闭、fail-closed
```

- **只有 `allowed-once` 是授权**；`rejected`/`cancelled`/`unavailable` 调用方一律拒绝。**缺席、非拥有、抛异常、不合规的 answerer → `unavailable`**，而不是开门。
- `ApprovalPolicy`：`ask`（默认，委派给组合的 answerer 链，无 answerer 落到 fail-closed 的 `unavailable`）/ `never`（**确定性返回 `rejected`，不派发任何 answerer**——CI/无人值守的严格姿态）。
- **策略在服务内部、waterfall 派发之前执行**，所以**后注册带 `prepend` 的 answerer 也无法绕过 `never`**。
- `ApprovalRequest` **刻意省略工具参数**：answerer 通过 `callId` 把提示附到**已经流式发出的工具调用**上，而不是渲染第二份可能漂移的副本。
- **审计对**：`approval/asked` + `approval/decided`（log-only，不进模型 transcript）。`request` **要求请求会话在开放 turn 内**（审计对必须被 durable 日志的提交/重放边界包住）。
- `approval/request` 是 **waterfall**：answerer 返回 outcome 即认领，或 `next()` 委派；**第一个答案占据唯一决策槽**。

### 3.2 sandbox：每调用策略、失败关闭

```ts
type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'
type SandboxEnforcement = 'full' | 'partial'
```

- **只治理文件效果**；网络与进程可见性**不在**这个词汇里。
- **策略按调用携带**（`SandboxPolicy`），不固定在 provider 上——**同一瞬间两个消费者可在不同策略下受限**，且"已批准升级重试"是**一个更宽策略的新调用**。
- **强制是"报告的事实"**：`full` = 治理模式承诺的每个文件效果；`partial` = 后端或旧内核 ABI 只治理子集——**要求绝对边界者必须拒绝或显式区分**。
- **`ConfinedArgv` 带两个正交的 stderr 分类器**：
  - `denialSignatures`：受限命令**被正确拦截**（后端特定的 EROFS/EACCES/EPERM 方言）。
  - `runnerFailureRules`：沙箱 runner **在执行命令之前就失败**——消费者**先查这个**，上报**沙箱基础设施失败，绝不是普通任务失败**。
- **`confine` 必须返回强制 argv 或在 wrap/runner 执行时失败关闭；静默不限制直通对受限策略永远非法。**

### 3.3 permission-presets

`PresetSpec`/`PresetOption` + 派生的 `custom` 状态 + **log-only 的 `permission/preset` 事件**。

## 主题四：任务/目标（plan / todo / goal / schedule）

四件事**分成四个包**，各自独立：

### 4.1 plan —— **软指导**，不是强制

- `plan/mode {active}` 是 **log-only、整值替换**的 session 事件（durable、可重放，**永不进模型 transcript**）。
- **plan 是软指导**：`sandbox` 与 `approval` **独立强制**限制，**都不读写 plan 状态**。活跃时渲染 `plan:policy` prompt 分节（order 50）。
- `exit_plan_mode` **在非 plan 模式也保持注册**——进出 plan 只改 prompt 分节，**永不改请求工具目录**。
- **每个 session 事件是 turn-enclosed 的**，所以**开放 turn 期间**用户选择保持 pending，直到下一个被接受的 in-turn pre-step 在请求派生之前追加它。唯一追加点是**前置的 `agent/pre-step` listener**（先调下游，它们接受后再追加）。**turn 之间则立即追加**（不会再有 in-turn pre-step）；`set()` 返回 `committed`/`queued`/`cancelled`/`noop`。
- `/plan [off|message]`：裸 `/plan` 选 plan 模式；其他消息选它并经 `agent.steer()` 提交。

### 4.2 todo —— 极简、整表替换

```ts
interface TodoItem { content: string; status: 'pending' | 'in_progress' | 'completed' }
```

> **刻意极简：无 id、无 priority、无 activeForm**——列表每次写入**整体替换**（last-write-wins），所以条目**不需要稳定身份**。

`todo/write: { todos: TodoItem[] }` 是 log-only 事件，携带完整替换列表。

### 4.3 goal —— 同会话目标，状态非调度器

```ts
interface GoalRef { id: GoalId; revision: number }              // CAS 身份
type GoalPhase = 'active' | 'paused' | 'blocked' | 'complete'   // durable 相位
interface GoalBlockReason { code: string; message: string }     // blocked 的原因
interface GoalSnapshot { ...; maxGoalRounds: number }
```

- **durable 相位**回答"目标发生了什么"；**进程本地激活（activation）**单独回答"继续消费者能否再开一轮"。**activation 是 `armed`/`disarmed`，刻意不进 durable 重放**——所以 resume/fork 需要后续**人类授权的 resume 变更**才能自动干活。
- 每次变更是一个 durable `goal/change` 事件（完整快照或 clear 墓碑）。**只有被 admit 的 `user/message` 推进 `roundsStarted`**。
- **goal 是状态，不是调度器或独立会话**；session log 仍是其真相源。

### 4.4 schedule —— 宿主级提醒

- **独立于 Session 激活**存储，投递到原 Session。version-1 `schedule` storage domain 拥有 `tasks` 表。
- 记录变体：`after`/`at`/`every`/`daily`/`weekly`/`cron`。创建把目标规范化成 RFC 3339 UTC `scheduledAt`——**重放永不依赖环境时区状态**。
- **必须有 `title`**（trim 后非空、≤120 字符）；缺失/空白/超长在**解码时**以 `ScheduleLogError` 拒绝——**domain 声明没有 backup-and-skip 策略，所以一条坏记录拒绝整个 domain open**，而不是被丢弃。
- 委托子 agent 拥有的 Session：create/update 以 `subagent_session` 拒绝（投递永远到不了它），但 delete 仍可。
- **一个 Host 级 FIFO 队列串行化变更与到期投递**；删除任务不撤销已排队消息。

## 主题五：LLM 接缝（llm-streaming）

### 5.1 内容与消息

```ts
interface ContentBlockMap {
  'text'; 'reasoning'; 'image'; 'file'; 'tool-call'; 'tool-addition'; 'tool-removal'
}
```

- 工具结果是**一等 `ToolResultMessage`**（有 `toolCallId`/`content`/可选 `isError`），**不是 content block**。
- `MessageSourceMap`：`user`/`model`/`tool`/`system-prompt`（merge-extensible，**没有共享的 catch-all `plugin` kind**）。
- **`ContextForm`**（`instructions`/`catalog`/`snapshot`/`notice`/`relay`/`recall`）是**语义的、永不是视觉的**——颜色/图标/排序/折叠默认值是**消费者的事**，不得进入这个 union。

### 5.2 `StreamChunk` —— **封闭**联合

```ts
type StreamChunk =
  | { type: 'block-start'; index; blockType }
  | { type: 'text-delta' | 'reasoning-delta'; index; text }
  | { type: 'tool-call-delta'; index; id; name?; argumentsDelta }
  | { type: 'block-end'; index; block: ContentBlock }
  | { type: 'usage'; usage }
  | { type: 'finish'; reason; replayState? }
```

> **封闭**联合：switch 以 `assertNever` 结尾——加变体会在**每个必须处理的消费者**处编译失败。（对比 `SessionEventMap` 是 merge-extensible，所以不能 assertNever。）

### 5.3 adapter 契约（每条都被消费者依赖）

- **`usage` 在 `finish` 前，`finish` 后什么都没有。**
- **tool-call `arguments` 端到端保持原始 JSON 字符串。**
- **两条受认可的错误路径，一个 `LlmFailure` 类型**：从 `stream()` 抛，或以 `finish {kind:'error'|'aborted'}` 结束。
- **一次 adapter 调用 = 一次 provider 尝试**（adapter 禁用库重试；agent 级恢复开另一个 durable 编号 turn）。
- **provider 卡顿在传输层有界**：`streamIdleTimeoutMs` 默认 5 分钟，watchdog 只在 `next()` 未决时武装。
- **上下文超长有唯一规范码**：`CONTEXT_WINDOW_EXCEEDED`——消费者**按码路由，绝不按 provider 文本**。
- **空 completion 是可重试错误，不是静默成功**：`EMPTY_RESPONSE`。
- **replay state 是 adapter 私有的；其"分割"是共享的**：`ReplayEnvelope {response; blocks?}`，per-block 条目与发出的 block 序列对齐——**assembly 丢弃一个 block 就在同一位置丢弃条目**，所以存储的元数据永远描述存储的内容。

### 5.4 `TokenUsage` —— 计数是**互斥**的

```ts
interface TokenUsage {
  inputTokens; outputTokens;          // inputTokens 是"未缓存输入"
  totalTokens?;
  cacheReadTokens?; cacheWriteTokens?;   // 计费输入 = 三者之和
  reasoningTokens?;                     // 已含在 outputTokens，别再加
}
```

> provider 把 cache 命中折进单一 prompt total 的（DeepSeek 的 `prompt_tokens`），adapter **减回去**。

### 5.5 `GenerateOptions` + 请求可重建

`GenerateOptions` 是**完全装配后**的一次模型请求。**loop 从 logged 状态构建每个请求**：

- `EpochHeader` 记 call config + adapter 默认标记 + 权威工具顺序。
- **渲染的 prompt 是派生历史**（`system/message` 在 surface node 0），所以 header + 派生历史**一起**让请求从日志可重建。
- **`systemPromptUpdate: 'in-history'`**：模型把 `messages` 任意位置的**最新** system 消息当作完整有效 prompt——**所以 loop 可以在缓存历史之后追加改变的 prompt，而不是重写 message 0**（缓存友好）。

`FinishReasonMap`：`stop`/`tool-calls`/`max-tokens`/`aborted`/`error`（merge-extensible）。

## 主题六：对照 ai-coding（速览，详见 05）

| dsh 子系统 | ai-coding | 差距 |
|---|---|---|
| compaction（surface replace + 孤儿锁 + 影子定价） | `ContextManager` 四层压缩（改 messages 副本） | 它的压缩是**日志里可审计的一次操作** |
| spill（locator + retrievalHint + 0700 + best-effort） | L3 `persist_large_outputs`（落盘 + 标记） | 它把 locator 做成**不透明品牌**，检索方式由提示给 |
| subagent（provider 三角 + continuable + catalog） | `SubAgentRunner`（同步+后台，worktree，结构化回包） | 它有 peer inbox + 冷恢复 + 父拥有目录 |
| approval（fail-closed 封闭 outcome + 审计对） | `PermissionGate` + `ApprovalCallback` | 它的 outcome 封闭且 fail-closed 是类型级的 |
| sandbox（每调用策略 + denial vs runner failure） | `Sandbox`（工具内） | 它**区分"被正确拦截"与"沙箱自己坏了"** |
| plan（log-only 软指导）/ todo（整表替换）/ goal（CAS 状态）/ schedule（宿主级） | `plan_runner` + `TaskState` 揉在一起 | 它**拆成四个独立包**，各管一件事 |
| llm（adapter 契约 + 可重建请求 + 互斥 usage） | `ChatEngine` + `StepResult.usage` | 它的 adapter 契约是**成文的十条**；usage 互斥 |
| `ContextForm`（语义词汇，视觉归消费者） | 无 | 值得偷：**词汇只描述语义，不描述外观** |
