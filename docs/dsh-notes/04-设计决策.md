## 0. 决策记录本身就是一项设计决策

`README.md` 定义了 **Agent Note**：一份记录"**为什么** + **放弃了什么**"的设计文档，分两类轴：
- **生命周期**（顶层目录）：`proposed/`（未建）→ `implemented/`（已发货，**且随代码更新而更新事实**）→ `rejected/`（考虑后拒绝）→ `archived/`（冻结）。
- **类别**（嵌套目录）：`feature` / `bug-fix` / `simplification` / `architecture` / `process` / `testing`。

**固定文件格式**（`verify-agent-note-format` 强制）：`Problem` → `Decision` → `Alternatives considered` → `Consequences`。

> **最值钱的是 `Alternatives considered`**。它记录"考虑过 B/C/D 为什么不要"——这是代码和测试永远载不动的信息。我们 ai-coding 的 `docs/r*-analysis.md` 有这个基因，但**没有把它制度化成"每决策一篇、含被拒方案、随代码更新"**。

**归档纪律**：已归档的 triplet **永久冻结**，不得编辑/翻译/移动/删除，也**不得当作当前行为的权威**。只有"已发货决策完整、理由不太可能指导未来、但仍有历史价值"的才归档；**绝不归档 proposed**（要么拒绝要么留着）。

## 1. 奠基决策（按重要性）

### D1. 事件溯源会话：日志就是状态

> **A `Session` is an append-only log of typed `SessionEvent`s — the single source of truth. The LLM message history is *derived* from the log.**

- **替代方案（被拒）**："可变消息数组 + 事件仅作通知"——更简单，但**状态与日志可能分叉**。事件溯源下**日志就是状态，分叉在结构上不可能**。
- **后果**：replay/trace/telemetry **结构上被保证，不是外挂**。派生成本随日志增长 → **用 compaction（surface 替换）缓解，而不是改日志**。
- **缓存稳定性是推论 #1，不是头条**（见 D3）。

> 这是 dsh 与 ai-coding 的**根本分界**。我们把 `SessionData.messages` 当状态；它把日志当状态，messages 是投影。

### D2. 能力接缝：三角角色

> 一个可替换能力有**三个关切，以不同速率、因不同原因变化**：*契约*（是什么）、*实现*（怎么跑）、*消费者 API*（模型和插件对什么编程）。把它们捆在一个包里 = 耦合变化速率。

三角：**Service Definition**（拥有 `ctx.<key>` 的 Cordis `Service`，**绝不是 TS `interface`**）/ **Service Provider** / **Consumer**。

- **替代方案（被拒）**："总是合并三角"（重新耦合）；`@cordisjs/plugin-capability`（那是**权限安全**服务，不同轴——**混淆两者正是这篇要命名的陷阱**）。
- **关键纪律**：**不要预先拆分**——一个只有一个可能 provider 和一个 consumer 的能力**保持一个包**，直到第二个出现。（LLM seam 就把 Definition 和 Consumer 折进 `dsh-llm`。）

### D3. 请求可重建：Model-visible ⟺ durably referenced

> **Anything that reaches a model request must be reconstructable from the session log and the immutable content-addressed objects it references.**

可检查的推论：**任何人拿着日志 + 引用的附件对象 + 钉死的代码版本，能逐字节重建每个 loop 请求。**

- **缓存稳定性是推论，不是目标**：append-only 日志 + 逐节点纯函数投影 → **只要 header 不变，请求就是前驱的 append 扩展**——**稳定性是涌现的，不是被管理的**。
- **被拒的替代方案（一串，很能说明思路）**：
  - **客户端为真相源**（MiniCode 字面做法）：与日志并存的第二真相 → 两者漂移，**没人发现**。
  - **有状态传输客户端镜像日志**：复制会话状态、需要 listener 回滚、留一条未记录编辑路径。
  - **每次调用的请求标量**（自由可变 config 交给每个 `agent/request`）：listener 可以零记账地每调用换模型，**静默抛弃 provider 缓存**。→ **config 是每会话的 logged 状态；waterfall 提议，日志记录。**
  - **检测并上报**（比较连续请求，分叉就警告）：事后发现；违规请求**仍可被构造并发出**。→ 拒绝，选**接口级不可表示**。
  - **事件驱动装配**（只在变更信号时重渲染）：漏信号 bug 类。→ 选**每步渲染 + 值比较，零信号纪律**。
  - **自定义 header-delta 编解码**：减少重复字节但**复制了表示及其 diff/apply/fallback 机制**。→ 选**全量快照，一种重放表示**。
  - **轻量 series 标记引用前一个 header**：从该标记开始的窗口**无法不取前驱就重建请求**。→ 选**自包含全量快照**。

### D4. 事件域语义：三个域，各管一件事，一条边界规则

> **durable、可重放的事实 = `SessionEvent`；live 拦截或瞬态/活对象信号 = `agent`/`tools` Cordis 事件。**

- `session/*`：durable、可重放的事实日志（也兼 live transcript feed——**live 渲染与重放投影共享一条路径**）。
- `agent/*`：总是携带活体 `Agent` 的 live 运行时表面。
- `tools/*`：工具注册表与执行流水线。

**边界规则的应用**：**turn/step 边界曾经同时是 session 事件和 `agent/*` 镜像 emit**——一个消费者对同一事实有两个真相源，每次生命周期变更都要改两处。**四个边界镜像全部移除**；消费者从 `session/event` 读边界。

> **这是一个"消除重复真相"的样板决策**，值得直接搬：**如果一个事实是 durable 的，它就只该有一个位置。**

### D5. 每条消息都是"有身份的不可变值"

> `Message` 有必需的 `id`/`role`/`content`/`source`。**消息在创建时就拿到 id**——在 inbox 路由、claim、pre-step 改写、durable append、请求投影**之前**。**同一个 id 存活过每一个表示边界。**

- `createMessage` 是规范创建边界（铸 id + detach + deep-freeze）；`freezeMessage` 是**导入**边界（身份已存在，不重新铸）。
- **替代方案（被拒）**：id 可选（保留歧义，无类型能证明准入/日志/投影保留了它）；让 agent 投递分配 id（让 agent 调用成为生产者最早能命名自己消息的点）；让每个 durable 事件分配新 id（**破坏与 live 输入的关联**，重放请求看起来含不同消息）；只在 agent/session 准入时冻结（留一段"已标识可变"区间）。
- **后果**：live inbox 事件、durable 事件、派生历史、模型请求**能关联同一条消息而不靠内容相等或信封专属 id**。

### D6. Session surface：日志之上的有序投影

> 加一个 **surface**——由 `surfaceOp` 标记维护的、派生的、缓存的**事件 seq 有序列表**（产生 LLM 消息的事件子集）。

- 两种操作：`append`（尾追加）/ `replace`（闭区间 `[startSeq, endSeq]` 遮蔽并就地插入）。
- **`SurfaceManager` 是增量的，不是全量重建**（全量重建是 O(N²)）。
- **替代方案（被拒）**：per-plugin `agent/request` 包装（listener 顺序脆弱、无 durable 记录、每个新操作都逼改 core 的 `deriveMessages()`）；半开区间；链表节点 + seq map（生产不读前驱链接）；全量重建 + dirty flag。
- **压缩骑在 surface 上**：追加一条既有 message-producing 事件（如 `user/message` 携带摘要）+ `surfaceOp: {op:'replace'}` + `sourceEventSeqs` 覆盖被遮蔽条目。**重放确定性地保留决策。**

### D7. 优先维护良好的依赖，而非手搓

> **引入外部依赖是合法的简化，不是策略例外。**

引入新依赖的门槛：
- **净删除**：替代真实的已拥有代码（实现 + 专门测试 + 文档），**不是假想的未来代码**。
- **健康**：活跃维护、广泛使用、传递足迹合理。
- **边界契合**：包的语义覆盖我们的实际契约。
- **不是已定的接缝**：schemastery、vendored Cordis 等**不因这条重开**。

- **被拒的替代方案**：保持隐式"不加依赖"文化（**它从未是被记录的决策**，代价具体：手搓协议/解析重复了久经考验的库，膨胀逐文件覆盖负担）；硬性批准清单；像 Cordis 一样 vendor 每个新依赖。
- **根因诊断**："仓库级外部依赖列表保持极小，而包各自长出自己的 SSE 解析器、协议分帧、重试循环、glob 匹配器。**AGENTS.md 里没有任何依赖策略**，所以 agent 从既有模式推断出一个比任何人决定过的都更严的规则。**这就是默认运行的 Not Invented Here 谬误。**"

> **这条对我们极其相关**：ai-coding 也有"能自己写就不加依赖"的反射。

### D8. Initiating Agent scope（用 AsyncLocalStorage）

> 强制服务 `ctx.agents` 用 Node `AsyncLocalStorage` 携带**发起 Agent**。

- `currentInitiator()` 可选读 / `requireInitiator()` 抛 / `withInitiator(agent, op)` 保持精确返回值 / `withoutInitiator(op)` 建立清除边界。
- **替代方案（被拒）**：每个函数传 Agent（重复转发）；暴露动态 `ctx.agent`（**混淆注册所有权与执行主体**，并发下意外）；单独 `ctx.agentExecution` 服务（无独立后端）；存命名/完整运行时帧（会造陈旧快照和另一个生命周期）；进程全局 `currentAgent`（并发 Agent 跨 await 互相覆盖）；**从模型可见参数派生身份**（模型/用户输入**不可信**去选 Session/租户/沙箱路由）。
- **后果**："**环境存在既非存活证明也非授权**"；ALS 只在显式边界内的异步链中。

## 2. dsh 决策方法论的**反复模式**（这是精华）

从上述决策里抽象出的、可迁移到任何项目的思维模式：

| 模式 | 表述 | 出处 |
|---|---|---|
| **结构上不可能 > 检测并上报** | 与其运行时验证，不如让违规**不可表示**（日志即状态、不可变消息、冻结请求） | D1/D3/D5 |
| **接口级不可表示** | "一个违规请求仍可被构造并发出"——所以拒绝 detect-and-report | D3 |
| **涌现 > 管理** | 缓存稳定性是 append-only + 纯函数投影的**推论**，不是被管理的属性 | D3 |
| **一种表示** | 全量快照胜过 delta 编解码：重复字节换"一种自包含重放表示" | D3 |
| **消除重复真相** | 一个 durable 事实只该有一个位置（移除边界镜像） | D4 |
| **一条边界规则** | durable 事实 → session 事件；live 信号 → agent 事件 | D4 |
| **失败关闭 / 响亮失败** | approval `unavailable`、sandbox 拒绝静默直通、坏配置加载即拒 | 03 篇 |
| **不要预先拆分** | 能力只有一个 provider 时保持一个包 | D2 |
| **优先维护良好的依赖** | 手搓是被记录的决策，不是默认 | D7 |
| **身份在创建时铸造** | 不在路由/准入时（避免"已标识可变"区间） | D5 |
| **显式 > 隐式（包边界）** | defaulting 是拥有实现里的显式 `resolve(request): Spec`，不是 `run()` 里隐藏的 `?? default` | AGENTS.md |
| **不可信输入不选路由** | 模型/用户输入不能选 Session/租户/沙箱 | D8 |

## 3. 对我们 ai-coding 的直接启发

1. **把决策记录制度化**：我们已有 `docs/r*-analysis.md`，但**没有**"每决策一篇 + 必含被拒方案 + 随代码更新事实 + 冻结归档"的纪律。**这是最低成本、最高回报的搬运。**
2. **"结构上不可能 > 检测并上报"** 直接适用于我们的：会话状态（D1）、消息身份（D5）、请求可重建（D3）。
3. **"消除重复真相"** 适用于我们的：`core/events.py` 与 `LoopObserver` 与 trace 的多路事实——是否有同一事实存在于两处？
4. **"优先维护良好的依赖"** 直接反驳我们"能自己写就不加依赖"的反射——**但要有门槛（净删除/健康/契合/非已定接缝）**，不是无脑加。
5. **"不可信输入不选路由"** 是安全不变量，值得直接写进我们的 guard 设计。
