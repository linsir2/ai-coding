## 1. 三种协作机制（这是"怎么触发别的插件"的答案）

dsh 的插件之间**只有三种耦合方式**：

| 机制 | 形态 | 何时用 | 例 |
|---|---|---|---|
| **服务调用** | `ctx.<key>.method(...)` | 需要**直接能力**、知道对方是谁 | `ctx.llm.stream()`、`ctx.tools.executionMode()`、`ctx.systemPrompt.assemble()` |
| **事件** | `ctx.emit/waterfall/serial/parallel/bail(name, ...)` | **不知道谁在听**，要广播/拦截 | `agent/pre-step`、`session/event`、`tools/pre-execute` |
| **依赖注入** | `inject: ['shell']` | 声明"我**需要**某能力"，由框架决定加载时机 | 消费者声明 `inject: ['llm']`，fiber 挂起直到 provider 出现 |

> **纪律（primer 原文）**："**优先用事件做拦截和策略；优先用服务方法做直接能力调用。**"
> 即：**要改行为、要否决 → 事件（waterfall）；要干活 → 服务调用。**

## 2. 事件扇出地图（谁产谁消）

`event-producer-consumer.md` 是**生成的**——从 TypeScript Program 解析每个事件的 dispatcher 和 listener。几个关键扇出：

| 事件 | 模式 | 生产者 | 消费者数 | 意义 |
|---|---|---|---|---|
| **`session/event`** | emit | `session` | **~30 个** | **中心扇出**：持久化、投影、telemetry、title、token-meter、tools、subagent… 全部从这里读 durable 事实 |
| **`agent/pre-step`** | **waterfall** | `agent-loop` | **~14 个** | **最强拦截点**：compaction、plan-mode、hooks、session-checkpoint、context 注入… 都能 rewrite/reject |
| `agent/created` | serial | `agent` | ~13 | 每-agent 初始化；**awaited**，失败即创建失败 |
| `agent/request` | waterfall | `agent-loop` | 2 | 换 provider/model/reasoning |
| `agent/request-error` | waterfall | `agent-loop` | 3 | compaction-basic、image-offload、llm-retry——**错误恢复** |
| `tools/pre-execute` | waterfall | `tools` | 5 | hooks、jobs、workspace-changes、auto-review |
| `tools/execute` | waterfall | `tools` | 6 | timeout-policy、checkpoint-policy、browser-use… |
| `tools/post-execute` | waterfall | `tools` | 6 | spill-policy、repeat-tool-reminder、fs-search… |
| `system-prompt/assemble` | waterfall | `system-prompt` | 4 | agent、working-directory、session-reference… |
| `approval/request` | waterfall | `user-approval` | 2 | acp、remotes |
| `llm/stream` | waterfall | `llm` | 3 | llm-replay、checkpoint、session-title |

**观察**：
- **waterfall 密集在"决策点"**（pre-step/request/request-error/tools.*/approval/system-prompt/llm）。这就是"不改循环就能加策略"的实现。
- **`session/event` 是 emit（广播）**，不是 waterfall——它是**事实流**，只观察不改。
- **turn/step 边界不再是 `agent/*` 事件**（D4 决策：边界是 durable 事实，只在 `session/event`）。

## 3. 一次 turn 的完整编排（源码级）

`packages/core/agent-loop/src/agent.ts` 的 `turn()`（298–398 行）和 `step()`（400–561 行）是**编排的实际所在**。骨架：

```ts
// agent.ts:298 turn()
async turn() {
  session.append('turn/start', { turn })              // ① 开 turn
  while (true) {
    const decision = await this.preStep(target, {turn, step})   // ② 认领 + 装配 + waterfall
    if (decision.kind === 'reject') { turnEnds = {kind:'blocked'}; return false }
    if (首次 && messages 为空) { turnEnds = {kind:'completed'}; return false }  // 空 turn 不花模型调用
    session.append('step/start', {turn, step})        // ③ 开 step
    const stepEnd = await this.step(decision)         // ④ 跑 step
    if (turnEnds && inbox.nextStep.length === 0)
      await dispatch.serial('agent/turn-stopping', {turn, signal})   // ⑤ 终止检查
    if (turnEnds && inbox.nextStep.length === 0) break
    target = 'next-step'                              // 后续 step 只认领 next-step
  }
  session.append('turn/end', {turn, reason: turnEnds})  // ⑥ 关 turn
}
```

`preStep()`（267–288）——**认领 + 装配 + 拦截**：

```ts
const claimed = this.inbox.claim(target, turn)                        // 认领
const assembly = await this.loopCtx.systemPrompt.assemble(ctx)        // 装配（waterfall）
const decision = await this.dispatch.waterfall(
  'agent/pre-step', {messages: claimed, ...position, signal},
  () => ({kind:'enter', messages: claimed + 运行时上下文}),           // 默认行为
)
```

`step()`（400–561）——**准备 → 流式 → 工具**：

```ts
const {config, preparedCall} = await this.prepareRequest(turn, step, signal)  // agent/request waterfall + prepareCall
// 系统提示按节点 reconcile（in-history 追加 vs 新系列合并）
for (const {message, intent} of commits) session.append('system/message', ...)
// 首次尝试：把 entered 消息追加为 user/message
for (const message of decision.messages) session.append('user/message', message, {surfaceOp:'append'})
const request = this.buildRequest(config, preparedCall, assembly.tools, ...)
const stream = preparedCall?.stream(request) ?? this.loopCtx.llm.stream(request)  // llm/stream waterfall
for await (const chunk of stream) live.push(chunk)
live.settle('assistant/message', () => session.append('assistant/message', {...}))  // 结算
const toolCalls = message.content.filter(b => b.type === 'tool-call')
await executeToolCalls(this.loopCtx, turn, step, toolCalls, signal, acceptContext)  // 工具调度
```

**四个关键顺序不变量**（源码与测试锁死）：
1. **`assistant/message` 在工具派发之前 append**——"durable 日志记录工具所遵循的确切消息"。
2. **`assistant/attempt` 保留无 surface 消息的失败/重试尝试**（内嵌流），**不伪造模型历史**。
3. **重试不重跑装配、不重跑 `agent/pre-step`、不重复 user 准入**（`step()` 里的 `while(true)` 循环）。
4. **`max-tokens` 粘性**：任何 step 触顶，后续正常 step **不得降级** turn 结果。

## 4. 拦截点全清单（waterfall = 插件改行为的唯一合法入口）

| 拦截点 | 能做什么 | 谁在用 |
|---|---|---|
| `system-prompt/assemble` | 改装配的 prompt 分节与工具 | agent、working-directory、session-reference |
| **`agent/pre-step`** | **reject 一步 / 替换进入的消息** | compaction、plan-mode、hooks、checkpoint、各种 context |
| `agent/request` | **替换冻结的 call 配置**（换 provider/model） | agent、webhook |
| `agent/request-error` | **恢复失败的模型请求**（返回 `{kind:'retry'}`） | compaction-basic、image-offload、llm-retry |
| `tools/pre-execute` | 策略、审批、沙箱 | hooks、jobs、auto-review |
| `tools/execute` | 围绕派发（超时、重试、指标） | timeout-policy、checkpoint-policy |
| `tools/post-execute` | accept/block/replace/加上下文 | spill-policy、repeat-reminder |
| `approval/request` | 应答一次审批 | acp、UI remotes |
| `llm/stream` | 短路或路由一次模型调用 | llm-replay、session-title |
| `compaction/summary-error` | 恢复失败的摘要请求 | image-offload |

> **每个 waterfall 的纪律**：只观察/注解的 listener **必须调 `next()`**；不调就是**故意否决**。忘了 `next()` 会**静默吞掉下游所有人的默认行为**。

## 5. 工具调度（exclusive barrier + bounded rolling pool）

`tool-calls.ts::executeToolCalls`：

```
按模型顺序遍历 planned calls：
  mode = ctx.tools.executionMode(call).kind      ← 每次分类前先 commit，使注册表变更影响未启动调用
  if mode === 'parallel':
      group = planned.slice(next)                ← 取连续 parallel 段
      有界滚动池（maxParallelToolCalls 上限），派发可重叠
  else:
      group = [first]                            ← exclusive 单独跑，作为顺序屏障
  结果的**策略/结果/结果上下文保持模型顺序**
```

- **abort**：停止补充，排空已启动调用，**为未启动调用记合成错误结果**（保持重放有效）。
- **内部调度失败**：停止新派发，排空已启动，以首个失败 reject；**拥有该 step 的层记保守恢复结果**再关闭。
- **分类是"一元"的**（Known Limitations）：安全性取决于**比较兄弟调用或资源**的调用**必须保持 exclusive**。

## 6. 作用域（scope）如何过滤事件扇出

`ctx.emit('agent/pre-step', ...)` 这类**关于某个 agent 活动**的事件，**用该 agent 的 carrier 派发**（scoped dispatch）：**agent 作用域内的 listener 只收到它自己的 agent**。而**关于注册表本身**的事件（如"一个工具被加了"）是 registry-subject，**保持不过滤**。

> 两级、扁平：scoped 注册**不下传**给子 agent；子树行为用 **lineage 数据**表达，**绝不用 scope 结构**（glossary:13）。

## 7. 编排的完整心智模型（一张图）

```
                    ┌─────────────────────────────────────────────┐
   followup(msg) ──▶│ Agent.inbox (next-turn / next-step)         │
                    └───────────────┬─────────────────────────────┘
                                    │ 唤醒 driver
                    ┌───────────────▼─────────────────────────────┐
                    │ Driver.turn()   [agent-loop/src/agent.ts]    │
                    │  append turn/start                           │
                    │  ┌────────────────────────────────────────┐  │
                    │  │ preStep()                              │  │
                    │  │  inbox.claim() ──────────▶ session     │  │
                    │  │  systemPrompt.assemble() ─▶ waterfall   │  │
                    │  │  dispatch.waterfall('agent/pre-step')  │  │◀─ 14 listeners
                    │  └───────────────┬────────────────────────┘  │
                    │  append step/start                           │
                    │  ┌───────────────▼────────────────────────┐  │
                    │  │ step()                                 │  │
                    │  │  prepareRequest()                      │  │
                    │  │    waterfall('agent/request')  ────────┼──┼◀─ 换路由
                    │  │    llm.prepareCall()                   │  │
                    │  │  append system/message, user/message   │  │
                    │  │  llm.stream() ────────────▶ waterfall   │  │◀─ llm/stream
                    │  │  append assistant/message              │  │
                    │  │  executeToolCalls()                    │  │
                    │  │    tools/pre-execute  ─────────────────┼──┼◀─ 策略/审批/沙箱
                    │  │    tools/execute      ─────────────────┼──┼◀─ 超时/重试
                    │  │    tools/post-execute ─────────────────┼──┼◀─ spill/提醒
                    │  │    append tool/result                  │  │
                    │  └───────────────┬────────────────────────┘  │
                    │  dispatch.serial('agent/turn-stopping')      │◀─ 终止钩子
                    │  append turn/end                             │
                    └──────────────────────────────────────────────┘
                                    │
              session/event (emit) ─┴─▶ ~30 listeners（持久化/投影/telemetry/…）
```

**三个"谁触发谁"的答案**：
1. **driver → 插件**：靠 **waterfall**（拦截点）和 **emit**（事实广播）。
2. **插件 → driver**：靠 **服务调用**（`agent.followup/steer/inject`、`ctx.tools.register`、`agent.inject()` 落进 inbox）。
3. **插件 → 插件**：靠 **服务**（`ctx.llm`、`ctx.tools`）和 **capability 事件**（`fs/*`、`tools/*`），**不 import 彼此**。

## 8. 对照 ai-coding（动态协作视角）

| 机制 | dsh | ai-coding | 差距 |
|---|---|---|---|
| 拦截 | 10 个 waterfall 点 | `guard.py`（DENY/observe）+ `LoopObserver`（emit） | **我们没有 waterfall**：拦截是 guard 链里的 if，不能"包装/否决/替换" |
| 事实广播 | `session/event`（~30 listener） | `LoopObserver.on_event`（一个观察者） | 我们的扇出是**单点**，不是多播 |
| 依赖加载 | `inject` 驱动 | `build_world` 手写顺序 | 顺序靠人记 |
| 工具调度 | exclusive barrier + 有界并行池 + 模型序结果 | `dispatch_batch`（`parallel_safe` 一票串行） | **效果等价**；它的"分类前先 commit"更细 |
| 作用域 | `scope`（两级扁平 + carrier 过滤） | 无 | 我们单 agent，暂不需要 |
| 声明式 agent | `cordis.yml` 的 `agents:` 条目启动 | `cli.py` 装配 | 它可配置启动 |

> **最该偷的动态机制**：**waterfall 拦截**。把 `guard.py` 的"链式 if"升级成"可包装/可否决的事件链"，`agent/pre-step`、`tools/pre-execute`、`agent/request-error` 三个点收益最大（分别对应我们的 nudge 决策、权限门、模型失败恢复）。
